File view ids share the page-id namespace (both address one sandboxed iframe entry per id), so a duplicate across `pages` and `fileViews` is rejected. One manifest may not declare the same content type in two file views — the open-file resolver could not pick between them. Each file view's `entry` must be a listed `text/html` file; content types are exact strings, no wildcards.

Capabilities are the consent set. `CAPABILITIES` in `packages/app/shared/plugins.ts` is the closed list, and `plugins_capability_validator` in `schema.ts` must match it exactly:

| Capability                         | Grants                                                                             |
| ---------------------------------- | ---------------------------------------------------------------------------------- |
| `plugin.secrets.read`              | Read the secrets configured for this installation                                  |
| `outbound.fetch`                   | The plugin's own backend may call its declared outbound origins                    |
| `workspace.files.read`             | Read workspace files                                                               |
| `workspace.files.write`            | Put `files:write` on a service grant, capped by its destination prefix             |
| `workspace.files.create-read-only` | Let a sealed service lock only the new file it creates                             |
| `workspace.files.own-write`        | The plugin's backend may create, update, and archive files in folders it owns (see "Plugin-owned files" below) |
| `workspace.files.own-access`       | The plugin may lock its own nodes read-only and restrict them to its private scopes |
| `plugin.data.read`                 | Read this installation's stored documents                                          |
| `plugin.data.write`                | Create, change, and delete them                                                    |
| `plugin.data.user-write`           | Pages and file views may store and change them as the acting member, via the app   |
| `plugin.backend.invoke`            | Pages and file views may run the plugin's backend on demand (see "Invoke runs" below) |
| `plugin.service.connect`           | Pages and file views may pass their access to a server outside the app (see below) |
| `ui.outbound.fetch`                | The plugin's pages and file views may call its declared UI outbound origins        |
| `workspace.members.read`           | Pages and file views may list every member of the workspace (see below)            |

Several capabilities and manifest fields imply another one, and `plugins_validate_manifest` rejects the manifest at publish instead of letting it install and fail later:

- `plugin.data.write` requires `plugin.data.read`. A plugin that can only write would store documents it can never read back.
- `plugin.data.user-write` requires `plugin.data.read` for the same reason.
- `workspace.files.create-read-only` requires `workspace.files.write`. It adds one create-time mode to the sealed upload door; it is not general lock authority.
- `workspace.files.own-write` requires `workspace.files.write` — it is a narrower door on the same file surface, and keeping the base capability visible keeps the consent honest.
- `workspace.files.own-access` requires `workspace.files.own-write`. Own-access only creates and releases locks on files own-write maintains; alone it would consent to authority over files the plugin can never produce.
- `plugin.service.connect` requires `plugin.data.read` or `workspace.files.write`. On its own it can obtain no scope, so the grant mint would always refuse it. `outbound.fetch` does not satisfy this: that is the plugin's own backend calling out, not an outside service acting for the plugin.
- `plugin.backend.invoke` and `backend.endpoints` require each other in both directions, like `ui.outbound.fetch` and its origins: the capability needs a `backend` block with at least one endpoint, and declared endpoints need the capability.
- A manifest `service` block requires `plugin.service.connect`, and each declared service scope requires the capability that gates it at exchange time (`plugin_data:read` → `plugin.data.read`, `plugin_data:write` → `plugin.data.write`, `files:write` → `workspace.files.write`).
- `userWritableCollections` requires `plugin.data.user-write`: the list narrows the user-write door, so without that door it means nothing.

`ui.outbound.fetch` and `uiOutboundOrigins` require each other in both directions. The capability with no origin would grant nothing, and origins with no capability would widen the frame's policy without the install dialog listing a capability for it.

## UI outbound origins

`outboundOrigins` is the plugin's backend calling out from the runner. `uiOutboundOrigins` is the plugin's UI calling out from a member's browser. They are separate lists, separate capabilities, and separate consent entries — the same origin in both is new to each of them (`plugins_consent_diff` returns `newOutboundOrigins` and `newUiOutboundOrigins`). That UI surface holds the member's session token, so whatever it may reach can be reached by anything that manages to run inside it.

Read "page" below as "page or file view". The list lives on the version, not on a page entry, and `plugin_page_csp` is applied to every plugin asset response — so a plugin that declares only `fileViews` still has these origins enforced on its file-view iframe, and still grants the same reach. See "Plugin file views" below for the machinery they share.

The list is enforced by the browser, not by app code: `plugin_page_csp` in `plugins_ui.ts` builds `connect-src 'self' <CONVEX_CLOUD_ORIGIN> <CONVEX_CLOUD_WS_ORIGIN> <uiOutboundOrigins…>` for the asset response, so a page that asks for any other destination is stopped. The two Convex origins are host infrastructure, not consent: since SDK 0.9.0 the page runs its own `ConvexClient`, which needs the `https` origin for its HTTP calls and the `wss` origin for its sync socket, so dropping either one breaks every plugin page's data bridge. Only `uiOutboundOrigins` comes from the manifest. Two consequences worth remembering:

- The policy comes from the **immutable version being served**, never from an installation. An asset request carries a version id and a path and nothing else, so the response cannot know which workspace is looking at it. One plugin's declared origin therefore never widens another plugin's page.
- `install_version` requires `acceptedUiOutboundOrigins` to equal the version's list exactly, with its own message (`Install must accept exactly the UI outbound origins the plugin declares`). A consent dialog that showed only backend origins cannot install.

**Two screens show this to a person, and both must say the same thing.** The install consent dialog and
the plugin Access screen each warn that a UI surface is trusted with whatever its capabilities expose.
Gate that warning on `pages.length > 0 || fileViews.length > 0`, never on pages alone, and name both
surfaces in the warning and in the network-access heading. A file view holds the same workspace-wide
file scopes as a page — `public_api.ts` builds the `plugin_ui` principal from the installation and never
reads the session's `fileNodeId` — so a plugin that ships only file views is exactly as trusted and must
be described that way. This has drifted twice: the dialog was fixed while the Access screen still said
"Plugin pages", and before that the dialog itself had no file-view section at all. When you change one
screen's copy, change the other in the same edit.

`workspace.files.write` reaches three doors for a sealed processing-phase service grant carrying `files:write` and a destination prefix. The `/api/v1/files/service-uploads/*` pipeline (see `../public-api/SKILL.md#service-upload-routes`) is the blob path, and it also covers cleaning up what the service stored: `archive-destination` archives the grant's own destination folder with everything inside it (what the Council delete calls), and `delete` archives the committed files one target key stored or cancels their unfinished placeholders. Since the invoke-door plan, such a grant also reaches `/api/v1/files/write` for Markdown strictly inside its seal — create plus in-place update, which is how a service rewrites a note it owns — and `/api/v1/files/plugin-archive` for a file it wrote there (`pluginServiceWritePluginName` provenance). Every other generic `/api/v1/files/*` route still leaves `plugin_service` out of its `allowedKinds` and refuses such a grant with 403. Archiving, not hard deletion, is what "delete a file" means in this product — see `../data-deletion/SKILL.md`.

`workspace.files.create-read-only` does not add a token scope. `create-target` checks it only when the required `readOnly` request flag is true, then rechecks the actor's live `content.permissions.manage` at the effective destination ACL before writing anything. The host records the exact service target on the new node. Only service cleanup for that same live target may pass that direct lock, while the capability and actor ACL still hold. Member lock changes clear the target pointer.

## Plugin-owned files (`workspace.files.own-write` / `workspace.files.own-access`)

Ownership is the internal `files_nodes.pluginOwnerName` stamp — the plugin NAME (not the installation id), so frozen output is adoptable on reinstall. Public file doors can never set it. An invoke run with `workspace.files.own-write` creates owned folder chains through `/api/v1/files/plugin-folders/ensure` (every created folder stamped), writes and updates files inside its stamped area through `/api/v1/files/write`, and archives owned nodes through `/api/v1/files/plugin-archive`; the route contract is in `../public-api/SKILL.md#plugin-file-doors`.

**The stamp closes the member sharing and lock doors.** `files_nodes_db_has_plugin_owner_authority` answers yes for any stamped node and any node whose lock points at one, and every member-facing share/restrict/lock door refuses it (`Plugin-managed files cannot be shared.`, `This item is managed by a plugin.`). So the moment a plugin stamps a folder, members lose the sharing and lock buttons on it — say this in the `workspace.files.own-write` consent copy, because "the plugin owns this folder" means members can no longer manage its sharing. Two rules follow: a member cannot unlock a stamped read-only file, so `plugin-access/set` with `readOnly: false` and `plugin-archive` are the only release doors; and a file a `plugin_service` writes through `/api/v1/files/write` gets NO stamp (only the private `pluginServiceWritePluginName` provenance), so members keep normal sharing and unlock on it.

`workspace.files.own-access` is the declared-access half: `access.readOnly` writes a direct plugin-passable lock (`readOnlyPluginName`), and `access.readScopeId` binds the node's readers to one live private scope of the same installation. The host restricts the node, mirrors one `content.read` grant per scope member (`plugins_file_access_bindings`, at most 4 bound nodes per scope, `MAX_SCOPE_PRINCIPALS` = 50 readers), and maintains the mirror synchronously in `user_manage_scope` — adds and removals both, because no file write interleaves. Scope deletion and account/org teardown (`cleanup_stranded_scopes`) remove the mirrored grants and binding rows; the node stays restricted. The organization owner still reads everything — plugins must keep disclosing that. Plugins never name users; the only principal input is a scope id.

## Invoke runs (`plugin.backend.invoke`)

A page or file view calls `POST /api/v1/plugin-backend/invoke` with its `plu_` token to run the plugin's own reviewed backend synchronously — route contract in `../public-api/SKILL.md#invoke-door`. The run is a normal `plugins_event_runs` record with event `ui.invoke.requested`: same runner, same `plr_` token, same `MAX_API_CALLS = 20`, same call ledger and retention. The plugin's `fetch()` now serves two callers: plugin-declared endpoint paths handle invokes, and host events arrive on the reserved `/__bonobo_senate/run` path — manifest validation refuses endpoint paths under `/__bonobo_senate`, and the runner refuses such a `requestPath` too, so a plugin route can never shadow or spoof an event delivery. The run's `actorUserId` is the member behind the `plu_` session, host-verified and delivered only in the event envelope — never inside the page's `input` — so backends enforce authorship from the envelope alone; the same id lands on the `plugin_run` principal, so store writes record that member as `createdBy`/`updatedBy`. Serialization: at most one live invoke run per `(installationId, lockKey)` — the default is one lock for the whole installation, and an endpoint declared `serialization: "caller-key"` uses the caller's `serializationKey`; a concurrent second invoke answers 409 `busy` with `retryAfterMs`. File reads for runs (`files:read` + `files:list`) are gated on accepted `workspace.files.read` for BOTH invoke and upload runs, and a run reads with its actor's eyes, so it never sees inside a restricted folder that member cannot open.

`plugin.service.connect` is the only capability whose holder is not code the app runs. It lets a plugin frame exchange its `plu_` token for an installation-bound `psg_` service grant, so the publisher's own server keeps working while nobody has the plugin open. A file view drives that exchange exactly as a page does: `plugins_service.ts` accepts any `plu_` UI token, and a page and a file view both carry one. So the capability row above says "pages and file views", and both consent screens must say the same thing, under the same both-screens rule as the UI outbound warning. A dialog that names only the page understates this capability by half.

The ceiling around it: the mint refuses outright unless the installation accepted `plugin.service.connect`, each scope is gated on its own capability, and the resolver rechecks both on every call. **An upgrade revokes every outstanding grant; it never narrows one.** An upgrade moves the installation's `pluginVersionId`, and `resolve_principal` refuses any grant whose stored `pluginVersionId` no longer matches, so the outside server stops now instead of when the grant expires. A capability cannot be taken away on its own either: `acceptedCapabilities` is only ever written as the new version's `capabilities`, in the same patch that moves `pluginVersionId`, and `install_version` refuses a partial acceptance. The resolver still narrows the stored scopes against the live capabilities on every call, but nothing in the app can currently produce an installation that reaches that branch. See `../public-api/SKILL.md` for the `plugin_service` principal and `#service-grant-exchange` below for the routes that mint and renew one.

## Rebuilding and publishing a plugin is pre-authorized here

**The user granted a standing authorization on 2026-09-01: build a plugin, push its repository, and
publish a new version without asking first.** The reason is that this deployment is the only one —
there is no production environment yet, so a plugin release reaches nobody but this dev workspace.
Do not stop a fix half-finished and hand back a "needs your republish decision"; finish it.

What the authorization covers: bumping a plugin's version, building it, pushing the plugin repository,
publishing the new version from the plugin detail page, updating the installation, and re-consenting
when the capability list changed.

What it does NOT cover, so keep asking for these:

- Deleting or resetting the registry, or a `hard_delete_plugin_from_registry` pass.
- Deleting user data to make a release land, including recreating files that hold content a person
  wrote. Recreating a plugin's own derived files (a transcript the plugin rebuilds from its store) is
  part of the release and needs no separate ask.
- Anything that reaches a service outside this deployment beyond the plugin's own GitHub repository.
- A production deployment, once one exists. Re-read this section then, because the reason above stops
  being true the day it does.

Practical note, unchanged by the authorization: `publish_version` refuses any principal that is not
`signed_in`, so publishing cannot be done from a CLI or an anonymous session. Drive the plugin detail
page in the user's signed-in browser profile (`app-playwriter-harness`), and never sign in or out.

Publishing behavior in `publish_version_from_github` (`packages/app/convex/plugins.ts`):

- Declared over-limit input is rejected before any file fetch, upload, or registration.
- Each review model request has two bounded retries for retryable provider errors. The AI SDK honors
  `Retry-After`, and the review's five-minute abort signal covers both requests and retry waits. Keep
  the retry inside the current review: restarting the publish repeats its earlier model calls and can
  hit the same token-rate window at the same later step.
- After reading only branch HEAD and the manifest, publishing rejects foreign plugin-name ownership and conflicting immutable versions before artifact downloads, AI review, uploads, or cleanup-attempt writes.
- Bodies are read through `read_response_body_bounded` — a streaming reader that cancels past the bound. `Content-Length` may pre-reject but is never the enforcement boundary. Exact byte-count and SHA-256 checks still run after the read.
- Downloads and uploads each run through a 4-wide shared-index worker loop (`ARTIFACT_DOWNLOAD_CONCURRENCY` / `ARTIFACT_UPLOAD_CONCURRENCY`), never unbounded `Promise.all`.
- The detail-page Publish, Install/Update, Uninstall, and Remove claim actions are one mutually exclusive group. While one request runs, block every sibling action in both the control state and its handler guard. Keep the active action's own focus-return control enabled and expose progress with `aria-busy` when that control stays mounted.

Publication visibility uses the required `sourceStatus` lifecycle only:

- A new or resumed exact artifact is `preparing`, non-latest, and unavailable to marketplace, install, runtime, page, mint, and asset paths.
- Source files are written under the version id. A failed write marks the version `failed`; an exact retry resumes idempotently.
- Registration and the final visibility mutation both recheck the live publisher account and the exact repository claim id, URL, and owner that authorized the publish. Account deletion, removing the claim, or reclaiming the URL while external work is in flight leaves the version non-ready.
- Publishing is bound to one independently reviewed commit. The operator first calls the read-only `get_publish_candidate_head`, records and reviews that full SHA, then pastes it into the confirmation dialog. `publish_version` requires it as `expectedSourceCommitSha` and compares it immediately after reading the current default-branch HEAD. A moved branch is a `conflict` before manifest or artifact fetches, review work, cleanup state, or R2 writes. The preflight must never copy current HEAD into the expected field for the operator.
- One final mutation changes the complete version to `ready`, records that ready time, demotes the previous latest version, and promotes the new version in the same transaction. It makes ready time strictly increase even when two mutations share one millisecond. Publisher history and repository cards use this ready time, so retrying an older failed version still makes it the visible current release everywhere. The `repair_plugins_versions_is_latest` migration uses the same rule and has a fresh migration identity, so a completed older backfill cannot skip it. It picks the newest ready `updatedAt` value and clears every other latest marker for that plugin in the same transaction. If old rows tie at the newest time, it keeps the valid current latest marker inside that tie.
- An exact artifact that is already ready is immutable: a later commit returns its stored version and source commit without replacing pointers or uploading another copy.

# Durable publish-artifact cleanup

Interrupted publishing must not orphan R2 objects. The lifecycle, all in `packages/app/convex/plugins.ts` plus the `plugins_publish_artifact_cleanup_attempts` table (`schema.ts`, indexed by cleanup deadline and by plugin/deadline):

- Every publish attempt creates a fresh `uploadId` and embeds it in every R2 key. Before the first upload, one mutation (`create_publish_artifact_cleanup_attempt`) inserts the exact key set (manifest + files, at most 65) and schedules cleanup one hour later. Attempts never share keys, so an old cleanup cannot delete a retry's uploads.
- `run_publish_artifact_cleanup_attempt` refuses before `cleanupAt`, keeps only exact keys owned by a ready version, deletes at most 10 unowned keys per operation, patches the remainder, and reschedules until empty. If the matching version is still `preparing` or `failed` and its manifest key belongs to this attempt's `uploadId`, the same attempt then drains its partial source tree and deletes the incomplete version. It also deletes the deciding review when account deletion already anonymized it and no version or repository `lastPublishAttempt` still links to it. An older attempt never deletes a version now owned by a newer retry. Object deletion is idempotent; external failure retains the batch and retries.
- Successful registration removes the attempt (`remove_publish_artifact_cleanup_attempt`) only once the registered version owns the exact keys.
- An hourly cron (`schedule_due_publish_artifact_cleanup_attempts`) schedules a bounded number of due attempts as a fallback.

Plugin artifact cleanup does not list the bucket. It deletes the exact R2 keys stored on versions and cleanup-attempt rows. Other app areas may use R2 listing for their own jobs; do not generalize this plugin rule to the whole codebase.

Admin registry deletion is name-scoped and requires publishing to be quiescent. Preview and deletion find versions, all reviews by plugin name, cleanup attempts by plugin name, installations, and run/call history by immutable plugin version id. Hard delete checks active publish cleanup leases through the `(pluginName, cleanupAt)` deadline index, so expired attempt history cannot make this fence read unbounded. This version-keyed traversal is required because uninstall keeps run history and upgrade can move the live installation to a newer version. The preview shares fixed budgets across large registry docs and across their smaller child rows. Every number is exact while `previewTruncated` is false; when it is true, one or more numbers are lower bounds and the operator should drain another bounded delete pass before reading again. Call `hard_delete_plugin_from_registry` repeatedly for one plugin name until it returns `done: true`. The first call creates a durable `plugins_registry_deletion_fences` doc before it drains anything. Install, publish preflight, review storage, publish-attempt feedback, artifact-attempt creation, version registration, and finalization all read that fence in their own transaction and refuse or no-op for the name while it exists. A failed or lost delete pass leaves the fence in place; resume the same delete. The preview reports this as `deletionFenced`. The fence also stays after `done: true`: a publish action can be paused in review without holding a database transaction, so an automatic clear could let that old action recreate the plugin after the drain. After old publish actions are quiescent and the delete returned `done: true`, call `clear_plugin_registry_deletion_fence`. It refuses while any version, installation, review, cleanup attempt, or named publish attempt remains. Clearing is the explicit recovery point after which the name may be registered again. The first bounded phase also marks every matching enabled installation disabled before any drain starts. That stored status makes page sessions, plugin-data writes, service-grant mints, service writes, and queued event-run starts fail closed while later calls drain the docs. A running event run requests cancellation and returns `{ done: false, deleted: 0 }`, so retry after the run reaches a terminal status. Before deleting each review, it clears one repository `lastPublishAttempt` that points at that review and returns for another bounded pass. A shared or losing publisher claim therefore never keeps a dangling review id. After reviews and cleanup attempts are gone, the `by_lastPublishAttempt_pluginName` index lets one more bounded pass clear any named attempt with no review id. This matters when a shared repository claim stays for another plugin name: the deleted name's old failure must not block later feedback for the surviving name. For the repository's last version, deletion drains publisher secrets before deleting each exact R2 key once, then removes the claim and version together. Name cleanup deletes a repository claim only when no other plugin version uses that URL and the current claimant is the version creator; it never deletes another user's reclaimed claim. Once a name preview is zero, `hard_delete_publisher_repository_now` removes any remaining claim-only repository and its secrets by repository id; claims cannot carry a plugin name because claiming happens before the manifest is fetched. Deletion removes each run's activity before the run doc, and the preview reports the count as `runActivities`. Only the `activities.by_source_id` index links the two, so removing the run first would leave the activity in the workspace feed with no producer that can ever clean it up. The preview walks runs, so it also reports zero once the runs are gone whether or not their activities went with them — assert registry deletion against the `activities` table itself, not against the preview.

# Review pipeline

- Publishing reviews every executable or renderable text file, not only the backend entrypoint. File selection uses both MIME and extension. Decoding is fatal UTF-8 and keeps a leading BOM because publishing uploads the original verified bytes. Classification or decode mismatches reject deterministically. Backend entries must be JavaScript by both classifications.
- Mechanical checks run first and have two severities. `plugins_dist_review_mechanical_findings` returns `{ findings, advisoryFindings }`, stored as `mechanicalFindings` and `mechanicalAdvisoryFindings`. Only `findings` rejects; a non-empty array stops the publish before the model call. The **content** checks reject — dense `\x`/`\u` escapes, a base64 literal of 256+ characters, and the `Function` constructor — because an author writes those on purpose and each hides code from the review. The **shape** checks are advisory — longest line, average line length, and single-character identifier share — because a normal vendored or bundled dependency trips them and the plugin author cannot fix it. Preflight decode and entrypoint findings reject with the content checks. The 10,000,000-byte review bundle limit is an operational input refusal and never writes a review doc. Advisory findings are recorded on the stored review even when the version passes, and the publisher releases list renders them under their own "Advisory — did not block this version" heading.
- Immutable reviewer policy is sent as developer/system content. Manifest facts, names, current source, the optional previous-version diff, and the reviewer's own notes quoted back to it are sent only as untrusted user content.
- **The host reads the artifact; the model only chooses where to look next.** `run_version_review` opens every reviewable file into `ReviewOpenFile` (UTF-8 bytes, line starts, and the byte ranges shown so far), then loops: draw a divider, call `plugins_ai_review.generate_step`, apply the notebook patch, run the chosen tool itself, and show the result on the next pass. Tools are `list_files`, `read_file(path, startLine, lineCount)`, `read_file_bytes(path, startByte, byteCount)`, `grep(literal, pathGlob)`, and `done`. `grep` is a literal substring search, never a caller-supplied regular expression; its path filter accepts only `**/`, `**`, and `*`, and anything resembling regex syntax is refused rather than guessed at. Pattern bytes (200), matches (50), and reported line length (400) are bounded before the search starts. A search result explicitly does not count as reading.
- `prepare_review_files` also returns `unreviewableFiles` — shipped files neither classification recognizes. They are listed in the inventory as `not reviewable text — not sent`, never sent as content, and never part of the coverage gate. The reviewer should be able to see that a 4 MB `.wasm` shipped even though it cannot read it.
- **Coverage is the gate, and it is the host's record, not the model's claim.** A read is recorded as the byte range that actually came back, widened to whole characters and cut below the 40,000-byte tool-result limit so the path and range header also fit. Every complete tool result is then capped by UTF-8 bytes. A path is complete only when the union of those ranges reaches the last byte; an empty file is complete from the start. The model gets eight moves to search or choose important files. After that, or when it answers `done` early, the host packs unread ranges from several files into one forced result. A random separator is checked against every printed path and source, then named as a trusted file-record boundary in the next system message. This preserves full coverage without requiring one provider call per small file: a 900,000-byte artifact needs about 26 forced batches plus a final `done` call. The bundle cap no longer bounds coverage. `REVIEW_MAX_STEPS` and the wall clock do, so the size a review can actually read is about 4 MB; an artifact between that and the 10,000,000-byte cap is accepted here and refused later at the coverage gate or the clock, after the publish has paid for model calls. After the loop, a gap, step exhaustion without `done`, or wall-clock exhaustion refuses the whole review; there is no sampling fallback and no terminal verdict is cached. The refusal names which budget ran out — steps, time, or a finish that landed just past the deadline — because a rejected publish keeps that message on `lastPublishAttempt` long after the log is gone. One shared abort signal carries the five-minute deadline through every model and token-count request, and the host checks the clock again after each await and before starting the verdict. Budgets: `REVIEW_MAX_EXPLORATION_STEPS` (8), `REVIEW_MAX_STEPS` (120 — coverage alone can take about 31 calls on a 900,000-byte artifact, and note-taking and repair turns between batches cost steps too; a 730 KB minified bundle exhausted the old 60 twice), `REVIEW_MAX_WALL_CLOCK_MS` (5 min, inside Convex's action ceiling), `REVIEW_MAX_NOTES` (120), `REVIEW_NOTE_MAX_CHARS` (600).
- **The notebook is append-only and source-bound.** The host assigns every id (`N1`, `N2`, …). A new observation cites nothing and is always a `hypothesis`; `confirmed`, `refuted`, and `superseded` must name an earlier note that existed before the current model step, and that note keeps its own status and only records which note answered it. Every accepted note names a real reviewable path and an exact covered UTF-8 byte range of at most 600 bytes. The host quotes that source range next to the model's explanation. A note also lists the exact typed capability-map subjects visible in that source. The host refuses any subject the manifest did not declare. When coverage is complete but a subject is missing, the host gives the reviewer three short repair turns while the latest source is still visible; the reviewer can also read the relevant source again. Answering the same note twice, naming an unknown id, citing an earlier note from a new hypothesis, using unread or invalid source bytes, and an over-long note are each refused and reported back to the model on the next step; none of them ends the review. Filling the notebook does end it as an operational failure. Nothing is evicted, merged, or summarized away.
- The diff reaches the model as the **first tool result**, headed `changed_lines since artifact <hash>`, truncated to the tool-result cap and framed like any other block, with a line saying a diff is a starting point and not a reading list. It orders navigation and never narrows required coverage.
- The line that separates one file record from the next is drawn per model call by `make_review_sentinel` and checked against the untrusted strings that reach that call: both artifacts' paths, content types and sources, the unreviewable files' paths and content types, the declared capabilities and both origin lists, the plugin name and version, the notebook text so far, the refusals quoted back from the model's last notes, and the tool result about to be shown. Anything new that reaches a prompt has to be added to that list by hand — the check is only as complete as the list, so treat this enumeration as the contract and keep it in step with `untrusted` in `run_version_review`. A collision draws again, and after four failures the review refuses instead of running with a divider the source contains. The system message names the drawn value, so the model knows which divider is the host's. Never store it or reuse it in a later call: a model reply can repeat it, and the next call's untrusted text would then be free to contain it. This makes the boundary unforgeable; it does not make the verdict unsteerable, because a file can still argue "vendored, skip" in plain prose.
- Sorted `{ path, contentType, source }` records are the deterministic input to both sides of the optional diff. They are **not** a model prompt: the reviewer sees an inventory plus whichever ranges the loop read. Two reviews of identical bytes can therefore navigate differently; the cache makes a repeated publish return the same terminal verdict. The bundle cap counts only the UTF-8 source bytes. It does not charge the manifest, JSON serialization, path headers, or diff dividers against a legal source artifact. The public publish path and internal review action both check the limit before the model, and the internal check returns an operational refusal without caching a content verdict. The OpenAI input-token endpoint counts the exact developer message, user message, and matching JSON schema before every navigation and verdict call. An input above 240,000 tokens is refused before the model call, and a count failure refuses the publish without a review doc. Counting every call matters because accepted notes can repeat long typed subjects and source ranges across the append-only notebook.
- After each successful navigation call, the host reads OpenAI's organization and project token-limit response headers. Before the next navigation call or the verdict, it compares both remaining-token windows with the larger of the exact input count and the request's output-token ceiling, plus a small margin. If either window is too low, it waits for the later reset with padding and jitter. The same five-minute abort signal bounds that wait. Each model call also keeps two SDK retries for temporary `429` errors caused by other traffic on the shared project. Do not replace this with whole-publish retries: failed calls still spend the per-minute budget, and restarting repeats the earlier review calls.
- Both model calls are `generateText` with `Output.object`, and each returns `result.output`. Reading `output` throws when the model wrote nothing the schema accepts, and also when it stopped before finishing. A step that throws and a verdict that throws both refuse to register the version, so the gate stays closed. Do not replace either read with anything that can return `undefined` instead of throwing: an undefined verdict would flow into `upsert_version_review` and the gate would fail open.
- Both calls use `openai.chat(REVIEW_MODEL_ID)`, the chat completions API. On the Responses API this model answers with several messages — a few the provider marks `commentary` and one marked `final_answer` — and the AI SDK joins the text of every message before parsing the structured output. Every message is schema-valid because the request carries a strict JSON schema, so the parser received `{...}{...}{...}` and every step failed with `NoObjectGeneratedError: could not parse the response` (found 2026-08-14, `@ai-sdk/openai` 3.0.96 / `ai` 6.0.253). Chat completions returns one message per answer and still sends `response_format: json_schema` with `strict: true`, `reasoning_effort`, and `max_completion_tokens`. Do not switch back to `openai(...)` without a way to read only the final message; `generateText` throws inside the call, so the parts are not reachable from `result`.
- Most action tests stub `generate_step` and `generate_verdict`, so they cover the loop instead of the provider contract. Focused tests restore the real wrappers and verify the retry options plus both token-rate header windows, but a reviewer change that alters the request shape still has to run against the real provider before it is believed. `run_version_review` is an `internalAction`, so `convex run internal.plugins.run_version_review '<args>'` with a hand-written one-file artifact exercises the whole loop in about thirty seconds; a failing review writes no review doc, and a passing one writes a doc that `hard_delete_plugin_from_registry` removes by its plugin name.
- **Nothing a passing artifact declares may go unexplained.** The stored `capabilityMap` carries `{ subject, path, evidence, startByte, endByte }`. Subjects are typed strings: `capability:<name>`, `backend_origin:<url>`, and `page_origin:<url>`. This keeps the backend and page roles separate even when both declare the same URL. The host builds this map from still-standing notebook notes, not from ranges invented by the final verdict call. Each stored entry therefore names a real file and a covered, character-aligned source range of at most 600 bytes that the navigation call saw. The final call repeats the map only as a review aid. A `passed` verdict missing any required subject is an **operational failure**, not a rejection. A `rejected` or `flagged` verdict stays terminal even when its map is incomplete; otherwise identical retries could sample until the model changed a negative verdict into a pass. No query returns the map yet, so today only an operator reading the review doc can see which file was held responsible for what.
- The verdict call sees the inventory, the coverage proof, and the notebook — **not** the source. To assert that a file's bytes reached the model, read the `generate_step` prompts (the `reviewer_saw()` helper in `plugins.test.ts`), not the `generate_verdict` prompt.
- The first terminal review result is cached globally by `(reviewSubjectHash, reviewPolicyVersion)`, including `passed`, `rejected`, and `flagged`. The subject is the validated manifest with the `version` field removed, serialized with every object's keys sorted (array order is kept, because file and page order is part of the manifest's meaning) and hashed. File hashes live inside the manifest, so one changed reviewed byte is a new subject. A release that bumps only the version number is the same subject and reuses the verdict without a provider call — that matters because `artifactHash` hashes the manifest text, which carries the version, so it would have paid twice. The model never receives configured publisher secret names. Those names are private repository metadata and cannot be copied into a globally shared cached review; the reviewer finds secret reads in the code instead. Every raw value returned by the host secret API still counts as a secret value even when its name is not shown. Every registered version stores the deciding `reviewId`, so version-only releases and another publisher's legitimate cache reuse both point to the same review. The registration mutation reloads every non-null review id and requires its plugin name, status, and policy to match before writing the version. Finalization checks the policy again before the preparing version becomes visible. The review action also passes its compiled policy to `upsert_version_review`, which refuses it when a deploy changed the current policy while that action was running. These checks close the account-deletion race and the cross-deploy race where an old verdict could look current. Before a fresh review insert, the same transaction rechecks that the publisher user is live and still owns the exact repository claim, so a model call that finishes after account deletion cannot recreate a drained review row. The publisher query returns reviews linked from its recent versions, its latest publish attempt, plus that publisher's recent unpublished attempts. It authorizes from one latest-version read first, then caps each history at 20 and projects reviews without the large capability map; the page says when older rows are not shown. Normalized manifest metadata and the stored findings/capability-map payload are each capped at 64 KiB, so those row-count windows are also safely byte-bounded. Before calling an own review “not published,” the query checks the global version index and omits it when any ready version outside the visible window already uses it. If a review creator is later deleted, an unreferenced review is deleted; a review still linked from a global version or another publisher's `lastPublishAttempt` is kept with `createdBy: null`. `artifactHash` is still stored, for release traceability only. Bump `plugins_REVIEW_POLICY_VERSION` (`shared/plugins.ts`) whenever prompts, mechanical severities, model or tool semantics, the classifier, or required coverage change; old verdicts then stop being reused instead of silently authorizing a publish under a policy that no longer exists. The optional diff baseline is the current `isLatest` version when it is ready and passed, so retrying an older failed release also moves the next review's baseline. Baseline R2 reads are bounded and verify stored size and SHA-256; a missing baseline omits the diff rather than blocking the complete current-artifact review.
- An artifact with no reviewable text auto-passes only when it also declares nothing. If it declares any capability or either kind of outbound origin, it is **rejected** instead, with the mechanical finding `The artifact declares [...] but ships no reviewable text that could use it`. Passing it would hand out `outbound.fetch` and its origins on an artifact no reviewer ever read. A page-bearing or file-view-bearing artifact never auto-passes for lacking a backend.
- Only a `passed` verdict registers a new version. A `rejected` or `flagged` verdict must carry at least one non-empty finding; otherwise it is an operational failure and is not cached. A valid negative verdict is cached but stops before upload and registration. `flagged` means the model found suspicious code that needs a human look, but this product has no manual approval door yet. The publisher must change the reviewed content and publish again, which creates a new review subject. `lastPublishAttempt.status` records `flagged`, not `succeeded`, and points at the review doc.
- `lastPublishAttempt` carries `pluginName`, `artifactHash`, and `reviewId` alongside status, message, and commit. The plugin name becomes known only after manifest validation and stays null for an earlier failure. A plugin details page shows the attempt and its review only when that name matches. The publisher repository page shows the latest non-success attempt under both unpublished and published repository cards, so a pre-manifest failure with no name still survives the toast. A later attempt for a different plugin name does not overwrite that stored non-success, including when the later attempt itself fails. A named attempt says `Last publish for <plugin>` because one repository may publish several names. `upsert_version_review` returns the stored doc id and `run_version_review` passes it up, so a completed policy attempt — including a rejection or flag — points at the immutable review that decided it. An exact ready republish copies the version's existing `reviewId` into the new successful attempt. The attempt mutation reloads a non-null review id in its own transaction and stores null if account deletion removed the review first. When an attempt replaces its old pointer, or any normal/admin/account-deletion path removes its repository, the same transaction deletes the old anonymized review only when no version or other attempt still links it. `pluginName`, `artifactHash`, and `reviewId` are `T | null`: an operational failure records only the facts already known. `publish_version` creates the small `attempt` object per call and stamps each fact only when it becomes known.
- Fresh model reviews use a per-user token bucket: 20 per hour with a burst capacity of 5. A cached subject does not consume this bucket. To re-run after an operational failure, publish the same commit again after the reported retry time or after fixing the named failure. The user-facing messages distinguish rate limit, safe-boundary, model-step, notebook, coverage/navigation, input-count, verdict, time, and capability-map failures. Logs keep the deeper provider details. Two concurrent publishes of the same fresh subject can still both spend review work before first-write-wins stores one verdict; the bucket bounds this cost, and it is not an authorization bypass.
- There is no review-policy generation or re-review migration path. This pre-production system deletes disposable plugin registry data and republishes current artifacts when the review implementation changes.
- The dev deployment completed the policy-6 registry reset on 2026-08-15. Gallery, Image, PDF, Video, Video Player, and the Data Probe fixture were republished under policy 6, and each is installed in `personal/home`. Publishing an exact ready artifact still returns that immutable stored version before review, so another prompt, tool, model, classifier, or coverage change must bump the policy and repeat the delete-and-republish flow.
- The invoke-door plan bumped `plugins_REVIEW_POLICY_VERSION` to `"8"`: the reviewer now judges a wider manifest surface (`backend.endpoints`, the `service` block, `userWritableCollections`, and the three new capabilities) and the runner's event path moved to `/__bonobo_senate/run`, so verdicts cached under earlier policies must not authorize a publish. Republishing the fixtures under policy 8 follows the same delete-and-republish flow; the Data Probe republish adds a backend endpoint so the invoke door has a live QA target.
- `raythurnvoid/bonobo-plugin-data-probe` is the fixture plugin for the plugin data store: a backend that writes one document per completed upload and a page that lists the same collection. It is the only published plugin declaring `plugin.data.read`/`plugin.data.write`. Use it to exercise a write-then-read round trip or an uninstall drain. Trigger it with a **stored blob** upload such as a PNG — a `.txt` upload is converted into an editable document, and `r2.ts` suppresses the plugin event on that path, so a text upload starts no run. Its page ships a hand-vendored pre-0.8.0 bridge (no build step, `fetchJson` reads only, never `client.data.*`), so it survived the data-bridge removal: the handshake and the `plugin_ui`-allowed `/api/v1/plugin-data/list` route are all it needs (verified live 2026-08-18 on 0.1.0). Upgrading it to the real SDK would require adding a bundler, because since 0.9.0 `frontend.js` imports `convex/browser`.

Repository claims intentionally remain normalized URL reservations without proof of repository control. This is an accepted provenance/name-reservation risk; do not describe the claim as verified ownership.

Publisher secrets remain bound to the immutable version creator. Runtime resolution and publisher-only management queries require the current repository claim owner to equal `plugins_versions.createdBy`; a different user who later claims the same URL cannot supply secrets or inherit the historical publisher panel.

The batch secret mutations (`upsert_publisher_repository_secrets`, `upsert_installation_secrets`) validate every name **and** value before the first write, and let an unexpected write failure throw. Both rules exist for the same reason: the batch writes run together in one transaction, and a Convex mutation that returns a value commits. Catching a write failure and returning `_nay` therefore kept whichever secrets had already been written while telling the caller the batch failed — observed in the browser before the fix, where a batch of one small and one oversized secret saved the small one and still reported an error. Do not reintroduce a `try`/`catch` around those writes, and keep any new per-item validation above the write loop rather than inside it.

# Plugin UI pages

- The current message contract is strict and has no compatibility version field. Before loading the frame, the host puts its canonical HTTP(S) origin and fresh `nonce` in the asset URL fragment. The nonce correlates one iframe generation; it is visible to the page and is not an authentication secret. Tokens and page context remain postMessage-only. The fragment key and message field are both named `nonce` since SDK 0.10.0 (renamed from `bridgeNonce`; no other nonce exists on the frame side, and the AES-GCM nonce beside encrypted plugin secrets never leaves Convex). Trust is layered: CSP `frame-ancestors` decides who may embed, the `event.source`/`event.origin` checks decide which window is talking, the nonce decides which mount a message belongs to, `parentOrigin` only gives the SDK a `postMessage` target so it never sends with `"*"`, and only the session mint produces authority. Do not describe the fragment values as authentication.
- The two hosts key the child frame differently, and the difference is load-bearing. The page route keys it by membership, plugin version, page, and Retry attempt (`$pluginName_.pages.$pageId.tsx`). The file-view host keys it by membership, plugin version, file view, **file node id**, and Retry attempt (`FileNodeViewPluginView` in `file-node-view.tsx`). Do not drop the node id when you copy one key into the other: one file view usually serves many files, so without it two files opened through the same view would share a single frame generation, and the second file would be shown by a frame still holding the first file's session and page context. The shared `PluginsUiFrame` owns the bridge. Its layout effect starts minting the session while the iframe assets load, but keeps the token in the host until the exact WindowProxy sends ready from the Convex asset origin with the current nonce. It attaches listeners before assigning the canonical `src`, captures the exact iframe node/generation in async work, requires the nonce for refresh, serializes refreshes, and revokes the host-only session id when the frame stops or navigates. A refresh whose action answers `_nay` "Unauthorized" means the session doc is gone for good (the device slept past the 30-minute TTL and the expiry job deleted it, or membership ended): the host then mints a new session for the SAME frame through the owner's `mintSession` and answers that same refresh with `bonobo:token`, so the page keeps its document, its state, its draft, and its live subscriptions — the iframe `src` and nonce do not change, and the SDK treats the token like any rotation. The gone id is marked revoked without a mutation; the new id is what unmount revokes, also when the re-mint resolves after unmount or after a second load. A refused re-mint (`Not found` after an uninstall, `Unauthorized` after a membership end, `Permission denied`, a rate limit) or a re-mint bound to another `pluginVersionId` stops the frame through `onError`, so the owner shows the mint message with Retry. The re-mint is capped at one per session: a re-minted session that is gone again before it ever refreshed stops the frame with "The plugin page session was lost" instead of minting in a loop, and a successful refresh clears the cap. Every other refresh failure still answers token-error for the SDK's own retry, and the host-initiated kills (ready flood, second load) set their cancel flag first, so a page the host revoked on purpose never mints itself a new session. A second ready after init means the page reloaded or was replaced, so the host revokes the session — with the page running its own ConvexClient, that revocation is the host's only lever over the page's live subscriptions (every door re-reads the session doc, and a deleted doc turns those queries into null). A ready flood kills the frame outright.
- The frame uses `sandbox="allow-scripts allow-same-origin allow-forms"`. `allow-forms` only lets the submit event fire so plugin code handles forms in JS (`onSubmit` + `preventDefault`); the asset CSP keeps `form-action 'none'`, so a real HTTP form submission is refused even when a plugin forgets `preventDefault`. The frame also sets `allow="clipboard-write"`. That feature is Permissions-Policy gated and is not delegated to a cross-origin frame by default, so without the grant `navigator.clipboard.writeText` rejects with `NotAllowedError` inside every plugin frame. Both hosts render the same `PluginsUiFrame` component, so the `sandbox` and `allow` values here are the file view's too. Some plugin values are shown once and cannot be read again (the Council join code), so a failed copy loses them for good. There is no `Permissions-Policy` response header anywhere in `packages/app`, so the iframe attribute is the whole story. Treat this as a reviewed host capability, not a manifest capability: it reaches every plugin, and no consent line mentions it. Keep the `allow` list at this one feature — delegating another one grants it to every plugin at once and must be reviewed and recorded here the same way. The plugin asset route and public API share the Convex origin, so normal JSON requests with `Authorization` stay same-origin and skip CORS preflight. The host app has a different origin, so the frame cannot access its DOM or cookies. Plugin frames share the asset origin; do not store secrets there or treat origin storage as a plugin-to-plugin boundary. The app mounts only one plugin frame at a time — the page route and the file-view tabs are distinct route leaves, and hidden file-view panels unmount their frames. The SDK's subscription caps below are per frame — one SDK client per mounted frame, page or file view — so a layout change that mounts two plugin frames at once would double the total server-subscription load; the server itself does not cap live subscriptions per session (accepted fan-out risk — see the docblock above the user-read queries in `plugins_data.ts`).
- The SDK validates one canonical HTTP(S) `parentOrigin` and one UUIDv4 nonce from the fragment before connecting. It installs its listener before sending nonce-bound ready to that exact origin, accepts host messages only from that origin, `window.parent`, and the matching nonce, repeats ready every 500ms until init or page unload, and rejects an unanswered refresh after 10 seconds. The host posts only to the concrete Convex asset origin. The host alone owns the 15-second startup deadline and Retry UI. `fetchJson` retains exactly one 401 retry; a late 401 reuses a token that another request already rotated instead of rotating it again. Since SDK 0.9.0 the init message also carries `convexUrl`, and the SDK opens the page's own `ConvexClient` there (`expectAuth`, no unsaved-changes handler), authenticated by the plugin-session JWT the host delivers beside the token in `bonobo:init` and every `bonobo:token` (`jwt`, `jwtExpiresAt`; since SDK 0.11.0). The client pins `initialAuthTokenReuse: true`, so it schedules its own refetch from that JWT's expiry instead of forcing a second fetch right after the first one is confirmed; that refetch lands 10 seconds before expiry, inside the SDK's 60-second margin, so one host refresh answers it with both credentials. Only a host that sent no JWT makes the SDK exchange the token at `POST /plugins-ui/session-jwt`. The SDK registers a one-second wake poll before the first `setAuth`; a wall-clock gap of at least 30 seconds calls `setAuth` again, which pauses Convex before the dead session's old query set can reconnect and deliver a permanent null while the host re-mints. The poll and client both stop on `pagehide`, and a bfcache-restored page stays frozen until a real reload. The auth callback retries a transient host refresh or fallback exchange failure (thrown fetch, 429, 5xx) after one and two seconds; if networking is not back quickly enough after wake, those three attempts can still answer null and kill the page.
- Sessions (`plugins_ui_sessions`) are minted per (user, installation), hashed, and have a 30-minute TTL. Refresh updates one session doc in place; the old token hash stops resolving. The mint and refresh entrypoints are actions (`mint_page_session`, `mint_file_view_session`, `refresh_ui_session`) over internal mutations (`insert_page_session`, `insert_file_view_session`, `rotate_ui_session`): the mutation writes the session doc, then the action signs the plugin-session JWT for it, because ES256 signing needs cryptographic randomness and Convex allows that only in actions (a mutation was refused on dev on 2026-09-02). Each answer carries `token`, `expiresAt`, `jwt`, and `jwtExpiresAt`, and `jwtExpiresAt` always equals `expiresAt`: both credentials live exactly as long as the session doc. When that doc is already gone, the host frame mints a new session for the same iframe instead of remounting it (see the bridge bullet above). Both mints schedule an `expire_ui_session` job at the session's expiry and refresh reschedules it, so an idle expired session is deleted server-side without waiting for the daily cleanup. Removing a member from an organization deletes that user's sessions in every removed workspace, so a later invite cannot revive them. Public API rate accounting uses a stable organization/workspace/user/installation principal key, while the route remains a separate bucket dimension.
- `POST /plugins-ui/session-jwt` (plain router, no CORS) is the fallback for a frame whose host delivered no JWT: it trades a live session token for the same plugin-session JWT the mint delivers — ES256 with the anonymous provider's key and kid, issuer `${VITE_CONVEX_HTTP_URL}/plugins-ui`, subject = the session id, `exp` = the session expiry. One module-private signer, `sign_session_jwt` in `plugins_ui.ts`, serves the two mints, the refresh, and this route. The Origin guard accepts only the frame's own asset origin or an absent header (server-to-server); `"null"` and every other origin answer 403. The exchange never extends the session, and a per-session token bucket (12/min, capacity 6) bounds it. Convex verifies the JWT through the third `customJwt` provider in `auth.config.ts`; only the plugin doors resolve that identity (`server_convex_get_plugin_session`), and every member-facing function refuses it — see `../auth-system/SKILL.md`.
- Development-only exchange exception: when the deployment sets `PLUGINS_UI_DEV_EXCHANGE_ORIGIN` to one bare origin, that exact origin is also accepted by the guard, its responses gain CORS headers echoing only that origin (plus an OPTIONS preflight answer for it), and a frame on an SDK older than 0.11.0 under the app's dev frame override (`VITE_PLUGIN_UI_DEV_*`, see `packages/app/.env`) can complete the exchange from a local server. A frame on SDK 0.11.0 or later gets its JWT from the bridge and needs no exchange, so the override works without this variable. Exact string match on the serialized origin — no wildcard, no list, no prefix. Production deployments never set the variable, so their guard and refusal surface are exactly the pre-exception ones; this invariant is pinned in the "refuses ... while the dev exchange variable is unset" tests in `plugins_ui.test.ts`.
- `/api/v1/files/download-urls` is the only download URL route. Every caller sends `fileNodeIds`, including one-item requests. Backend runs may send only their triggering upload id and still sign the original source asset. The route resolves the exact presented bearer again after file materialization and immediately before signing. The signer TTL keeps a one-second margin inside the remaining plugin authority, and the route repeats the same scope, `content.read`, tenant, credential/session/run, and installation/version checks after signing before returning any URL. Reported `expiresAt` is the same conservative boundary. Requests are limited to 100 ids and 32 KB before authentication, reject duplicates before authorization or file work, then process at most the first 20 ids in request order and report truncation and per-id errors.
- Expired sessions drain through `cleanup_expired_ui_sessions`. Uninstall/workspace/user/admin deletion remains bounded — see `../data-deletion/SKILL.md`.
- Canonical assets use the single direct route `/plugins-ui/<versionId>/<path>`. Published plugin versions are immutable, so asset or response-policy changes require a new plugin version and republish; there is no compatibility redirect or asset-policy path generation.
- Canonical asset responses retain CSP, `nosniff`, immutable cache, and CORP. Their CSP uses `'self'` for scripts, styles, fonts, and same-origin module/style fetches. `connect-src` is `'self'`, the Convex cloud `https` and `wss` origins the page's own `ConvexClient` needs, and then the served version's `uiOutboundOrigins` — see "UI outbound origins" above. R2 failures return 502 with `Cache-Control: no-store` + `Retry-After: 3`. Never log raw R2 errors or keys.
- The host startup deadline is 15 seconds and clears once `bonobo:init` posts. Failure replaces the iframe with a `role="alert"` and focused Retry button; Retry creates a fresh frame, nonce, and session. The immutable asset path stays canonical, and the query stays empty. Only the fragment carries `parentOrigin` and `nonce`, so neither value is sent in the asset request, cache key, or referrer.
- A page that already received its read-only token can self-navigate before the host observes the next load. The host disables the bridge and revokes on that load, while per-call liveness and TTL remain the backstop; do not claim already-authorized in-flight work can be recalled.

# Plugin file views

A manifest may declare `fileViews` — frames the host offers as tabs next to the stored-file details card when a member opens a matching file. They reuse the page machinery: same sandboxed iframe, same asset route, same `plugins_ui_sessions` table, same bridge protocol through the shared `PluginsUiFrame` component (`packages/app/src/components/plugins-ui-frame.tsx`).

- `bonobo:init` `context` is a union on `kind` since SDK 0.6.0: `"page"` keeps the page fields; `"file_view"` carries `fileViewId`, `fileViewTitle`, and a `file` object (`fileNodeId`, `name`, `path`, `contentType`). Since SDK 0.7.0 both kinds also carry `userId`, the acting member the host is signed in as, so a page can mark the member's own documents. Hosts always send `kind`; the SDK validator requires both.
- `list_file_views` (`plugins_ui.ts`) lists enabled installations whose ready+passed version declares file views, with `installationCreatedAt` for stable ordering. `plugins_list_file_view_matches` (`packages/app/shared/plugins.ts`) lists every view whose `contentTypes` include the node's exact stored content type, ordered by installation creation time. Since the editable-text feature, uploads with a recognized text extension store the classifier's media type (for example `application/json`), so file-view `contentTypes` can now match plain-text stored files too.
- The tabs live in `FileNodeViewStoredFile` (`file-node-view.tsx`): with no matching view (or while the upload pipeline runs) the plain details card renders with no tabs. With matches, a tab bar renders "File details" first (the default tab) and one tab per matching view in installation order. Hidden view panels use `unmountOnHide` so switching tabs tears the frame down and revokes its session. The selected tab is reset by keying the component on the node id. The selection is controlled: if the selected view disappears from the live match list (plugin uninstalled or its update dropped the view), the UI falls back to the details tab. `selectOnMove` is off, so arrow keys only move focus and Enter/Space selects — selecting a plugin tab mints a session, and key-repeat must not burn the mint rate bucket.
- `mint_file_view_session` re-checks, in order: user auth, membership, its own rate bucket, node existence, live `content.read` on that node (`access_control_db_authorize_membership` with the file node — restricted nodes answer only from scope-node grants), enabled installation, ready+passed version, declared view id, and content-type match. The session stores `fileNodeId`; `refresh_ui_session` re-loads the node and re-checks `content.read` on it, so a restriction applied mid-session stops the next refresh.
- Only the **mint** is split. File-view mints use their own `plugins_ui_file_view_session_mint` bucket (token bucket, 30/min, capacity 8), because a file view mints on every file switch and every details/view toggle, and browsing a few files in quick succession must not read as broken. Page mints stay on the stricter `plugins_ui_session_mint` bucket (12/min, capacity 2). Rotation is not split: `refresh_ui_session` charges `plugins_ui_session_mint` for both frame kinds — a plugin page and a file view — and it charges above the `session.fileNodeId` branch, so the frame kind cannot pick the bucket. That costs a file view nothing in practice, because browsing mints instead of refreshing: a new file or a tab switch tears the frame down and mints again, and a dead session never refreshes. A frame that stays open rotates rarely — shortly before the 30-minute expiry, and again after a `401`. A frame that slept past the expiry mints again instead of rotating: one page-mint charge, the same as the remount it replaces.
- Signed download URLs pin response headers at signing time: `public_api.ts` derives them from the file NAME through `files_get_signed_download_serving` (never from the stored content type, which is client input at upload time) and passes `responseContentType` plus an RFC 5987 `responseContentDisposition` into the signed `GetObjectCommand` (vendored `r2` change). Only the literal media map serves `inline`; everything else — editable text, `svg`, `html`, unknown — downloads as an attachment. Response-header overrides must be part of the signed command — appending `response-content-*` query params to an already-signed URL breaks the SigV4 signature.

# Plugin document store

A plugin keeps its structured data in `plugins_data` instead of adding tables to the core app schema, the same way installation configuration keeps plugin settings out of it. One document is one installation, one collection inside it, and one key inside that collection. The store lives in `packages/app/convex/plugins_data.ts`; the nine `/api/v1/plugin-data/*` routes that reach it are in `plugins_data_http.ts` and are documented in `../public-api/SKILL.md`. `list` takes an optional `keyStartExclusive`/`keyEndInclusive` key range beside `keyPrefix`, which is how a frame reads history older than a live window can hold. A cursor may be sent beside a range: the route binds each cursor to the exact range it was issued for and refuses one replayed with a different range, so the continuation rule is in `../public-api/SKILL.md`.

Consent gates it in both directions. `plugin.data.read` is required to read and `plugin.data.write` to write, and every call rechecks the accepted capabilities inside its own transaction, so an upgrade to a version that stops declaring one revokes access immediately — `install_version` is the only writer of `acceptedCapabilities`, and it always writes the installed version's own set. The same recheck also reads `installation.status`. Registry hard delete writes `disabled` before its first drain, so every store door closes while cleanup continues. A version that declares `plugin.data.write` must also declare `plugin.data.read`: a plugin that can only write would store documents it can never read back.

Read "page" in this section as "page or file view": `db_authorize_page_read` and `db_authorize_page_write` load the session doc by id and never read its `fileNodeId`, so a file view reaches these doors exactly as a page does. A plugin page reads and never writes. Three separate things enforce that: the write routes leave `plugin_ui` out of their allowlists, a page token never carries the write scope, and `refuse_page_principal` refuses the kind inside the mutation itself. Only the third one survives a caller that reaches the mutation directly or one wrong edit to an allowlist. A page session can belong to an anonymous identity, and a page is the first thing a scripting bug in a plugin reaches, so a write door there would turn one such bug into stored data that plugin backends later act on with their own secrets.

**Every document outside a private scope is visible to every member of the workspace.** A page read is authorised workspace-wide, so `ownership: "owned"` decides who may _write_ a document and nothing about who may _read_ it. A plugin that keeps per-member state in the public half of a collection — read cursors, drafts, per-person settings — keeps it where any member of that workspace can read it through the plugin's own frame. Do not put anything there that one member must be able to hide from another. **Private scopes are the door for that**, and they are the only one.

## Private scopes

A scope makes part of the store private: a private channel, a direct message, or anything else only some members may read. One scope covers one key prefix across the collections it names, with one `plugins_data_scopes` row per collection, all sharing the scope id. `plugins_data.user_manage_scope` owns the whole lifecycle — create, atomic create with its first document, add or change a principal, remove one, delete — `watch_scope_principals` reads the active workspace members in it, and `watch_my_scopes` lists the scopes this member is in.

- **The binding lives on the server, and no caller ever supplies a scope id on a write.** Every write door resolves the key's scope itself, by reading scope prefixes downwards from the key and testing the first one, so a new write path cannot quietly put a public document inside a private range. Live scopes and released fences may not overlap, which is what makes that one indexed read enough.
- **A scope's key range must be unused when it is created.** A document written before the scope existed would carry no scope id and would stay readable by the whole workspace inside a range that now calls itself private. A live service reservation also owns its promised key, and a revision tombstone owns its key through the retry horizon, so creation checks the full prefix range in all three tables. Those indexed reads also make a concurrent reservation and scope create conflict and retry.
- **Scope ids and released key ranges are never reused during one installation lifetime.** Creation writes one durable identity marker whose collection and prefix are both empty. Deletion keeps that marker and writes one real `plugins_data_released_scope_ranges` fence per collection before it removes the live rows and grants, even when the scope stored no document. Scope creation refuses parent and child overlap with those real fences. Every write door checks both live scopes and released ranges. A stale frame therefore cannot turn old private data public or add a new public document under the released prefix. A broad prefix can reserve a broad namespace for the rest of that installation; this is the safe result under the current arbitrary-prefix API. Installation and workspace drains remove markers and fences only after the stored documents are gone.
- **Name every collection in the one create call.** A private channel keeps its name, its messages, its replies and its reactions in four collections, all under the channel key. Creating the scope one collection at a time leaves the others readable in between, and it would cost the member one scope against their cap per collection instead of one per channel.
- **Use `createWithDocument` when the first document makes the private area visible.** It creates every scope row, the creator's `manage` grants, all invited user grants, and one shared document in one `user_manage_scope` transaction. A new setup charges the page-write bucket once, not once per invite. An exact retry returns the stored success without a second charge. Before any row is written, the server checks the full document/reservation/tombstone range, the first document, every active workspace member, both scope caps, and document capacity. A refusal leaves no scope, grant, document, or usage behind. The creator is implicit and must not appear in `principals`; the document's collection must be named by the scope and its key must start with the new prefix. An exact retry returns success only while the stored scope, principal set, and first document still match the original request. If a principal left or any setup differs, the retry returns `conflict` and does not restore them.
- **Every read door excludes a scope the caller has not proved**: `watch_documents`, `watch_recent`, `watch_changes`, `read_document`, `list_documents`, and the `/api/v1/plugin-data/list` route over them. A read with no key range returns only unscoped documents — an equality on `scopeId` of `undefined`, which is an ordinary indexed equality and not a scan. A scoped read that the caller may not see answers absent (`null`, or an empty page), never denied, so the refusal itself says nothing about what is there.
- **Lifecycle changes hide unreadable scope ids and ranges too.** A non-create change answers `Not found` for an unreadable live scope, a released scope, and an id that never existed. An exact create retry returns success only after the caller proves current read access to that scope. An unreadable live id and a released id both return the same `conflict` answer before the host compares the private range, principals, or first document. A new scope that overlaps either an unreadable live range or a released range gets the same `This key range is unavailable` answer. A caller who can read the overlapping live scope may get the more useful live-overlap message. The SDK passes these backend results through unchanged. A caught transport or runtime failure instead resolves `{ _nay: { name: "unavailable", message: "Failed to change who can read this" } }`, so the page knows the outcome is uncertain. The raw principal query still returns `principals | null`; the SDK validates it and wraps an exact answer as `{ _yay: principals | null }`. A thrown or malformed read instead resolves `{ _nay: { name: "unavailable", message: "Failed to read who can access this" } }`, so exact unreadable or absent state is never confused with a broken query.
- **Membership revisions order lifecycle races.** The required `plugins_data_scopes.updatedAt` is also the scope's membership revision. Creation starts it. Every successful member or level change sets every live row of that scope to a value strictly greater than its old value, even when `Date.now()` did not move. Scheduled cleanup after a departing user's direct grant advances each surviving scope once. The audit migration advances a scope only when it repairs a missing manager, so checking a healthy scope does not change its revision. An exact create replay returns the stored value without changing it. Every successful lifecycle result includes `membershipRevision`, including a deletion result after the rows are gone. `watch_my_scopes` returns the maximum row value as the same field. A page must compare these values when a successful Leave reply races a later re-add: an absent scope proves the Leave, a present scope with a greater revision proves the re-add, and a present scope at the same or an older revision is still a stale watch value.
- **Scoped append activity is durable and separate from membership.** Each live collection row keeps `lastAppend: { at, key, createdByUserId } | null` plus an `appendSequence`. Only a new accepted `user_append_document` inside that live scope updates them, in the same transaction as the document. The sequence increases for every such append, even when its same-millisecond key is below the prior marker. The append key's server timestamp is `at`; later time wins, and a lexically greater key wins an equal-time tie. Replays, refusals, and every put or remove door leave both values alone. `watch_my_scopes` returns sorted `{ collection, at, createdByUserId, sequence }` rows in `appendActivity`, without the key. This patch never changes the scope row's `updatedAt`, so `membershipRevision` still means membership only.
- **A member finds their own scopes through `watch_my_scopes`, and nothing else can.** The plugin mints the scope id, and from then on it lives only inside the key range it hides, so the rangeless read above cannot reach it. Without this door a member creates a private channel and it disappears from their own list. The frame reads this first, then opens one ranged read per scope beside its public one. Listing follows the grant, not the workspace: the organization owner may _read_ every scope, but only the scopes they were added to are _listed_, so an owner who is in nothing gets an empty list. It is a live query, because being added to a private range has to show up without a reload.
- **Grants only, never roles.** A `plugin_scope` permission check is answered by the grant alone; a workspace role, however senior, gives nothing inside a scope. See `../access-control/SKILL.md`.
- **The organization owner reads every scope**, before any grant is consulted, and no revocation reaches that. A plugin whose UI says "private" must say this too, or the feature is a disclosure rather than a bug.
- **Caps: 50 people per scope, 50 scopes per member, and 1,000 scope ids per installation lifetime.** These caps keep scope management, each member's share, and durable lifecycle state bounded. One id has one marker plus at most 16 real collection fences, so one installation can keep at most 17,000 lifecycle rows. Create number 1,001 returns `storage_full`. Uninstalling and reinstalling starts a new installation and resets this lifetime cap. The last active principal's leave deletes the live scope but keeps its id and range reserved. A page that creates scopes must therefore give members a Leave action; managers may also offer Delete.
- **Roll out scoped append activity in gated phases.** First deploy the compatible schema and runtime while `lastAppend` and `appendSequence` stay optional. Then, with explicit approval, run `migrations:run_backfill_plugin_scope_append_activity`; it preserves append history and makes its sequence at least 1 before it writes null/0 defaults. Walk both paged append-activity audits until they report zero candidates. Only after that proof may sequence-based Chitchat deploy. Tighten both fields to required only in a later schema push. Do not run the migration, skip the audits, deploy the sequence consumer early, or tighten the schema as part of the compatibility push.
- **The lifetime cap counts on identity markers that a one-time backfill wrote.** Scope ids that predate released-range fences were marked by `run_backfill_plugin_scope_identity_markers` in 2026-08: it recovered orphan Chitchat documents as identity markers plus per-collection fences, then marked live and released-only ids. The backfill ran to completion on this deployment, its audits reported zero candidates, and the runner and its migrations were then deleted. Since then, scope creation writes the identity marker itself, so no new unmarked id can exist.
- **Bind destructive dialogs without exposing the member count.** Leave, remove, and delete may send `expectedPrincipalCount` from the dialog they showed. `watch_scope_principals` omits inactive or deleted members whose grants are waiting for cleanup, and the mutation compares that same active-principal set. The server first proves direct self-membership for Leave or `manage` authority for the other actions, then compares the count before any write. Checking the count first would let an unrelated workspace member probe how many people are in a private scope.

## Member writes through the page (user-write door)

Member-initiated writes bypass none of that: the page never writes with its own UI token. Since SDK 0.9.0 the page's own ConvexClient calls the `user_*` public mutations in `plugins_data.ts` directly, authenticated by the plugin-session JWT the host delivered with the session (an older SDK exchanges its `plu_` token for the same JWT). That JWT identifies a person with less authority: only the plugin doors resolve it, so a page identity can never reach the rest of the app's API, and the bearer-token ban above stays intact.

- The manifest may scope the door with `userWritableCollections`. An absent field means every collection stays user-writable (the Data Probe's behavior); when present, a member-identity write (a frame write or a `user_api_key` write) to a collection NOT in the list is refused with `This collection is not user-writable`. The plugin's machine writers (`plugin_run`, `plugin_service`) are never restricted by the list — it exists exactly so a backend can own some collections alone: Chitchat 0.6.0 declares `["channels", "cursors"]`, making messages, replies, and reactions backend-only. Known gap, accepted on purpose: `channels` stays user-writable because private-channel creation writes the channel document from the page through `scopes.createWithDocument`, so a member can also write public channel docs directly through the door — the backend's channel-manage endpoint is the normal path, not an enforced one. Reads, private scopes, ownership, and CAS are untouched. Declared names must be valid collection names, at most 16, and the field requires `plugin.data.user-write`.
- The doors take no scope args: `db_authorize_page_write` / `db_authorize_page_read` derive everything from the session doc the JWT's subject names, mirroring `resolve_principal`'s liveness chain. Every call rechecks in its own transaction: session existence and expiry (the session doc is the kill switch — revoke, expiry, uninstall, upgrade, and account deletion all end access on the next call, whatever the JWT's remaining lifetime), enabled same-version same-tenant installation, live user and active membership, workspace `content.write`, the both-sides `plugin.data.user-write` capability gate, and the `plugins_data_page_user_write` token bucket (30/min, capacity 10, keyed `user:installation` so one busy plugin cannot drain the member's budget in every other installed plugin).
- Five operations. `user_append_document` stores at `<keyPrefix><inverted 13-digit ms>:<4 random>` so ascending key order is newest-first and chronology is server-stamped; the doc is `owned`. Replaying the same `clientRequestId` (scoped per creator by the `by_installation_collection_createdBy_requestId` index) answers the exact first append result when the request fingerprint matches and refuses `conflict` when it differs. Later edits do not change that answer. A physical delete moves the first answer into `plugins_data_append_replay_receipts` for 24 hours, so a lost-response retry cannot recreate content another page deleted. `user_put_document`/`user_remove_document` take a caller key: the target decides — a `shared` doc takes any member's write, an `owned` doc only its creator's. `user_put_owned_document`/`user_remove_owned_document` append `:<actorUserId>` to the caller key server-side, so identity in keys can never be forged (per-user toggles: reactions, votes, RSVPs).
- `ownership` is enforced in the storage layer, not just the door: every interactive writer (`user_api_key`, `plugin_run`, `plugin_service`) is refused on an `owned` doc whose `createdBy` is not the acting user, with `This document belongs to another writer`. The field is required; the service and API writers stamp `shared` on the docs they create. A replayed append answers its stored key before the rate bucket is charged, so a retry of a delivered write never reports as failed.
- Compare-and-set: `user_put_document`, `user_remove_document`, `user_put_owned_document`, and `user_remove_owned_document` take an optional `expectedRevision` through the shared guard `refuse_revision_mismatch`. Absent means optimistic; `0` means "no document exists" (the first stored revision is 1), so a put with `expectedRevision: 0` is create-only. One narrow recovery applies to `putOwned`: a create-only call replaces a normal shared document squatting the server-composed key with a fresh owned document at revision 1. A versioned producer document or another member's owned document still refuses. A mismatch refuses `{ name: "conflict", message: "This document changed since it was read" }` and deliberately carries no current revision — the door never proved the caller may read, so the fresh revision must come from a read surface. Removing an absent doc with `0` or no expectation keeps the idempotent `deleted: false`; expecting a live revision of a gone doc is a conflict. Delete-then-recreate restarts at revision 1, so a revision orders writes within one document lifetime, not across them (accepted ABA). Ownership is checked before the revision, except for that shared-squat recovery, so a conflict answer never reveals whether another writer's owned doc changed underneath. `user_append_document` has no `expectedRevision` — its args validator rejects the field, because an append never targets an existing revision. Conflict probing costs the same 30/min user-write bucket every door call pays.
- Read side for pages: `watch_documents` (public query; session-derived auth INSIDE the query — reading the session, installation, and membership docs there is what re-runs every live subscription to null on revocation; ascending key order, `limit` <= 100, optional `keyPrefix` plus optional `keyStartExclusive`/`keyEndInclusive` interval bounds whose intersection may be empty; reads one past the limit so the answer is `{ docs, truncated }`; malformed input answers the same bare null a denial gets; never reads the usage doc), `watch_recent` (the same query shell in creation-time order instead of key order, for a cross-key feed: one collection, `limit` <= 100, `order: "asc" | "desc"` defaulting to ascending, and each direction owns its fencepost — `since` belongs to `asc` (catch-up after a cut) and `before` to `desc` (paging a feed backwards), both strict bounds compared on `createdAt`, and naming the fencepost of the other direction is malformed input, so it answers the same bare null a denial gets; an optional `scopeId` narrows the feed to one private scope the caller has proved, otherwise only unscoped documents; tombstoned values still arrive like any watch, and the answer is the same `{ docs, truncated }` shape), `watch_changes` (the same query shell in **update** order, for an invalidation feed: one collection, `limit` <= 100, inclusive `updatedSince` on `updatedAt` (gte: a change whose `updatedAt` equals the cursor must still be delivered), optional `scopeId` with the same proved-or-unscoped rule; an edit and a soft-delete both patch the row and bump `updatedAt`, so both surface here, and that is why `watch_recent` must not use this index — a typo-fix would jump to the top of a new-messages catch-up read; a physical delete leaves the table and cannot appear; never read the usage doc), `resolve_member_display` (workspace-member display names; non-members and deleted users resolve null) and `list_members` (the roster, see below). Public documents expose `createdBy`, `updatedBy`, `ownership`, `createdAt`, `revision`, `byteSize`, and `writeMode`.
- The window manager lives in the SDK since 0.9.0 (`create_documents_window` in `bonobo-plugin-sdk/frontend.js`, behind a `start_watch` seam over the page's ConvexClient). `data.watchWindow` (`collection`, `keyPrefix?`, `pageSize`) keeps a history-RETAINING ordered list of key intervals, each backed by its own `watch_documents` subscription whose fenceposts are keys the server already delivered — sliced positionally, never compared with JS `<`, because keys are not guaranteed ASCII. The newest interval stays unbounded so arrivals land live; a truncated unbounded tail re-seats onto the closed range its docs already cover (content-neutral, no delivery lost); `loadOlder` appends a new unbounded tail starting at the stored bound; a truncated bounded interval splits around a delivered fencepost; adjacent intervals that shrink below one page merge to reclaim a subscription. One flush per microtask, delivered only when the whole JSON payload changed. Window updates add `hasMore` (an undelivered or non-terminal tail), `atCapacity` (interval ceiling reached), and `incomplete` (a truncated bounded interval no split can repair — docs are missing in the middle, and the page must say so instead of rendering a silently shorter history). The ConvexClient delivers cached results asynchronously (its own `setTimeout(0)`), so a window born from a sibling's cached result still registers before its first delivery; the flush calls the page's `onUpdate` directly, so a chitchat-style catch-up loop may call `loadOlder` re-entrantly from inside a delivery and must work (pinned by an SDK test).
- Resource model, all SDK-side per page: 16 subscription slots shared by plain watches (`watch`, `watchRecent`, `watchChanges`) and windows (a window is one slot; the cap was 8 until SDK 0.9.4 — see its sixth ride-along bullet for why it moved), at most 6 intervals per window (600 docs at the 100 page-size ceiling), and 100 server subscriptions across the whole page — one per plain watch and one per window interval, committed and pending alike. That 100 is a backstop for a buggy or hostile page, not a budget honest plugins design against. Slots and intervals are what shape a page: 16 × 6 = 96 stays under 100. The three caps are checked independently; honest pages hit the 16-slot or 6-interval cap first. A window whose own interval budget is gone reports `atCapacity` and refuses `loadOlder`. The start-token budget was retired together with the data bridge. Since 0.9.4 a death names one of **five** reasons, and a page shows something different for each: `invalid` (SDK-side validation, a strict SUBSET of the server rules — lengths, printable-ASCII prefix, integer limit — so a browser's newer Unicode tables can never refuse names the server still serves; input outside the subset still dies server-side), `capacity` (the slot cap, delivered asynchronously so the caller already holds its unsubscribe handle), `denied` (the store answered null: uninstalled, revoked, or the data is gone), `session_expired`, and `unavailable`. The last two come from the _same_ opaque Convex `queryError` and are split by the SDK's own `tokenExpiresAt`, because the server cannot say which one it was. Only `unavailable` logs — a lapsed session is the ordinary end of a frame's life, not a fault. A death with no info at all now means only that the SDK could not start the subscription, and the caller already sees that failure at the call site. Every death is delivered once and drops the registration, so a later unsubscribe is a no-op.
- Writes and member resolution run on the same client: the five `data.*` writes call the `user_*` mutations and always resolve (a caught transport or runtime failure resolves `{ _nay: { name: "unavailable", message: "Failed to write plugin data" } }`); `members.resolve` calls `resolve_member_display` and resolves `{}` on denial or failure; `members.list` calls `list_members` and resolves `{ _yay: { members, cursor } }` or `{ _nay: { name, message } }`, never an empty roster for a refusal.
- The host's theme reaches the frame over the bridge, because a plugin frame is a separate document and inherits none of the app's custom properties. `bonobo:init` carries an optional `theme`, and a nonce-checked `bonobo:theme` message follows every later switch. The init theme is the one read when the session was minted, and the host reads it again when the frame says ready, so a switch made while the frame was still loading is sent right after init instead of being dropped (the sender skips it when nothing changed). The payload is `{ mode: "light" | "dark", tokens }` where `tokens` holds the app's nine numbered colour scales under their real custom property names, `--` prefix included (`--color-base-1-01` … ; `base-1`, `base-2`, `base-alt-1`, `base-alt-2`, `fg`, `green`, `red` with 12 steps, `accent` and `accent-alt` with 10; 104 entries, since SDK 0.10.0). Nothing else is sent: the shadcn tokens are placeholders on their way out, and there is no second vocabulary of role names. The host keeps the list static in `PLUGIN_THEME_SCALES` (`plugins-ui-frame.tsx`) because computed styles cannot be enumerated, and the page route test parses `app.css` and fails when the list drifts from the declared scales. `mode` is read from the lightness of `--color-base-1-01`, not from the root class, because the palette does not swap yet. **The SDK applies the theme to the frame document itself**: on init and on every `bonobo:theme` it writes each token onto `document.documentElement.style` and toggles the app's own `light` / `dark` root class, so a plugin stylesheet uses `var(--color-base-1-03)` and `.dark &` exactly as the app does with no plugin code in between. `client.theme.current()` (`null` when the host sent none) and `client.theme.subscribe(cb)` remain for what CSS cannot do; `subscribe` fires after the SDK has painted and never replays the current theme. A malformed message is dropped whole rather than partly applied, so a page never paints one wrong colour.

The three caps above are **client-side**: they are closure counters inside one SDK client, so they bound one well-behaved frame and nothing else. Frame code that reaches its own ConvexClient directly (`client.convex` with a reference from `client.api`, a supported path since SDK 0.12.0) can open as many subscriptions as it likes, and the server enforces no per-frame cap. Treat the 16-slot and 6-interval caps as a budget an author must design within, and the 100-subscription count as a backstop, never as a security boundary. The limits below are the opposite — enforced in the mutations and queries themselves, so they hold whichever door the write came through.

| Key prefix length (append/watch) | 109                             |

| Stored + reserved bytes          | 16 MiB                          |
| Document slots per installation  | plan: Free 10,000, paid 100,000 |
| Documents per batch write        | 50                              |
| List page size                   | 100                             |
| Reservation TTL                  | 8 days                          |
| Retry horizon                    | 24 hours                        |

The document-slot ceiling is **plan-driven**. `PLAN_MAX_DOCUMENT_SLOTS` in `plugins_data.ts` maps the synced Polar product name to a ceiling (`Free` keeps 10,000; both paid plans get ten times that), and every write flow resolves it fresh through `db_resolve_document_slot_cap` before its capacity check. The ceiling always follows the organization owner's plan, never the acting member's: one installation gets one ceiling for every member, and a member's own plan cannot raise it. Every door resolves it the same way, including the expiry pass, which has no actor. Unknown billing state — no snapshot, no product, or an unknown product name — reads as `Free`, like every other billing gate. Nothing about the ceiling is stored anywhere, so a downgrade needs no migration: existing data stays readable, in-place updates cost no slot so they still work, deletes free slots, and only _new_ documents refuse with the same `storage_full` name, now naming the smaller number. An upgrade raises the ceiling on the next write. The 80% warning threshold follows the same resolved ceiling. The cap is a temporary rail: the product plan is to remove it entirely and bill per write instead — read the planned-removal entry in `../billing-system/SKILL.md` under "TODO / known gaps" before investing more in the cap.

Stored bytes are **not billed**. Writes do not emit a billing event either. The 16 MiB byte ceiling and the plan-driven slot cap are the only protection against a buggy or hostile plugin filling the database.

The key-prefix budget is `plugins_data_MAX_KEY_PREFIX_LENGTH` = 128 − 19: an append completes the prefix with `<inverted 13-digit ms>:<rand4>` (18 characters) plus one spare. The same 109-character limit bounds watch/window `keyPrefix`, so a key longer than 108 characters cannot have prefix-addressable children — plan hierarchical key schemes around that.

Byte size and idempotency hashes both use `canonical_json`, which sorts object keys at every depth. Convex does not promise a field order, so a size computed from `JSON.stringify` would drift between reads of the same value. Arrays keep their order because their order is data.

One accounting doc per installation (`plugins_data_usage`) carries `usedBytes`, `reservedBytes`, `usedDocuments`, `reservedDocuments`, `tombstoneDocuments`, and `collectionNames`. Neither ceiling can be answered by counting rows at write time, so the owning mutation maintains these counters in the same transaction as the document it changes. That makes it a hot doc: concurrent writes to one installation can lose an optimistic-concurrency race and retry. Value bytes, live reservations, revision tombstones, and deleted-append replay receipts all consume slots — the byte ceiling alone would not stop a plugin from writing ten million empty documents. Deleting an append moves its installation slot from `usedDocuments` to `tombstoneDocuments`; expiry returns it.

Beside it, one row per member who has written through a frame (`plugins_data_member_usage`, keyed by installation and `userId`) carries `usedBytes`, `usedDocuments`, and `collectionNames`. It exists so one member cannot spend the whole installation: a frame write is refused at 1.6 MiB, 3,000 slots, or 8 collections for that member alone. **Every one of those three refusals carries `name: "storage_full"`, the same name the installation ceiling uses**, and only the message tells them apart — a page that wants to say "you" rather than "this plugin" has to read the text. The two ceilings also differ in who they stop: a member at the _slot_ share can no longer patch **any** shared document in the installation, so channel renames and archives stop working for them, not only their own new writes. Only frame writes count against a member. A `user_api_key`, `plugin_run`, or `plugin_service` write stores `chargedTo: null` and skips the member ceiling entirely, and its size lands in the document's `machineBytes`, which is excluded from every member's own bytes. On a machine _patch_ of a member's document `chargedTo` is left alone — writing `null` there would discharge the owner, and their `usedBytes` would never be credited back when the row is deleted. Every charged document also stores `chargedToMemberUsageId`, the exact counter generation that owns it. Credits and backend size changes target only that row. If organization removal already deleted it, they do nothing; they never redirect into a row created after the same user rejoins. A rejoined member's own next write to an old document is a takeover into the new generation. A deleted append credits its bytes now but keeps its member slot until the replay receipt expires. The receipt stores the same exact row id, so expiry cannot debit a newer generation. The row is a counter, not an entitlement: `remove_user_from_organization` and `db_finalize_deleted_user` delete it (see `../data-deletion/SKILL.md`), and a later credit naming an absent member is a no-op. The rows are write-only in phase 1: nothing shows a member their own usage against the share their refusal names. The only reader is the operator's `preview_hard_delete_registered_plugin`, which reports `pluginDataMemberUsage` — a count of rows, never a per-user breakdown — because those rows carry user ids and an operator must see that before an irreversible delete. The count stops at 100 per installation; `pluginDataMemberUsageTruncated` says when it means `100+`.

Roll out exact member generations in two phases. First deploy the optional `chargedToMemberUsageId` and `generation` fields with the generation-aware runtime. New writes create `document_bound` rows; the first write by a member who still has a legacy row replaces that unsafe row with a fresh generation. Legacy documents stay readable and keep ownership, but they are uncharged until a member writes them again. Then run `migrations:run_delete_legacy_plugins_data_member_usage` and page `audit_legacy_plugins_data_member_usage_page` until every page reports zero candidates. Do not tighten either optional field: old untouched documents intentionally have no generation id, and a departed member's documents intentionally keep a stale id after their row is pruned.

`plugins.get_installation_storage_usage` is the manager-facing counterpart for the installation-wide counters (`usedBytes`, `documents`, `liveReservations`, `tombstones`, `collectionNames`). It takes `workspace.plugins.manage` through `db_authorize_plugin_management` and returns `null` on any refusal. It compares the _installation's_ own tenant against the membership's, not the tenant the caller passed: the counting helper resolves the accounting doc by installation id alone, so an installation from another workspace would otherwise answer with that workspace's byte totals. Before it there was no manager-reachable surface for these counters at all, and the store has no eviction and no repair short of uninstalling.

## The workspace roster (`workspace.members.read`)

`list_members` answers one page of the workspace roster to a plugin frame, for a member picker or a mention list. A row is `{ userId, displayName }` and nothing else; `displayName` is null for a member with no profile name. **The door must never answer an email.** The obvious app-side helper, `users.get_workspace_member_anagraphic`, returns the whole anagraphic document, which carries the member's email — and a frame may post whatever it reads to the origins in the version's `uiOutboundOrigins`. Paging rides the membership index, so the order follows the user id and carries no meaning; the caller sorts what it shows. `limit` is 1 to 100.

It is its own capability, and it does **not** ride on `plugin.data.read`. Resolving names for ids a plugin already stored (`resolve_member_display`, 50 ids per call) enumerates nobody; reading the list is a different consent, and a plugin that stores nothing and only shows a member picker must not have to ask for access to a document store it never writes to. The door checks both halves on every call, like every other: the installed version declares the capability and the installation accepted it.

Two consequences worth knowing before adding it to a manifest:

- **Every installed plugin that adds it forces a re-accept.** Consent is exact-match and an upgrade rewrites `acceptedCapabilities`, so the roster stays shut until an admin accepts the new list. A frame calling it in the meantime hears `{ refusal: "not_consented" }` — a distinct answer, never an empty roster, because a page that received an empty list would tell the member this workspace has nobody in it and the admin would never learn there is a consent waiting. Every dead-frame refusal (uninstalled, revoked, session gone) stays the ordinary opaque `null`.
- **An anonymous identity can read the roster.** `mint_page_session` resolves its caller with `server_convex_get_user_fallback_to_anonymous`, so a page session can exist with no Clerk account behind it, and such a member is a normal member for every check the door makes. This is deliberate: one rule for every invited member. It does mean an anonymous visitor invited into a workspace can enumerate the full member list, where `resolve_member_display` only ever turned ids they had already seen into names.

## Ordered writes for external producers

An external service that owns a stream of updates uses the versioned pair instead of the interactive routes:

- `write_versioned_document` binds the key to the writing `plugin_service` principal for good. Every other writer, including the plugin's own page, is refused with `This document is written by a service and cannot be changed here`; a different service producer gets `This document belongs to another writer`. The fence also covers the window after a terminal `delete-versioned`, when the tombstone is the only thing left holding the key. Revision n is accepted only when the stored revision is n - 1, so a replayed request is recognized instead of applied twice.
- `delete_versioned_document` may skip ahead to any higher revision, because a terminal delete supersedes entries the producer has not sent yet. It leaves a `plugins_data_revision_tombstones` row that refuses every later write until its retry horizon. Deleting a stored value is never refused for capacity: it frees the value's bytes and its tombstone takes the slot the value just gave back, or a full store could never be emptied. Deleting a key that was never stored is checked, because that tombstone gives nothing back and would otherwise let a producer fill the store with tombstones alone. A live reservation already holds that slot, so the tombstone converts it instead of charging a second one. A released retry records whether it still owns a `tombstoneDocuments` slot. Only a never-stored retry with that marker can supply the delete's slot; a converted reservation cannot.
- `reserve_document` holds capacity for one exact key before an external side effect happens, so a full store cannot refuse the write afterwards. It answers `reservationId`, `remainingBytes` and `expiresAt`. The id is for the producer's own records: `release_reservation` finds the row by `idempotencyKey` plus the same collection and key, and never takes the id. The idempotency key is validated exactly like a collection name or a document key — not empty, at most 128 characters, no surrounding whitespace, no control characters — because it is the lookup key of the replay index, and a padded copy would quietly become a second reservation for the same document.
- A replay under the same idempotency key answers with what the reservation holds **now**, not with the first answer it gave. An ordered write spends part of a live reservation, so a first answer kept on the row would promise bytes the producer already spent. The reservation stores no reserve result at all for that reason. Only a release freezes anything, in `releaseResult`, so a replayed release answers the same thing twice. A replayed reserve reads `remainingBytes` and `expiresAt` straight off the live row. Once the reservation is released the replay is refused as a conflict (`This reservation was already released`), because the producer would otherwise learn the same thing only after doing the outside work the reservation was meant to protect. A _different_ request under that key is refused too (`This idempotency key was already used for a different reservation`). A fresh idempotency key clears only the prior key's replay refusal. It does not cancel a live reservation or a durable document or tombstone fence on the same target key. A fresh request for that same live target therefore answers `This document already has a live reservation` until a release or the expiry cron ends it; a fresh request for a different target is not blocked by the old target's reservation.
- An expired reservation still fences and still costs until the cron reaches it. `db_get_live_reservation` asks the index for `state === "live"` and does not compare `expiresAt`, so between the expiry and the next hourly pass the key cannot be reserved again and its bytes stay in `reservedBytes`. `expiresAt` is what makes the cron pick the row up, not what ends the hold.
- Storing or growing the value moves bytes out of the reservation and into `usedBytes`; shrinking gives them back. `release_reservation` returns the rest and keeps the doc as a retry record, whose 24-hour horizon starts at the release. A released retry also stores `holdsUsageTombstoneSlot`: `true` when a never-stored release moved its reserved slot into `tombstoneDocuments`, and `false` after a write already converted that slot or a terminal delete consumed it. Expiry returns a slot only when that marker is true; checking the current document is not enough because a fresh reservation may write the same key before the old retry expires. The live-reservation lookup uses `by_installation_state_collection_key`, with `state` ahead of the collection, so it asks the index for the live doc. One key collects a retry record per reserve, and a lookup that read the key's docs and filtered afterwards would stop before the live one and hand out a second reservation for the same document.
- All three release paths — the release route, the terminal `delete_versioned_document` (which ends the work the reservation was held for, so it gives the bytes back instead of waiting for the cron), and the hourly expiry cron — go through the one `db_release_reservation` helper, and the helper is what drops the collection name when the release empties that collection. A caller that patched the accounting doc itself would leave the name behind, and a collection name is a slot out of sixteen, so the installation would slowly lose collections it no longer stores anything in. The helper asks after its own patch has landed, so the reservation it is releasing is not counted as one of the live documents keeping the collection alive.

The producer identity is `principalKey`, which survives token rotation, so a renewed grant keeps writing the same keys.

## Deletion and expiry

`plugins_data_db_drain_batch(ctx, {organizationId, workspaceId, installationId, batchSize})` deletes one bounded batch across the installation-owned tables. An installation-scoped pass starts with `plugins_ui_sessions`, because public uninstall deletes the installation first and uses that deletion as the immediate revocation. Reservations, append replay receipts, revision tombstones, documents, service grants, file access bindings, `plugin_scope` grants, live scope rows, scope lifecycle markers and released-range fences, service upload targets, member usage, and the accounting doc follow. A workspace purge sets `organizations_workspaces.pluginDataPurgeStartedAt` before its first bounded content step, then disables enabled installations through `by_organization_workspace_status_pluginName` before plugin-owned rows drain. `install_version` checks the fence before both insert and re-enable. The central plugin UI, store, service, and runtime gates require the workspace doc to exist without the fence; enabled status is the later second guard. Both guards stay until the later UI-session and installation deletion passes, so a stale writer cannot turn a removed private range into a public document. A data-only reset clears the fence only after it finishes; workspace deletion removes it with the workspace doc, and the missing doc itself closes those gates. Organization deletion keeps workspace docs during retention, so its phase-one mutation fences each one. The service-upload helper does nothing on an installation-scoped drain because uploaded files belong to the workspace, not the plugin. The accounting doc goes last so it is never the survivor. The drain never writes `files_nodes`: files a plugin created belong to the workspace and stay, and the mirrored `file` grants on them stay too, because those frozen files outlive the plugin (only the binding rows drain). A `null` installation id drains a whole workspace, and only then are upload targets deleted. Callers must keep calling until `done`.

Three paths use it. `uninstall_version` deletes the installation doc in its own transaction and therefore schedules `drain_uninstalled_installation` with the scope it already holds — the drain cannot look the tenant up afterwards. `db_purge_organization_workspace_content_batch` quiesces the workspace installations, runs a workspace-scoped pass, then removes sessions and installations; this also covers organization deletion and admin data reset. `hard_delete_plugin_from_registry` runs a per-installation pass before deleting the installation doc.

`preview_hard_delete_registered_plugin` reports the four document counts from the accounting doc rather than by counting docs: one installation may hold up to its plan's document-slot ceiling (10,000 on Free, 100,000 paid) inside a 16 MiB byte ceiling, and reading them all to learn how many there are would exceed what one Convex query may read. So its `pluginDataTombstones` covers released reservation records and delete tombstones together, because one counter pays for both of their slots. Member usage, service grants, file access bindings, live scope rows, `plugin_scope` grants, and scope lifecycle rows have no accounting counters; each of those reads is bounded and its count means `100+` past the cap. `releasedScopeRangeRows` counts both identity markers and real range fences. `plugins_data_db_count_installation_docs` bounds every read and returns a count plus a truncation flag. A truncated installation makes the whole plugin total a lower bound. Read every flag with its count; a count alone cannot say whether it is exact. The registry-wide caller also passes its shared child-row budget into this helper so many bounded installations cannot add up to an unbounded transaction.

The hourly `cleanup expired plugin data` cron runs `cleanup_expired_plugin_data`, which releases live reservations past `expiresAt`, deletes released retry records past `retryHorizonExpiresAt`, deletes revision tombstones and deleted-append receipts past `expiresAt`, and deletes expired `plugin_service_grants`. A released retry returns a tombstone slot only when its own marker says it held one. A converted-release retry never took a usage tombstone, so deleting it must not give a slot back while the value or revision tombstone still fences the ceiling. An append receipt always returns its installation tombstone slot; it also returns the member slot only when the exact stored `memberUsageId` still exists. It is hourly rather than daily like its plugin siblings because a retry record becomes deletable only 24 hours after its release or delete, so a daily pass would routinely miss rows that just became eligible and hold their slots for another full day. The reservation index is `by_state_expiresAt` with `state` first, so a workspace holding many released retry records cannot fill every batch with rows that need nothing.

# Service grant exchange

`packages/app/convex/plugins_service.ts` and its `plugins_service_http_routes.ts` own the four `/api/internal/plugins/service-grants/*` routes an outside server uses to get and keep a `psg_` grant. `public_api.ts` still owns the grant table, the token format, the mint, and the resolver; this module owns only the lifecycle.

Scope the word "page" below by the token, not by the paragraph. The `plu_` bearer is a plugin frame's UI token, and a plugin page and a file view both carry one: `resolve_principal` finds it by token hash alone and hands back a `plugin_ui` principal with no frame kind on it, and `plugins_service.ts` never reads `fileNodeId` — the word does not appear in the file. So every rule about that bearer is a rule for both kinds. Any publisher can register their plugin's service now, but Council is the only registered plugin today, and it ships one page and no file view, so the passages naming Council's own `council_page_auth` machinery say "page" because that is what Council has, not because a file view is shut out. The optional manifest `service` block exists only so the reviewed manifest and both consent screens can show the service surface — the registration row, not the manifest, is the exchange authority, and the two are deliberately not cross-checked at publish (Council 0.2.3 has no `service` block and keeps working through its seeded registration).

All four take two credentials, the same way the runner host routes do. `Authorization: Bearer <token>` says which installation and member the call is for. `X-Bonobo-Service-Authorization: Bearer <secret>` proves the call comes from the registered service: the plugin's publisher manages a `plugins_service_registrations` row (Service section on the plugin details page) holding a hashed `pse_` exchange secret plus the scopes the service will request, and `authorize_service_request` resolves the bearer first, loads the registration by that installation's `pluginName`, and compares the presented secret against the stored hash in constant time. The bearer-before-secret order is deliberate — the registration is keyed by the plugin the bearer names, so there is nothing to compare until the bearer resolves — and every authentication failure (missing header, unknown token, unregistered plugin, wrong secret) answers the same flat `Unauthorized` literal, so a caller cannot tell which credential was wrong or whether a registration exists. The publisher-facing query never returns the hash; `set` returns the plaintext secret exactly once and a re-set rotates it, killing the old secret immediately. Registry hard delete drains the registration row with the name.

| Route             | Bearer | Does                                                                                      |
| ----------------- | ------ | ----------------------------------------------------------------------------------------- |
| `exchange`        | `plu_` | Mints a new 24-hour `interactive` grant for the UI token's installation                   |
| `renew`           | `psg_` | Gives that same grant doc a new raw token and another 24 hours (processing: token only)   |
| `seal-processing` | `psg_` | Trades a live interactive grant for a NEW six-day `processing` grant sealed to one prefix |
| `verify-live`     | `psg_` | Answers whether the grant may still act, and what it may attempt                          |

Rules that are easy to get wrong:

- A plugin with no registration row cannot use any of the four routes: the missing registration answers the same flat `Unauthorized` as a wrong secret. The publisher gate on the registration mutations is the same ownership rule as publisher secrets — signed-in, `plugins_manage` rate limit, current repository claim owner equal to the latest version's creator. Council's registration was seeded once in 2026-08 by a one-use migration action that read the then-deployed Council env pair inside Convex, hashed the secret, and inserted the row without ever returning the secret; the env vars and the action are both gone now, and rotation goes through the publisher UI like any other plugin.
- Only `exchange` can create a grant, and only a `plu_` token can drive it. A grant that could exchange itself would keep a service alive forever without a member ever opening the page again, and a leaked exchange secret would then be enough on its own. `renew` refuses a `plu_` for the mirror-image reason.
- Account finalization drains every grant for the actor through `plugin_service_grants.by_actorUser` before it deletes memberships. Same-email recovery and a later invite therefore cannot make an old `psg_` token valid again.
- Because the exchange is what creates a grant, a service must exchange once per UI token, not once per request or once per cache window. A plugin frame polls for as long as the member leaves the tab open, so exchanging on a timer leaves one live 24-hour grant per timer tick per tab. Council's `council_page_auth` keeps the page token's hash pointing at the grant that token already produced (`page_token_cache`), so a later call re-checks that same grant instead of minting another one. Two separate deadlines then decide what one call does. The first is the mapping row's own `expires_at`, which Council writes as `min(grant expiry, exchange + 30 minutes)` (`HOST_PAGE_SESSION_TTL_MS` in `grants.ts`). Past it the page exchanges again, because the exchange is the only step that presents the `plu_` token to the host. The host gives a plugin frame a 30-minute session and rotates the plaintext token on every refresh — one `SESSION_TTL_MS` in `plugins_ui.ts` serves the page mint, the file-view mint, and the refresh — while `verify-live` asks about the grant and never about the token that bought it. So only a fresh exchange can notice that rotation, and the ceiling keeps a stolen or rotated token working for at most one session instead of the grant's full 24 hours. The second deadline is the one-minute liveness window (`PAGE_TOKEN_CACHE_MS`), measured from `service_grants.updated_at`, the last time Convex answered about that grant. Inside that minute the stored answer still stands. Past it the call runs `verify-live` on that same grant, and `verify-live` re-reads the installation, the actor account, and the actor's membership on every call, so revocation still closes the page on the next minute boundary; reuse only skips the mint. Reuse renews nothing: the grant keeps the 24 hours it was minted with, and the mapping keeps the ceiling it was written with. Revoking a UI session does not take a minted grant back either, because the grant is bound to the actor and not to the session — the 30-minute ceiling, not session liveness, is what bounds a rotated token here. This is not the "newest grant for the actor" lookup the host-ticket rule below refuses: the grant is found by the token that minted it, which pins it harder than exchanging again would.
- **What Council claims when it re-checks a grant is what decides who keeps the page.** `council_verify_grant` in `grants.ts` takes its `scopes` claim from the caller and has no default value, so every call site has to state what it is about to spend. `council_page_auth` claims `["plugin_data:read"]` and nothing else, because reading is all the page does: it lists the member's meetings and watches one they are already in. Every other caller claims `["plugin_data:read", "plugin_data:write"]` — the seal in `lifecycle.ts`, the host room ticket and the page close in `routes-page.ts`, and, through the two wrappers `council_verify_meeting_grant` and `council_verify_host_actor_grant` (which state the pair themselves, because every action behind them writes), the open retry, the room join, and start recording. That narrow page claim is what keeps a member an admin has moved to the `viewer` role on the page: they keep `content.read` and lose `content.write`, so the second `verify-live` scope check below refuses every claim carrying `plugin_data:write`, and a page that claimed it would take the member's own meeting list away from them within the one-minute liveness window. Asking for less loses no check, because every route that writes claims the write scope again for itself. The missing default is deliberate — the only value a default could carry is the wide pair, which is exactly that over-claim, so a caller who forgets the argument gets a compile error instead of the defect back in silence. Two consequences are also deliberate and should not be "fixed". A `viewer` cannot close their own meeting, because `handle_close` claims write: the close is what hands a recorded meeting to the pipeline, and the scheduled deadline sweep closes the meeting instead. And `handle_create` verifies no grant at all — it spends the member's write permission at `/api/v1/plugin-data/reserve`, so a demoted member keeps the page and is refused there, with a message that names the permission rather than storage.
- `renew` patches the grant doc it was given; it never inserts. The mutation looks the doc up by the hash of the presented raw token, never by a grant id, because an id is not a secret. It repeats the mint's own liveness checks (enabled installation, same plugin version, `plugin.service.connect` still accepted, live actor membership), so the service learns now instead of holding a token that answers 401 on its next real call. It leaves the stored scopes alone: the resolver narrows them against current capabilities on every call, so rewriting them would only make a capability that is given back later stay lost.
- The registration binds a secret to exactly one plugin name, and that binding is what the old `COUNCIL_PLUGIN_NAME` check became. Every plugin frame is served from the same asset origin, pages and file views alike, and this skill says plainly that the shared origin is not a plugin-to-plugin boundary (see "Plugin UI pages" above), so one frame can read another frame's `plu_` token. The registration lookup rides the bearer: `authorize_service_request` loads the row for the bearer's own `installation.pluginName`, so a stolen `plu_` token from another plugin's frame compares against THAT plugin's hash and the presenting service's secret fails flat — even when both plugins are registered. Keep both frame kinds named here — a reader auditing whether the file-view frame is inside this threat model follows the docblock citation in `plugins_service.ts` and must not land on a sentence naming only pages. Without the binding the exchange would turn a stolen read-only token into a grant carrying the other plugin's producer identity — and a service grant is the only principal allowed to write versioned documents at all.
- `exchange` requires `plugin.service.connect` plus the capability behind each REGISTERED scope (`SCOPE_GATING_CAPABILITY`: `plugin_data:read` → `plugin.data.read`, `plugin_data:write` → `plugin.data.write`, `files:write` → `workspace.files.write`), and refuses with 403 before writing anything. The mint would narrow a missing scope capability away instead of refusing, and by then the grant doc would exist. `workspace.files.create-read-only` is deliberately NOT required at exchange: it gates one create-time mode on the sealed upload door, which `create-target` checks at the moment a read-only target is requested, so a service that never locks a file needs no such consent to connect. Consent is all-or-nothing per version (`install_version` requires the accepted set to equal the version's declared set), so in practice this fails only when the installed version stopped declaring a gating capability.
- `exchange` mints the registration's scopes minus `files:write`. That scope exists only together with a destination prefix, and the destination is chosen when a meeting opens, not when the service connects. `seal-processing` is what mints it: it takes a live interactive `psg_` bearer plus `{ destinationPathPrefix }` (a normalized absolute path of canonical lowercase folder names, not `/`), repeats the exchange's registration, capability, and actor `contentPermissions.write` checks, and mints a NEW grant — same installation and actor — with phase `processing`, exactly the registered scopes, exactly that prefix, and a six-day expiry. The mint runs with `requireAllRequestedScopes`, so a capability that disappears between the pre-check and the mutation refuses the seal instead of silently writing a narrower grant. A processing grant cannot seal again (403), so the six-day window cannot roll forever, and `rotate_plugin_service_grant` keeps a processing grant's `expiresAt` unchanged — renewal rotates the token only. The interactive grant stays alive beside the sealed one.
- `verify-live` compares the values the service sends with what the grant really says, but **not every field the same way**. `installationId`, `phase` and `destinationPathPrefix` are exact `!==` comparisons, so any difference answers 409. `scopes` gets two checks, and both walk only the scopes the service claimed. The first is a one-directional subset test — `expected.scopes.some((scope) => !liveScopes.includes(scope))` — and refuses a scope the grant no longer has, with `This grant no longer has the scopes it needs`. The second reads the actor's live `contentPermissions` and refuses a scope the member behind the grant may not use, with `This grant's member can no longer use the scopes it needs`. An admin can move that member to the `viewer` role while a meeting runs: the member stays in the workspace and the grant keeps the scope, so every check above this one still passes. `REQUIRED_CONTENT_PERMISSION_BY_SCOPE` says which content permission each scope needs. Keep it in step with `REQUIRED_APP_PERMISSION_BY_SCOPE` in `public_api_http_auth.ts`, because that map is what an `/api/v1/*` call applies to this grant's scopes before it does the work. A scope one map calls readable while the other calls it writable is answered 200 here and `Permission denied` at the very call the service asked about. Those are claims to check, not authority to hand out: a wrong value can only turn a yes into a no. The 200 body also reports the actor's current `contentPermissions`, so a service sees a permission it lost even when it claimed no scope that needs it.
- Every `verify-live` body field is required: `installationId`, `phase`, `destinationPathPrefix`, and `scopes`. A service that states nothing cannot be told it was wrong. `scopes` is the service's claim about the grant it thinks it holds, and it catches drift in one direction only. A service that claims a scope the grant no longer has, or one its member may no longer use, gets a 409 here instead of failing later, on the write at the end of a meeting. A service whose own record lists _fewer_ scopes than the grant holds passes instead, which is harmless: it can only attempt less than it is allowed, and the 200 body hands back the grant's real `scopes` and the member's `contentPermissions` so it can correct its record. It is not how a service learns that a capability went away: an upgrade replaces `pluginVersionId` and the resolver refuses the grant outright, so there is no narrowed-but-still-live grant for this field to catch.
- The exchange body is a strict empty object. Tenant, installation, plugin, scopes, and destination all come from the live installation, so there is no body field to ask for more with. The response returns `actorUserId` from the resolved `plugin_ui` principal so Council can bind its D1 grant and meeting rows to the trusted actor. That is the principal's real kind in the code (`principal.kind !== "plugin_ui"` is the guard the route uses), and it is the same kind for a page and for a file view.
- A Council host ticket stores the exact interactive grant that minted it, and the room session keeps that same grant id. Host join and start-recording verify that exact grant. Do not look up the newest grant for the actor: opening another plugin frame can create a newer grant with a different lifetime. Host close deliberately skips the actor recheck so a host whose membership was removed can still end an already-open provider meeting.

# Clean-slate changes and recovery

This plugin system is pre-production. Change the manifest, SDK, host, schema, and current plugins together; do not add legacy protocol handling, dual database shapes, redirect routes, or review-policy migrations. Stored plugin pages and file views are always required arrays; omitted manifest `pages`/`fileViews` fields are normalized once to `[]` during registration. The stored `runtimeVersion` field and the UI message protocol version are gone. Manifests still require `compatibility.bonoboPluginRuntime: "1"` as the single current runtime stamp; there is no fallback or multi-version runtime path. If persisted plugin data conflicts with the current contract, use `../dev-data-reset/SKILL.md` to remove the registry and republish the current source commits. Preserve Clerk-backed user docs and their Polar state during that reset.

Recovery uses trusted sources only: current Git submodules/remotes for plugin artifacts, Convex deployment environment variables for known publisher values, and provider-supported credential creation or explicit user input for a missing value. Never use Playwriter or other browser automation to extract tokens from provider pages, and never print secret values in logs or reports.

# Installation configuration

Configuration is manifest-driven. `plugins_versions.configuration` stores the plugin's editor description and default YAML, while `plugins_workspace_installations.configurationYaml` stores only the user's YAML string or `null`. Never store parsed filter values on the installation doc.

```jsonc
"configuration": {
	"description": "Choose which upload folders start this plugin.",
	"defaultYaml": "routing:\n  allowedFolders:\n    - /\n"
},
"events": [{
	"type": "files.upload.completed",
	"contentTypes": ["image/png"],
	"filters": [{
		"field": "source.path",
		"operator": "pathIsUnderAny",
		"configurationPath": ["routing", "allowedFolders"]
	}]
}]
```

- A manifest may omit `configuration`; validation normalizes it to `null`. Event `filters` may be omitted and normalize to `[]`. A filter requires a configuration declaration, and the declared default YAML must validate before publish.
- The YAML root is a plugin-owned object. It is at most 16 KiB and rejects blank or multi-document YAML, aliases, tags, duplicate keys, and non-JSON values. Unreferenced plugin settings are allowed.
- The current generic filter is `source.path` + `pathIsUnderAny`. Its `configurationPath` points to an array of at most 32 unique canonical absolute folder paths, each at most 512 characters. `/` matches every folder; other entries match the exact path and descendants, case-sensitively; an empty array disables that automatic event.
- New installations use the version's `defaultYaml`; upgrades preserve valid existing YAML. A version without configuration stores `null` and rejects configuration edits.
- The public save mutation resolves auth, applies the plugin-management rate limit, checks plugin-management permission and tenancy, loads the installed version, validates against its manifest events, then patches only `configurationYaml`.
- `workspace.plugins.manage` is not `content.read`. A custom role can hold either without the other, so a query that returns plugin state plus file details needs both. `list_recent_runs` is the worked example: it authorizes on plugin management, then drops each run's file name, path, content type and size to `null` unless the caller also holds `content.read`. Run status, errors and timings stay visible — an operator has to see failures.
- Automatic dispatch loads the matching manifest event and applies its generic filters before dedupe and run creation. Invalid stored YAML is an unreachable invariant, but dispatch logs and isolates that installation so it cannot block upload finalization or other plugins. Manual runs bypass automatic event filters. Every run receives the parsed value as `event.configuration`, or `null` for a plugin without configuration.
- Upload dispatch rule: every upload that settles as a stored blob dispatches `files.upload.completed` — including an editable-text upload whose host conversion failed deterministically and fell back to the stored blob (`settle_upload_conversion_fallback` in `convex/r2.ts`). Only a successful host conversion suppresses the event. Service uploads are the other exception: `plugins_runtime_db_enqueue_upload_completed_runs` refuses any asset a `plugin_service_storage_targets` row owns, fallback blobs included — a plugin's stored artifact must not fan out into other plugins' backends.
- Service-upload targets require the sealed destination path plus its stable folder node id. The dev rollout audit found no target missing either field before the schema was tightened. Council deletion archives that exact folder even after a member renames it. Releasing a pending upload deletes its placeholder but keeps the target as a released identity record for the archive step. The archive route bounds active and archived descendant reads together at 256 docs.
- Settlement bills money too: when the R2 event commits a target, `db_settle_canonicalized_target` emits one `file_save` (1¢) to the workspace payer through `billing_db_emit_file_save`, once per target — the stored bytes still charge the storage quota separately. See `../billing-system/SKILL.md`.

# Manifest secrets declaration and installation health

A manifest may declare its secrets so the details page can say when an installation is incomplete:

```jsonc
"secrets": [
	{ "name": "OPENAI_API_KEY", "description": "Key used for transcription.", "optional": false }
]
```

Declaration rules in `plugins_validate_manifest` (`packages/app/shared/plugins.ts`):

- Names must already pass `plugins_validate_secret_name` unchanged (env-key syntax, max 128). A name that fails those rules could never be configured or read, so the installation would stay "incomplete" forever.
- Names are unique per manifest. `optional` defaults to `false`. `description` is required but may be empty; it is capped at 300 characters and rejects control and format characters (bidi overrides, zero-width) because it renders in the manager UI next to a credential input.
- Declaring secrets requires the `plugin.secrets.read` capability. The converse is allowed: an already-published plugin may hold `plugin.secrets.read` without a `secrets[]` field.
- Persistence: `plugins_versions.secrets` is `v.optional(...)` because versions published before the field exist without it. Every read is `version.secrets ?? []`; an absent field means "declares no secrets" and must never produce a `missing_secret`.

Health is computed on read by the public query `plugins.get_installation_health` (`packages/app/convex/plugins.ts`, region "installation health"):

- Args are `membershipId` + `pluginName`; org/workspace derive from the membership doc, so a forged scope is structurally impossible. Non-managers, anonymous callers, and not-installed plugins get `null`. The enumerated `returns` validator carries only names, descriptions, booleans, and counts, so a handler bug fail-closes instead of leaking secret docs.
- Health evaluates the INSTALLED version (`installation.pluginVersionId`), not the latest published one.
- `missing_secret`: a declared non-optional secret with no installation-tier row and no valid publisher-tier row. The publisher check replicates the runtime re-claim guard (`repository.ownerUserId === version.createdBy`), so health never says "configured" where `get_secret_for_runtime` would return null.
- `secrets_capability_unconfigured`: only for versions that declare NO `secrets[]` but accepted `plugin.secrets.read`, computed from installation-tier rows only. Checking the publisher tier here would leak whether the publisher keeps secrets on the repo — an existence oracle no manager-reachable surface exposes. Accepted residual: a plugin running fine on publisher defaults shows this notice.
- `recent_runs_failing`: the last 5 finished runs all failed. The query reads a bounded slice (20 rows) and keeps the first 5 with status succeeded/failed, so queued and running rows never count. Accepted residual: a backlog of 16+ queued/running rows can temporarily hide the flag. Payload is the count plus the latest plugin-authored `errorMessage` — same audience and gate as `list_recent_runs`, with no file details.
- `disabled` is not a health issue. It is a short operator-owned state during registry hard delete, not a normal user control. The health query has no status gate, while plugin pages, data doors, service grants, public API calls, and queued event-run starts all require an enabled installation. The Hero may show its "Disabled" badge during that destructive drain.

The details-page Health section (`RoutePluginsPluginHealth` in `$pluginName.tsx`, between Hero and Secrets):

- Issue titles and instructions are app-owned strings. The publisher-authored description renders as escaped plain text, attributed as "Publisher's note:", and must never render inside the secrets modal itself — keep the publisher's words one click away from the credential input.
- The header says "Installation incomplete" only when a `missing_secret` issue exists and "Needs attention" only for failing runs. The capability notice alone keeps "Installation healthy": it is informational, and demoting the header would make correctly-configured publisher-default plugins read as unhealthy forever.
- The missing-secret action opens the shared secrets modal (its open state lives on the route so both the Health row and the Secrets section drive one modal). The failing-runs action opens and scrolls to the Activity section.
- Hidden when the plugin is not installed or the viewer cannot manage plugins.

# Chitchat plugin (`plugins/bonobo-plugin-chitchat`)

Git submodule with its own repo (`raythurnvoid/bonobo-plugin-chitchat`), scaffolded from the Council/Gallery template: committed `dist/`, `scripts/build-manifest.mjs`, React source (bundled through the repo's Preact aliases), and the same release rules. One page (`chat`) and, since 0.6.0, a backend worker (`dist/backend/worker.js`, source `src/backend/worker.ts` with `markdown.ts`, `state.ts`, and `host.ts`) with seven invoke endpoints — `message-send`, `message-edit`, `message-delete`, `reply-send`, `reaction-toggle`, `channel-manage`, `reconcile` — all `serialization: "installation"`. The manifest declares nine capabilities: `plugin.data.read`, `plugin.data.user-write`, `plugin.data.write`, `plugin.backend.invoke`, `workspace.files.read`, `workspace.files.write`, `workspace.files.own-write`, `workspace.files.own-access`, `workspace.members.read`. Keep `workspace.files.write` in that list: manifest validation refuses `workspace.files.own-write` without it. `userWritableCollections` narrows the user-write door to `channels` + `cursors`: message, reply, and reaction writes go through the backend (`src/chat-invoke.ts` wraps `client.backend.invoke` — it waits out `busy` answers and maps the relayed JSON into the `_yay`/`_nay` shape the page's write machinery already speaks, and `unavailable` stays a replay-with-same-request-id case exactly like the old append door), while the page still writes channel docs and read cursors directly. `channels` stays user-writable because private-channel create writes the channel document from the page through `scopes.createWithDocument` — a known gap, not an oversight. The backend also writes the workspace transcript files described under "Plugins write their own workspace files" above. Chitchat was the first consumer of the user-write door and CAS writes, and (since 0.1.4) of the SDK's page-owned ConvexClient, so its data shapes double as the door's reference usage.

- Key shapes (`src/chat-data.ts`): channels are SHARED docs created through `put` with client UUID keys — any member can rename or archive, and the sidebar sorts by name because the keys carry no time. Messages are appended under `<channelKey>:`, so a message key is `<channelKey>:<inverted 13-digit ms>:<rand4>` (3 colon parts); replies append under the root message key (5 parts tells a reply from a message). Reactions live in their own collection as OWNED docs keyed `<messageKey>:<token>` plus the server-stamped `:<userId>` suffix; the palette is 8 fixed tokens because emoji keys are unreliable, not uniformly refused — the store's key rule rejects only control and format characters, so simple emoji pass while ZWJ-joined ones fail, and a fixed ASCII token set keeps reaction keys predictable (the `chat-data.ts` header comment says exactly this since 0.1.4). The worst-case composed key stays well inside the 128 budget with real user ids (32 characters on this deployment).
- Windows and change feeds (`src/channel-view.tsx`): the open channel keeps **one** `data.watchWindow` on messages at page size 100 under the channel's key prefix. "Load older" extends that window through the SDK window manager; once it reports `atCapacity` the same button switches to HTTP `POST /api/v1/plugin-data/list` (omit `installationId` — a plugin token answers 400 if that field is sent). Reactions and channel-wide replies are **not** windows. After the first messages delivery the page HTTP-lists those two collections under the same prefix, then opens three `data.watchChanges` feeds (messages, replies, reactions). All three fence at the same value: the newest `updatedAt` among the messages just loaded — not the wall clock, and not a per-companion fence. An empty companion list does not pick its own fence; a lower fence would only over-deliver, which the revision-forward merge already dedups. `updatedSince` is an inclusive lower bound (`gte` on the host query): a write batch stamps up to 50 docs with one `Date.now()`, so a change whose `updatedAt` equals the cursor must still be delivered. Copy the newest applied `updatedAt` as-is; over-delivery of that millisecond is free. Advance the cursor when the newest delivered `updatedAt` is strictly greater than the current fence, so a same-ms re-delivery does not re-subscribe. If a truncated feed page is entirely tied to that fence millisecond, step to `newest + 1` so a later edit is not stuck behind those 100 rows — messages, replies, and reactions all do this. That step can permanently skip tied rows past the first 100 when 101 or more documents in one collection and scope share the same `Date.now()` millisecond, reachable only through parallel bulk imports on the batch door (three 50-document mutations in one millisecond); replies and reactions have no heal for it, and messages heal one page. Each feed applies pushed documents by revision-forward merge, filtered to this channel's key prefix on a public (unscoped) read; the cursor then advances from the newest `updatedAt` in the **full** batch so another channel's updates cannot stall the fencepost. A truncated **messages** feed also heals by HTTP-listing keys after the window's oldest key (the same `keyStartExclusive` shape as load-older). Replies and reactions drain by walking that cursor; they do not HTTP-list on `truncated`. A failed companion HTTP list marks coverage incomplete. It retries with exponential backoff plus jitter (start about 1 s, double, cap about 30 s), stops for good on success, and never retries on feed death. Feed delivery and tab-visible are early wake-ups of that same attempt, with one list in flight at a time — this is failure recovery, not a periodic refresh. Private channels pass `scopeId` equal to the channel key. After EVERY messages-window delivery, a catch-up loop HTTP-lists another companion page while that list reports `hasMore` and its deepest delivered root key is still newer than the oldest visible **window** message root (HTTP history must not drag the companions). Root keys use their exact three-part message or five-part reply shape, so `p/<uuid>` private roots keep their full length. Reaction coverage derives the root from the validated target key, reply coverage derives it from the validated reply key, and malformed keys do not move the coverage frontier. HTTP paging still fences on the full stored companion key. Valid roots use JS `<` because every key Chitchat mints is ASCII by construction (client UUID prefix, server-minted digit-and-hex tail).
- Companion HTTP paging fences on the last runtime-validated public-document envelope, not the last collection value Chitchat accepts. A full page of foreign values can be dropped without hiding older valid reactions or replies. A page with no usable envelope and `isDone: false` is incomplete and retries.
- Reply-count honesty: a per-message reply badge shows a number only for a COVERED root — the replies HTTP list has no more history, or the root is strictly newer than the deepest delivered reply root — **unless** the replies feed (or an HTTP page) already delivered replies for that root, in which case the known count shows even on an otherwise uncovered row. An uncovered root with no delivered replies shows "View thread" instead of a guessed zero, and `chat_format_reply_count` caps at "99+" only while `hasMore` is true. The thread panel does **not** open a watch: it reads the parent replies store, HTTP-lists that root's prefix on open, and rides the channel replies feed.
- Channel rename/archive is compare-and-set: the put sends `expectedRevision` from the doc the dialog read, and a `conflict` keeps the dialog open with a clear message instead of last-write-wins.
- Seam stitching (`src/chat-store.ts`): messages, replies, and reactions accumulate by key with a revision-forward merge — the same seam lets an optimistic local echo coexist with the server's later delivery, and it is how a change-feed document updates a frozen HTTP row. Reactions are no longer replace-from-window: a removal is an in-place owned `{ removed: true }` marker on the same key (`putOwned`, not `removeOwned`), so it keeps its document slot, re-adding reuses the doc, and grouping treats a marker as absent. Every doc read from a watch, a feed, or an HTTP page is Zod-validated and an invalid doc is dropped, not rendered — the store is multi-writer and the door cannot enforce value shapes.
- Attachments are workspace-file references inside message values, listed through `workspace.files.read`. Uninstall drains the plugin's documents but never the referenced workspace files. Since 0.6.0 the plugin's own backend renders public channel transcripts under its owned root and each private channel under a restricted per-channel folder whose readers follow the scope (`access.readScopeId` bindings); see "Plugins write their own workspace files" above.
- Accessibility: the message log is `role="log"` with `aria-live="off"` plus one hidden polite announcer fed only remote-authored arrivals; `atCapacity` and `incomplete` render as visible status/alert text; controls stay at least 44px and the layout holds at a 360px viewport and 200% zoom.
- Private channels and DMs (since 0.2.0): a private channel is an ordinary channel whose key starts with `p/`, and the scope created over that key covers all four collections at once — the channel document carries the channel's name, so a scope over three of them would leak it. **A DM is a private channel with two people in it and nothing else**: no separate kind, no separate component, no branch in the store. Privacy is read from the key alone (`chat_channel_is_private`), never from a flag in the channel value, because the value is rewritable by everybody who can see the channel while the key never changes. **A channel the member is not in is absent, not locked** — its documents never arrive, so the sidebar shows nothing for it, and the app deliberately renders no placeholder: a placeholder is how a member learns the channel exists. The privacy sentence names the organization owner as a reader, in the same words in the create dialog, the people dialog and the channel header (`chat_PRIVATE_CHANNEL_DISCLOSURE`). Creating one calls `scopes.createWithDocument` once. The host checks every invite and creates the four scope rows, grants, and channel document in one transaction and under one page-write rate charge. The people dialog reads `scopes.listPrincipals` when it opens and lets managers add or remove people. Exact `{ _yay: null }` means the list is no longer readable; `_nay unavailable`, a rejected old-client promise, or malformed data is a visible retryable read failure. After an unavailable change, it reloads the current principals before showing access as current. Leave and Delete are in the private channel's row menu. Leave deletes the channel when that member is the last principal; both destructive dialogs freeze the principal count they showed and send it as `expectedPrincipalCount`. Exact-null count reads use the honest unknown-count copy and may continue without a count; unavailable or malformed reads keep the destructive action disabled until Retry gets an exact result. Only `_yay` proves the exact lifecycle success. A successful shared-scope Leave waits for the full `watchMine` list: absence settles `Left`, while a present scope whose `membershipRevision` is greater than the result proves that a later re-add won. The result stays pending while the watched target revision is the same or older, so a coalesced Leave plus re-add cannot hide a live channel. An `unavailable` result also waits for a later full list; if the scope is absent, the page gives a neutral action-not-confirmed message because absence proves only that this member lost access, not that everyone lost the channel. Chitchat replaces even a healthy scope watch after that uncertain result, because a failed write may leave membership unchanged and the old live query would not send the same value again. Exact proof then reads the channel and unwraps the principal Result: exact null settles departure or stops a re-add candidate, while unavailable or malformed results retry with bounded backoff. Private-create proof also stops on exact null with its exact key and fields locked for Retry or Cancel, while unavailable or malformed Results use the same bounded retry. The sidebar finds private channels through `scopes.watchMine` and then opens one ranged channels watch per scope, merged into one list with the public channels. It keeps the last full scope list when that watch dies and restarts only an `unavailable` death with bounded backoff; access, session, capacity, and invalid deaths stay with the host page. While that full list is live, each unavailable ranged watch also keeps its cached channel and cursor rows and restarts with bounded backoff. It filters cached rows against the full live scope list and keeps the selected scope inside the eight-watch budget. A departed row therefore leaves live without losing a selected draft during a harmless capacity reorder. Thread-only responsive CSS uses `:has(.thread)`, so a Threads result whose old root is not loaded cannot hide or collapse navigation when no thread panel exists. A polite announcement and visible focus repair handle a removed trigger, but a delayed archive or unarchive echo does not move focus after the member chose another live control. A re-add focus repair keeps the exact channel key, uses the visible thread-back control after a narrow resize, and falls back to the visible Channels toggle when a thread root or row action cannot take focus.
- Theme (since 0.1.7, on the raw scales since 0.6.2): `src/chitchat.css` declares one palette of `--cc-*` properties twice — `:root` for dark and `:root.light` for light — and no rule outside those two blocks writes a colour of its own. Ten of the properties read an app scale first (`var(--color-base-1-01, #0b0b0e)`, the same variable the app uses); the other 22 are Chitchat's own shades between the app's steps (the `chitchat.css` header comment still says "nineteen"; it is wrong and fix it at the next Chitchat release, because a comment edit rebuilds the dist and would need a republish). The page has no theme code: the SDK writes the scales onto the document element and toggles the app's `light` / `dark` class there, and `chitchat.css` reads both. A host that sends no theme leaves the properties unset and the stylesheet's dark block standing. `chitchat-css.test.ts` pins the ten reads and refuses any `--bonobo-` leftover.
- Chitchat tracks every top-level and reply append or retry at App level by channel. A request starts before the append promise can settle and ends only on a definite result. An `unavailable` result may hide a committed write, so the queue stays in flight and replays the exact client request id and payload with bounded backoff. The whole uncertain replay series has one App lifecycle count and one final local delivery. While the selected channel has any request in flight, controls and handlers refuse channel, view, or thread changes that would unmount the send queue, and Leave or Delete refuses before a scope mutation. A visible status and polite announcement explain the wait. A definite failure unlocks navigation but keeps the failed row, text, and Retry button in the still-mounted queue; manual Retry starts one new lifecycle with the same client request id. Send retry timers stop when their composer unmounts. Sends do not maintain channel unread stamps.
- Leave waits for the channel's in-flight sends to settle before changing a private scope. It does not flush or write an unread stamp; scoped append activity is already durable.
- Unreads, mentions, and the three views (since 0.3.0): the sidebar carries an Unreads/Threads/Activity view list above the channels (view keys `view:*`, which no channel key can collide with), and unread state is split by channel privacy because one mechanism cannot serve both. **Public** unread comes from one always-on `data.watchRecent({ collection: "messages", limit: 100, order: "desc" })` folded against a per-member cursor map — one OWNED doc in a `cursors` collection, caller key `me`, value `{ channels: { [channelKey]: lastReadMs } }` — so the horizon is the newest 100 public messages and the Unreads view says so in a note. **Private** unread never touches that map. `scopes.watchMine` is its durable source: accepted `messages` and `replies` appends advance their own sequence even when timestamps tie. Each member's read cursor is an OWNED `<channelKey>:read` doc in the `channels` collection INSIDE the scope range, riding the per-scope channels watch at zero extra slots. Its value is `{ at, activity: { messages, replies } }`: the two sequence values decide unread, while `at` is an observed server time used only for the New divider. Opening a private channel advances both sequences and the display timestamp through the observed activity. Cursor writes use compare-and-set and component-wise maxima across pending, stored, watched, and authenticated exact-read values. A conflict reads and validates the exact `<channelKey>:read:<userId>` document, then retries with bounded backoff; a live ranged watch may win first. This also covers a selected ninth scope after navigation returns the live-read budget to the stable first eight. Timers stop when the app unmounts or the private scope exits. Sends and Leave never write channel unread stamps. A `p/` key in the public cursor map would tell every member which private channels this member reads, so `app.test.tsx` holds a leak assertion on exactly that, and the fold skips `p/` keys by construction. Cursor-map writes are compare-and-set with per-key maxima merge on conflict (the watch doubles as the conflict-read). Mentions ride the message value (`mentions: string[]`, ids whose `@Name` is still in the text at send), are rendered by longest-name-first span matching, and count into amber badges — the amber (`oklch(0.617 0.15 52)`) is reserved for unread/mention emphasis and never selection. The composer @-menu (an Ariakit combobox since 0.5.0) reads `members.list` lazily on the first `@`: bounded paging of 10 pages × 100, with a complete ready roster cached per client for the page's life, self excluded, null names offered under the shared anonymous label. If any page fails, that roster attempt is incomplete and is not cached, so a later composer mount retries. A refusal is shown as one status line in the menu — `not_consented` gets the ask-an-admin copy. Ariakit-initiated dismissals clear the picker state through the store's `setOpen`, so Enter after an outside press sends instead of picking from an unmounted menu. The mention UI needs the `workspace.members.read` consent while everything else works without it. Slot arithmetic at the ceiling (since Chitchat 0.6.4 the cursors read runs on `client.convex` with `client.api.plugins_data.watch_documents` directly, so it spends no SDK slot): channels 1 + `watchMine` 1 + N scope watches + recent 1 = 3 + N on the rails, plus one open channel's messages window and three `watchChanges` feeds (4 more) = 7 + N ≤ 16. The page still watches at most 8 private scopes, which leaves one slot spare, and the sidebar says how many more are hidden. Server subscriptions at that worst case are unchanged, because the server holds the direct read too: rails 11 counted by the SDK + the direct cursors read + messages window 1–6 + 3 feeds = 16–21, under the 100-subscription backstop (16 × 6 = 96 is the honest max). The feed is what made the old companion windows and thread watch droppable — without that drop the page spent 31 server subscriptions (three grown companion windows plus a thread watch on top of the rails), which exceeded the then-24 ceiling. The current cap is 100; keep the change-feed design anyway. The Threads view opens its own `watchRecent` over `replies` only while mounted.

# Releases (SDK + Gallery)

Plugin runs keep their platform baseline of exact-source download, sibling Markdown writes, and
activities. Every staged write also reloads the live run, installation, source node, actor membership,
and the actor's `content.write` on that source in both the prepare and publish transactions. Removing
the actor or their source-file authority stops an in-flight output. The intrinsic read-only lock is a
second post-ACL gate: plugin output cannot write into a locked destination. An upload accepted before
its node locks still finishes and starts its `files.upload.completed` runs. Those runs do not bypass
locks on their output destinations. Lock refusals settle the plugin call with the existing `conflict`
code and zero output writes; see `../files-read-only/SKILL.md`.

`/api/v1/activities/start` consumes the run API call before a separate activity mutation writes the
activity. That mutation must recheck that the installation is still enabled on the same version and
tenant, that the actor still has an active workspace membership, and that the triggering file is
still active in that tenant. This closes uninstall, upgrade, disable, actor-removal, and source-archive
races between route authorization and the durable write.

Use the app workspace for app tests:

```powershell
vp env exec pnpm --dir packages/app exec vitest run --project convex convex/plugins.test.ts
vp env exec pnpm --dir packages/app exec vitest run --project src 'src/routes/w/$organizationName/$workspaceName/plugins/$pluginName_.pages.$pageId.test.tsx'
```

Gallery sits outside the root workspace, because no glob in `pnpm-workspace.yaml` matches `plugins/*`. The SDK does not: `packages/*` matches it, so it is a workspace member. Keep `--ignore-workspace` on both sets of commands anyway — for the Gallery it stops pnpm walking up to the root workspace, and for the SDK it stops a real member install from rewriting the shared `pnpm-lock.yaml`:

```powershell
vp env exec pnpm --dir plugins/bonobo-plugin-gallery --ignore-workspace run test:once
vp env exec pnpm --dir packages/bonobo-plugin-sdk --ignore-workspace run test:once
```
