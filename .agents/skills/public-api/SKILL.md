# Mental model

The public API serves external clients, scripts, and plugins. It includes Files, plugin data, and creator-private AI conversation reads. Every route is a Convex HTTP action with a typed entry in `api_schemas_Main` (`packages/app/shared/api-schemas.ts`). A route without a schema entry does not exist.

Keep AI conversations and human Messages in separate API names and scopes. AI reads use `/api/v1/ai-chat/threads/*` and `ai_chat:read`. Human channels and their reply threads have no public HTTP API yet; do not add a generic chat alias that mixes them.

A credential never expands its subject's access. Personal plugin Files access uses applied consent. Check the request's subject and target, not just its scope. A personal key acts as its user; a service-bound key acts as its account. AI conversations remain creator-private even when an owner or admin has broad Files access.

The HTTP wrappers are split by startup cost. `/api/v1/files/list` lives in `packages/app/convex/public_api_files_list_http.ts` and stays in the small static root graph because it is the hot plugin read path. The other `/api/v1` routes use small modules registered in `http.ts`, including `public_api_http_routes.ts` (the generic file routes), `public_api_plugin_files_http_routes.ts`, `public_api_service_uploads_http_routes.ts`, `plugins_data_http_routes.ts`, and `plugins_invoke_http_routes.ts`. Each route loads its heavy implementation (`public_api.ts` or `plugins_data_http.ts`) with a literal dynamic import only when that route runs. Shared Bearer-token authorization lives in `packages/app/convex/public_api_http_auth.ts`. Public scopes and the plugin token formats that principal resolution and HTTP authorization must agree on live in `packages/app/shared/public-api.ts`; one-consumer credential and grant details stay private to their owning Convex module.

Plugin UI documents and `/api/v1/*` share the Convex HTTP origin. Their iframe keeps that origin through `sandbox="allow-scripts allow-same-origin allow-forms allow-downloads"`, so the browser sends the existing JSON plus `Authorization` request directly without a CORS preflight. Do not add a `text/plain` token envelope or route calls through the host app. External browser callers on another origin still use normal CORS behavior.

`public_api_http_auth.ts` maps plugin-data and `backend:invoke` scopes to their app permission. Routes pass only their scope. File scopes map to `null`: every file read and write checks the actual target for the caller, so a guest (a member without workspace `content.read`) uses only what is shared with them, by exact path; a service account may hold only a file grant, so HTTP entry must not require a workspace-wide account grant. A personal plugin file request uses its exact pair's applied consent (see the access-control skill, "Personal plugin file grants"). Owner and account grants add no access. A folder a plugin creates is a regular folder. Upload-triggered runs keep their source/sibling ceiling. The plugin-data store keeps its separate actor and private-scope rules. Final file mutations recheck the original credential, membership, consent, target ACL for the request's subject, and current policy in one transaction.

HTML is an editable text type. New `.html` and `.htm` text writes use `text/html;charset=utf-8` and the `plain_text` shape. An explicit HTML upload uses the normal text conversion pipeline. Existing files keep their stored type and shape; a rename does not convert them. HTML download URLs remain attachments. Built-in Preview uses authorized app reads and does not add an HTTP route or grant a file access scope.

# Read-only and force

Read-only is one local boolean. It blocks ordinary content, metadata, and direct child-list changes. It does not change sharing. Keys need the new `files:read-only` scope for explicit set/clear, create-true, or force. Plugins need `workspace.files.manage-read-only`; old consent never grants it. Copy and Restore preserve a source flag without this extra grant, but that does not grant force on a destination. Final writes recheck current grants. Staged writes store force and the create flag. Existing request fingerprints include force only when true; false and omission keep the ordinary request identity. Switching to true with the same request ID conflicts. Exact committed replay, accepted upload completion and remint do not become new writes or targets because the flag changed later.

Optional top-level force is supported on write, write-many, edit, append, touch, mkdir, upload-urls, move, copy, delete, restore, plugin folder ensure, `plugin-archive`, and service create/delete/`archive-destination`. Each route keeps its own batch and error contract. There is no new agent force tool.

# Principals and scopes

`public_api_authorize_request(ctx, request, { requiredScope, allowedKinds, route })` resolves the Bearer token into one principal kind:

Public API scopes and app permissions are separate concepts and use separate values. API scopes use colon names such as `files:read`; app permissions use dot names such as `content.read`. Several file scopes can map to the same app permission, so do not make their values identical or pass the permission from each route.

Plugin credentials pin a `plugin_pair` subject. Files calls reach their exact
target check even with a narrow selection. Non-Files scope checks stay separate.
Missing or null pairs fail current authentication, including renew, seal and
token recovery. Old credentials never gain a current pair.
See [personal plugin file grants](../access-control/SKILL.md#personal-plugin-file-grants).

API key `lastUsedAt` is display data. It lives in its own table, `api_credentials_last_used` (one doc per key). `mark_credential_used` lives in `packages/app/convex/public_api_credential_usage.ts`, so this small write skips the file API's editor imports. It writes on first use, then at most once per minute, and never moves the time backward. It never writes the `api_credentials` doc, because every file publish reads that doc to check revocation, so parallel writes there would conflict. `api_credentials_list` shows the usage doc's time, or the old `api_credentials.lastUsedAt` when the key has no usage doc yet. Every request and final file mutation still checks live credentials and permissions.

- `user_api_key` (`pk_<keyId>.<secret>`): key minted on the API keys page by a signed-in Clerk user. `serviceAccountId: null` is a personal key. A bound key acts as the account: it uses only the account's file grants, the restricted-folder shares of its role, and its live account identity. The sponsor's own access does not count. It also lists the Trash and restores as the account (see "Trash list" and "Trash areas" below). Bound keys accept only `files:list`, `files:read`, `files:write`, `files:download`, `files:permissions`, and `files:read-only`. Personal keys also accept `files:publish`, `plugin_data:read`, and `plugin_data:write`. Binding requires current account-management permission and an active account in the same workspace. Rotation preserves that binding and revokes the original credential ID; a new token cannot revive a staged write from the old key.
- `public_api_grant` (64-hex, short-lived): accepts `files:list`, `files:read`, and `files:download`. Download scope allows the bounded byte route, never signed download URLs. An ordinary byte-enabled grant has its own 8 MiB read budget; other ordinary grants have zero. Code grants share one invocation budget across current and personal/home. Organization removal deletes the member's destination grants. Code grants also check their original chat membership lifetime, so re-invitation cannot revive a token for either root.
- `plugin_run` (`plr_...`) and `plugin_ui` (`plu_...`): plugin runtime tokens with their own constraints. A run writes editable workspace text next to its triggering upload, or on nodes with matching editable `plugin-name` metadata for an invoke run. It can download only its source upload. A run with the Mounts capability can also write its own staging trees through the separate Mounts API below. Both token kinds require their workspace doc to still exist with no `pluginDataPurgeStartedAt` fence, so phase-one tenant deletion and data reset revoke them before delayed plugin rows drain. Organization removal also deletes that member's plugin UI sessions. A `plu_` token is minted together with a plugin-session JWT that runs live Convex queries against the plugin-facing doors — the first step toward exposing Convex reactivity as a public API; both expire with the session. `POST /plugins-ui/session-jwt` (outside `/api/v1/*`, no `api_schemas_Main` entry) stays as a fallback that exchanges a live `plu_` token for that same JWT. The public API itself never verifies a JWT: `resolve_principal` reads the `plu_` bearer only. Contract: `../plugin-system/SKILL.md`; identity model: `../auth-system/SKILL.md`. Read "page" as "page or file view" everywhere this skill talks about a `plugin_ui` token: a plugin page and a plugin file view get their `plu_` token from the same table, `resolve_principal` looks a token up by its hash alone, and the principal it returns carries no frame kind at all. So every `plugin_ui` rule here is a rule for both frame kinds.
- `plugin_service` (`psg_...`, stored hashed in `plugin_service_grants`): a grant for an external service that acts for one installation. An outside server gets one by presenting a member's plugin frame token to `/api/v1/plugins/service-grants/exchange` together with the plugin's registered exchange secret (a publisher-managed row in `plugins_service_registrations`, compared by hash in constant time), and keeps it alive through the sibling `renew` route; both live in `packages/app/convex/plugins_service.ts` (see `../plugin-system/SKILL.md#service-grant-exchange`). It is bound to the installation rather than to a user session, so a worker can finish work the member started. Its `principalKey` is stable across token rotation, which is what makes it a durable producer identity for versioned documents and reservations. Grants come in two phases. An `interactive` grant is what the exchange mints: one working day, renewable, carrying the registration's scopes minus `files:write` (a file scope only means anything sealed). A `processing` grant comes only from `/api/v1/plugins/service-grants/seal-processing`, which trades a live interactive grant for a new grant sealed to one exact destination path prefix, carrying exactly the registered scopes, expiring six days after the seal; renewal rotates its token but never moves that deadline, and a processing grant cannot seal again. Both phases need live membership. Files uses the pair's applied consent; non-Files calls keep their live human permission checks. Every call also rechecks that the installation is enabled, its workspace exists without the purge fence, and the installation still accepts the matching capabilities, so uninstalling, tenant deletion, or removing a capability revokes it. `resolve_principal` narrows scopes by the installation's live capabilities and drops `files:write` whenever `destinationPathPrefix` is null.

Scope names: `files:list`, `files:read`, `files:write`, `files:download`, `files:permissions`, `files:publish`, `ai_chat:read`, `volumes:write`, `runs:follow_up`, `secrets:read`, `outbound:fetch`, `activities:write`, `plugin_data:read`, `plugin_data:write`, `backend:invoke`. The six file scopes, two plugin-data scopes, and `ai_chat:read` are available for personal keys. `files:publish` and `ai_chat:read` start unchecked and are never granted to service-bound keys, short grants, or plugin tokens. Existing keys keep their scopes. The remaining scopes belong to plugin tokens only; `backend:invoke` exists only on a `plugin_ui` token whose installation accepted `plugin.backend.invoke`.

`volumes:write` belongs only to a plugin run. It requires both saved and current acceptance of
`workspace.volumes.write`, plus the actor's current management of that exact installation.
The generic scope map uses `null`; every volume transaction repeats the exact installation check.
Ordinary API keys, frame tokens and service grants cannot use the Mounts write routes.

Plugin runs, service grants, and UI sessions pin their account when minted. Each use requires that active account to still match the installation and its trusted publisher/source binding. Rebinding refuses old credentials instead of moving them to the new account. Personal credentials also pin `filePairId`: Files uses its applied consent, with live tenant and membership-lifetime checks. Account grants never expand that consent. Downloads repeat the check after signing, before returning URLs. File grants never grant private plugin-data access. Plugin-session JWT store calls validate the same live account pin and keep the existing member/store rules; they are not file-write credentials.

File stages and service upload targets copy the credential's pair ID. Completion checks that
same pin. Missing or null plugin pairs grant no live authority. Retained run, grant and upload
history stores explicit null when no pair was accepted. UI sessions always store a pair ID.
Service exchange always checks its source credential and current service secret, even without
`requestId`; that ID controls retry receipts only. Invoke mint also checks its source frame.

Routes restrict kinds with `allowedKinds`; a valid token of a disallowed kind gets 403. `write-many` and `upload-urls` are `user_api_key` only. `write` and `touch` also allow `plugin_run`, and `write` also allows a `plugin_service` grant: the route refuses any grant that is not sealed (`processing` phase) or whose path is not strictly inside its `destinationPathPrefix`, with 403 `Path is outside this grant's destination`. `read` and `list` allow `plugin_run` too — the scopes come from the installation's accepted `workspace.files.read`, and a personal run uses its pair's applied file consent (`principal.subject`). A selected folder does not cross a restricted boundary. `download-urls` allows the plugin kinds too. Ordinary service grants reach write, moving one file to Trash, and sealed uploads. Registered writer requests also reach the folder/access/inspection/generation contracts below with a current service secret. A `plugin_ui` token may read and list plugin documents but never write them — a page that needs to write goes through its own backend or a service grant. Three separate checks enforce that, and they are not redundant: `resolve_principal`'s `returns` validator makes `plugin_data:write` unrepresentable for a page token, every write route leaves `plugin_ui` out of `allowedKinds`, and `refuse_page_principal` refuses the kind inside the mutation itself. The in-transaction one is what a caller reaching the mutation directly, or one wrong edit to an `allowedKinds` list, still runs into. A page session can belong to an anonymous identity and is the first thing a scripting bug in a plugin reaches, so a write door there would turn one such bug into stored data that plugin backends later act on with their own secrets.

# Scheduled plugin API calls

A stored scheduled event uses its pinned user, direct consent grant, and membership lifetime.
Effective scopes intersect that grant with live accepted capabilities and current user access.
Scheduled runs get no baseline Files write/download or Activity opt-in. Files read/list responses
repeat consent, token, call, and actual target checks after I/O in
`public_api.validate_and_finish_scheduled_file_read`. That same transaction settles success.
KV operations keep their private-store checks. Mount writers repeat assignment checks before upload
and final publication and bill the current live owner. Secret/outbound calls also need exact
installation management; secret plaintext is checked after decrypt. See the scheduled plugin spec.

`POST /api/v1/plugin-runs/follow-up` needs `runs:follow_up` and a scheduled `plugin_run` token.
The body is `{ state: string }`: valid JSON text, at most 16 KiB. One outgoing state per run is allowed.
Only successful finish queues the child. A chain has at most 20 runs and 30 minutes. An authenticated
request past the run count returns 409 `chain_limit`. At the root deadline the token expires, so late
API requests return 401. Auth runs before chain-limit checks. Normal per-run call and token rules still apply.

# Routes

All routes are POST. Responses are JSON except the successful `files/read` response. Batch caps are tied to rate-bucket capacities — do not raise one without the other.

Every declared body object is `.strict()`, nested known objects too. An unknown field is 400 with the first problem only: `Unknown request field "expectedRevison" in "files.2". Remove it.` (`server_request_body_issue_message` in `server/server-utils.ts`). The message never echoes values or causes. `write`, `edit`, `append`, and `write-many` also add `errorCode: "invalid_input"`; the other routes answer `{ message }` only. Free-form payloads stay open: plugin document `value`, invoke `input`, and run-stream `messages`. `files/list` keeps the declared, ignored `scanLimit`, because Data Probe sends it.

Each public batch route states its commit rule. `write-many` checks the whole body first; then each file saves on its own, a failed file fails alone, and the response lists every item. Routes that promise one atomic batch keep that promise.

The helper filters stored scopes through current actor permissions. An empty list is valid. Account access is checked on each requested file, not inferred from this workspace-level answer.

`/api/v1/files/download-urls` accepts optional `download: boolean`. `true` signs an attachment

headers. Safe content types and encoded filenames stay unchanged. The flag grants no file access
and changes no scope, batch limit, TTL clamp, or before/after-signing authority check.

# AI conversation reads

`public_api_ai_chat_http_routes.ts` registers the two AI routes with a literal dynamic import of `public_api_ai_chat.ts`. Both require `user_api_key` with `serviceAccountId: null` and `ai_chat:read`. The scope maps to `null`, like current app AI reads: active guests may read their own conversation without workspace `content.read`. Every data query repeats live key/scope, user, membership, exact tenant, thread creator, delete/copy fences, and workspace purge checks. A cursor and each before/after-output check pin the original membership ID and nullable lifetime. Foreign and unavailable chats/outputs use the same 404. Owners cannot read another creator's thread.

`transcript` takes `{threadId,endMessageId?,cursor?}`, with nullable optional end/cursor, a streamed 32 KiB request cap, and a 16 KiB cursor cap. First response is a header with `{id,title,endMessageId}`. An empty chat ends there. Later responses contain one whole inline message or reply step, at most 8 MiB of encoded JSON including the cursor/envelope. Walk exact parents from the supplied end or first-page `newestNodeId`; never use the model summary, the UI downward walk, siblings, or a total-history cap. Copied replies keep their steps even with `runId: null`; detect inline parts by content shape.

Fragments keep message IDs, parent/client IDs, role, dates, status, version, metadata, step index/status, and saved parts. Messages and reply steps arrive newest first. Clients reverse message order and sort steps upward. Keep empty replies. `isDone` means root reached, not run finished. The saved view is not a frozen active-chat snapshot.

Use cursor purpose `ai_chat_transcript`. Bind its encryption scope to the known route/key/user/tenant/thread. Seal pinned end, original membership/lifetime, and message or exclusive-step position in the payload. Later message arrivals keep the selected branch. A reply version change while paging it returns 409 `transcript_changed`; a bad cursor or one from another key or thread returns 400 `invalid_cursor`. Restart rather than mix reply versions. Add `ai_chat:read` only to plugin call tracking's requested-scope validator so valid plugin tokens reach 403; leave plugin grant/schedule allowlists closed.

`tool-output/read` takes `{threadId,outputId,offset,limit?}`. Offset is a nonnegative safe integer; limit is 4–65,536 bytes and defaults to 65,536. Read only ready objects with a committed owner in the exact authorized chat. A branch copy can share the object, so its original thread ID is not authority. Validate exact R2 range/length, bound the streamed body, cancel it on completion/failure, and recheck key, original membership, thread and owner after I/O. Accept a 200 storage response only for a bounded whole-object read. Return `{text,offset,nextOffset,totalBytes}` on whole UTF-8 boundaries; pages advance before EOF. EOF is empty text; offset past EOF is 400. Storage failure is plain 503 without keys, URLs, or provider details.

Both routes use existing auth/principal rate buckets, one request per page, and `Cache-Control: no-store` on successes and errors. Common statuses are 400 bad input/cursor, 401 dead credential/membership, 403 scope/kind/binding, 404 private/unavailable target, 409 changed reply, 429 rate limit, and 503 output storage failure. Preserve historical text and metadata; shape quotes and `data-ui-context` screen info like the UI and clear unreadable file pointers. Other file references grant no fresh file access. Do not resolve fresh names, bytes, or signed URLs. No in-app transcript tool, short AI grant, or gateway expansion is added.

## Organize routes

Follow the [Files delete words](../files-explorer-tree/SKILL.md#trash-view-and-delete-permanently).
The `delete` routes move saved items to Trash. Route names and response fields keep their current names.

Saved warnings, refusals, and errors returned by `jobs/get` follow the
[Activity history rule](../activities/SKILL.md#historical-messages-and-live-data) for Move, Copy,
Trash, Restore, and every other file operation. They may keep old paths after access changes.
The job reader's checks and live item-path checks still apply.

`stat`, `mkdir`, `delete`, `restore`, `trash/list`, `trash/areas`, `move`, `copy`, and `jobs/get` live in `packages/app/convex/public_api_files_organize.ts`, with routes in `public_api_files_organize_http_routes.ts`. Trash list and areas also allow personal plugin runs and frames. The other routes take `allowedKinds: ["user_api_key"]`. They use the "Locked, not hidden" rules (access-control skill): each path is resolved with `files_db_get_path_access`, so a locked path, or any path below a locked folder, answers "Permission denied", never "Not found". Each path costs a few index reads that grow with its depth, never with folder size.

- `mkdir` runs in one mutation. An existing folder answers `created: false`, also a locked one in a readable folder, because it already shows there as a locked row. It revalidates the key once, then creates each missing path from its deepest existing folder with `files_nodes_db_create_node_recursively_at_path`, so a guest makes folders only inside a folder shared with them. Any refusal throws `convex_error` with `{ path, status }`, so the whole batch rolls back, and the HTTP action answers that status. It charges `public_api_files_write_bulk` with `count: paths.length` (at most 20, under the 25-per-charge shard rule above).
- `delete` from a key bound to a service account acts as the account, in the request and at every job step: `public_api_credentials_db_get_write_context` reads the account from the key the job stores, because a key never changes its account. The person behind the key still owns the job, its Activity, and its rate buckets. It charges one `public_api_files_write_bulk` token per call, and the person's `files_tree_write` bucket like Move to Trash in the app. Found paths go to `files_nodes_db_archive_named_nodes`, the same code the app's `archive_nodes` uses, with the key's id. The job stores it in `files_archive_runs.credentialId`. Each background step (`files_archive_runs_db_advance`) checks that key: not revoked, same person, still `files:write`, and its service account (if any) still active. A forced job also requires `files:read-only`. Losing the key or a required scope stops an ordinary job's check or a forced job's remaining work, with the message "The API key that started this job was revoked or lost a required file scope." An ordinary delete that already passed its check finishes, like in the app. The app's job card does not check the key, so the person still sees the job after a revoke.
- `stat`, `mkdir`, `delete`, `restore`, `move`, and `copy` count their paths (or `restore` nodes) in the route, not in the body schema. So a longer list answers 400 with the limit and the fix, for example `Restore at most 100 items at once. Split the list into several calls.`, instead of `Request body validation failed`.
- `delete` takes at most 200 paths. Each path costs about 11 database calls for a member (path lookup, access check, and Trash helper), and Convex allows 4,096 per transaction. A test measures this at the limit; 500 paths needed 5,518.
- When every found item is refused before a job starts, `files_nodes_db_archive_named_nodes` answers one general message, and its `_nay.data.refusedItems` keeps each item's own reason. An ordinary job's check walk does the same when it refuses every named item inside the request, for example each folder holds a restricted folder the key cannot change. `delete` uses that list, so each path keeps its own reason whatever the other paths are. An ordinary move to Trash writes nothing before its check passes, then finishes its apply. It does not repeat flag or ACL checks during that later stamp walk, so a change after the check may not stop it. A 429 from the `files_tree_write` bucket carries `retryAfterMs`.
- Explicit `force:true` moves allowed children to Trash before their parent and checks current authority at every step. Force skips only Read-only, not access checks. A denied branch and its ancestors stay active; allowed siblings remain in Trash. Stop or loss of membership, the key, or a required scope stops new work and keeps completed changes. See the [trash rules](../files-read-only/SKILL.md#trash-and-restore).
- `restore` brings back each selected item and the items inside it that were moved to Trash with it; see [Trash and Restore](../files-read-only/SKILL.md#trash-and-restore). Each delete id has one job. A refusal reports every original path or node selected from that delete, including a covered child. Other deletes still start. Retries keep the original body and answer.
- Each `restore` path is resolved with `by_organization_workspace_path_archiveOperation`, taking 2 trashed nodes at that exact path. None: the answer follows `files_db_get_path_access`, so a locked place stays "Permission denied"; an active item is `Not in the Trash`, nothing is `Not found`. A trashed node the key cannot read is "Permission denied", checked before the next rule, so a locked path does not tell how many items it has. Two trashed nodes (the path was deleted more than once) are refused with "Several deleted items have this path. Find the one you want in files/trash/list and restore it by nodes." Then each node needs `content.write`, like `unarchive_nodes`.
- `restore` sets the clash choice up front: `onConflict` is `keep_both` (default) or `skip`, stored as `applyToRemaining` for files and folders. An API job never waits for a choice: where the app would ask (Keep both found no free name), `db_land_node` fails the job with the reason. Nobody sees the clashes of an API job, so `db_land_node` writes one `files_archive_run_items` row for each item it renames or skips (`newPath: null` for a skip). App jobs write none. History cleanup deletes the rows with the run, 50 per call. `restore` charges the same buckets as `delete`.
- `restore` from a key bound to a service account acts as the account, like `delete`: the request checks (read and `content.write` on each selected item) and every job step use the write context from the key. That includes where an item lands: write on the folder it lands in or the folders the job creates, Read-only there, and Can manage on the restricted folder it leaves (`authorize_leaving_restricted_scope`). The landing rules are the app's Restore rules, only checked as the account (decided 2026-11-01). The person still owns the job, its Activity, and its rate buckets. A Replace check (`db_can_replace`) still uses the person, because only the app's clash question offers Replace.
- `restore` keeps its jobs even when they end inside the request, so the last job's `files_archive_runs.apiRequest` can hold the request id. The jobs run one after another, so the last one ends last and history cleanup deletes it last. It holds the request id (`api:<credentialId>:<requestId>`, index `by_user_workspace_apiRequest`), `inputHash` (SHA-256 of the paths or nodes, onConflict, and `force` only when true; a nodes request adds a "nodes" tag, so a paths request and a nodes request never share a hash), the items refused at the start, and every job's Activity id. A retry is looked up first, because restored paths are no longer trashed, and a late retry must not restore a later delete of the same path. A different body answers 409. The answer is `{ jobIds, isDone, refused }`. A job that stops partway inside the request ("Stopped partway") is in `jobIds` too, because it keeps what it restored: `files_archive_runs_db_start` returns its ids and `isDone` in `_nay.data`. Such a job can still be `stopping` while it gives Trash entries to the items left in Trash, so `isDone` can be false. The next job of the request waits for it. Each step checks the key like for `delete`, but a restore stops even in its apply phase.
- `restore` takes either `paths` or `nodes`, never both. A node is `{ nodeId, archiveOperationId }` from `files/trash/list`, so a caller can pick one of several deleted items at one path. A node is read where the saved view shows it (`files_saved_placement_db_get_node`), like `files/trash/list`, so during a published Move it has its new place and Trash stamp. A path is resolved on the node docs, as before. Each node is checked in this order: it exists in the workspace (else `Not found`), the key can read it (else `Permission denied`), its `archiveOperationId` still matches (else "This Trash item changed. List the Trash and pick it again."), then `content.write`. The first two refusals have `path: null`, so a locked item does not tell whether it changed. A node refusal is `{ nodeId, path, message }`; a path refusal stays `{ path, message }`. A duplicate `nodeId` answers 400 `Duplicate node in batch`.
- `dryRun: true` runs the real restore and undoes it. `preview_restore` calls `restore_items` with `requestId: null` through `ctx.runMutation`, reads each job with `get_job`, then throws a `convex_error` with `data.kind: "restore_preview"`. The throw rolls back every write of the mutation: files, jobs, Activity, and scheduled steps. The HTTP action catches only that marker and answers `{ dryRun: true, complete, refused, jobs }`. Each job has the `jobs/get` fields without `jobId` and `refusedCursor`, plus `hasMoreItems`, which is true when the job renamed or skipped more items than one page holds. Only the first step of each job runs in the request, so a big delete or a job that waits for another one is not finished: then `complete` is false and its later results are unknown. A dry run takes no `requestId` (400), and a real restore requires one. The preview charges the `public_api_files_write_bulk` token. The `files_tree_write` check still runs and can answer 429, but its charge rolls back with the rest.
- `move` and `copy` start one `files_transfer_runs` job through `files_transfer_db_start_for_api`. Its origin is `{ kind: "api", credentialId, inputHash, refused }`. The helper starts and seals the selection in the same mutation, so at most `files_TRANSFER_SELECTION_PAGE_SIZE` (100) sources fit. A service-account key acts as the account at every step, like `delete`: a move or copy reads, writes, and leaves restricted folders only where the account's own grants allow.
- `to` follows the agent's `mv` and `cp`. An existing folder takes the sources inside it. Otherwise one source gets `to` as its new path. A `to` that ends with `/` must be an existing folder. A `from` path that ends with `/` must be a folder; a file there is refused alone with `Not a folder`. A new name must be clean (`public_api_get_invalid_name_message`), because the API never renames on its own.
- Unlike the agent's `cp`, a copy makes no missing parent folder. The engine makes missing parents only as private drafts, and a saved copy plans its top items into `targetParent`. So the folder above `to` must exist (409), and the client runs `mkdir` first.
- The conflict policies match the agent: copy uses `{ file: onConflict, folder: "merge" }`, and move uses `{ file: onConflict, folder: skip ? "skip" : "error" }`. Nobody can answer a question for an API job, so `db_pause_item` stops an API run instead of waiting.
- Each call charges one `public_api_files_write_bulk` token. `db_start` also charges `files_tree_write`, and that 429 has no `retryAfterMs`. A `busy` start answers 409 without the other job's ids.
- The request id is `api:<credentialId>:<requestId>` in `by_user_workspace_request`. A retry is looked up before the paths are resolved, because after a finished move the `from` paths are gone. `inputHash` (SHA-256 of kind, from, to, and onConflict) tells a retry from a reuse. A different body answers 409.
- The key must stay live at every step, like for `delete`. `db_get_run_memberships` checks it for transfer steps; a copy also needs `files:read` and `files:download`. `files_move_cohorts` `db_parent_running` checks it for each Move step. A move that is already published finishes.
- An API move adds the key's scopes on top of the app rule. `files_move_cohorts` `db_headers` checks each selected item; descendants inherit from it. A move into, out of, or between restricted areas needs `files:permissions`, because each restricted area has its own people. So does joining a new Add people chain; the check reuses `access_control_db_extended_chain_allows` on the old place. A move never makes anything public, so it needs no `files:publish`. In the app, write on the destination is enough.
- Such a scope refusal fails only that item. `settle_cohort` marks the item `failed` with the message, and the other items go on, like in `delete`.
- Copy into a shared folder needs no extra scope. A copy starts not public. It reads and writes bytes, so it needs `files:read` and `files:download`, and a key with those could download and upload the same file.
- `move` takes at most 100 paths. 100 paths as a member cost about 650 database calls. A test measures it at the limit.
- `jobs/get` answers only for a job whose `credentialId`, person, and workspace match the caller, so a rotated key cannot read the old key's jobs. For a Trash job it names a refused item's path only while the caller can still read it, using the service account's own access for a bound key. The renamed and skipped items of a restore job keep the paths the job saw when it ran, like a transfer job. A restore job answers `kind: "restore"`, and its last job also lists the items the request refused at the start: `{ path, message }` for a path, `{ nodeId, path, message }` for a node. A stopped restore may name one unfinished item under its selected roots at their current paths, only while the key can read it. Other selected roots may need separate restores. Successful jobs do not look for unfinished items. See [Trash and Restore](../files-read-only/SKILL.md#trash-and-restore). A transfer job keeps the paths it saw when it ran, like the agent's `list_denied_for_agent`.
- For a transfer job, `jobs/get` pages refused items 100 at a time. First come failed items (`by_run_state_order`), then items skipped as permission denied (`by_run_skipReason_order`). The cursor is `failed:<order>` or `denied:<order>`. The paths refused at the start come on the first page only. A restore job pages its `files_archive_run_items` rows the same way, 100 at a time by `order` (`by_run_order`), with the cursor `items:<order>`: a skipped item goes in `refused`, a renamed one in `renamed` with its `newPath`. `path` is the item's path when it was deleted; a skipped item keeps it in the Trash, so a later restore of that path finds it. Move and copy answer `renamed: []`. The `files/restore` answer names none of these items: a retry must answer the same, and the jobs that go on in the background can rename many items. Jobs are deleted 7 days after they end (activities skill), and then it answers 404.
- A forced delete also pages `files_archive_run_items` through `by_run_order`, 100 at a time with `items:<order>`. Its `force_archive` rows go in `refused`, including folders kept because children remain. Each page checks current read access before returning the current path. An unreadable item stays in the page as `{path:null,message:"Permission denied"}`; it is not hidden or named from history. Keep following `refusedCursor` until null to read every outcome.

## Trash list

`files/trash/list` takes `{ areaNodeId?, folderNodeId?, cursor?, limit? }` (limit 1–100, default 100), with at most one of `areaNodeId` and `folderNodeId`. An area is the open part of the workspace (`areaNodeId` null or missing) or one restricted folder. A folder (`folderNodeId`) lists the items in Trash directly inside it; see "Folder mode" below. Each item has `path`, `name`, `kind`, `nodeId`, `contentType`, `updatedAt`, `size`, `locked`, `archiveOperationId`, `operationAt`, `changedBy`, and `top`. Items come newest delete first. Inside one delete they come in reverse `treePath` order, then newest doc first. The last page has `cursor: null`.

- It lists every item in Trash, not only the top items of the app's Trash view. `top` is true when the item's parent is the root, active, or in another delete: those are the items the app's Trash view shows.
- `archiveOperationId` groups items from one delete. Restore uses it only inside each selected item's subtree. A saved node id and operation id still need the caller's current access checks. They do not grant access by themselves.
- `operationAt` is the time inside the archive operation id (`files_archive_operation_id_time`). It is not stored separately. `changedBy` is the item's `updatedBy`, the app's "Changed by": usually who deleted it, but after a restore with Skip, who restored it, because Skip puts the item in a new delete. A locked item has `changedBy: null`.
- `path` is the item's current path. A rename while the item is in Trash changes it, like any other item; the Trash does not remember the path at delete time. Decided: do not store who deleted an item, when, or from where. `changedBy` and `operationAt` stay the close values above. (Optional later: store `deletedBy` and `deletedAt` at delete time, which needs a migrate-or-erase choice for items already in Trash.)
- A restricted folder lists in the area of its parent, locked when the key cannot open it. Its contents list only in its own area. An area the key cannot open answers 403, a missing one 404, and a node that is not a restricted folder 400.
- Two existing index ranges serve an area, so no index was added: `by_org_ws_scope_archive_treePath` (the area's own items) and `by_org_ws_parentScope_archive_treePath` (restricted folders whose parent is in the area). During a Move, the Move view's `by_view_scope_archive_tree` and `by_view_parentScope_archive_tree` are merged in, like `files_saved_list_page`. The ranges start above `archiveOperationId: null`, so active items are never read. Ties use `_creationTime` and `_id` (or `nodeCreationTime` and `nodeId` in the Move view), so equal paths in one delete never skip a doc.
- The docs dropped after the range are bounded: the "items" range drops the area's own folder, and the "folders" range drops a former restricted folder, which keeps `parentScopeNodeId` only while its scope job runs. Each item costs one parent read for `top`.
- Callers: personal keys, keys bound to a service account, and `plugin_run` and `plugin_ui` tokens. Plugins need `workspace.files.read`; scheduled runs get 403 `Scheduled plugin runs cannot use Trash yet.`. Service grants are refused.
- The open area needs read at the workspace root as the caller's subject, and a restricted area needs read on that folder. An account with only folder grants gets 403 for the open area. A personal plugin needs applied Whole workspace View or Edit consent to open it. A guest (a person without workspace `content.read`) gets 403 in every mode, like the app. This is a route gate for plugins, not a second human check on each selected file. An account-bound key uses the account; its sponsor's access does not count.
- `changedBy` is shown to every caller, including service-bound keys and plugins, like the app's "Changed by" column. Decided (user, 2026-11-01): do not hide it. Software then sees a person's user id, and for a delete made with a service-bound key it names the key's person, not the account. Do not "fix" this by hiding it.

### Folder mode

`folderNodeId` lists the items in Trash whose parent is that folder, so a caller that can open a folder but not its area still reaches its Trash. The folder may be live or in Trash itself, so a client can walk into a deleted folder. The subject must read the folder (else 403), a missing one answers 404, and a file 400 `folderNodeId must name a folder.`. A guest gets 403.

- One index range serves it: `by_organization_workspace_parent_archiveOperation_name` (`parentId` = the folder, `archiveOperationId` above null), and during a Move the Move view's `by_view_parent_archive_name`. Every row read is returned, open or locked, so a page costs the same in a folder of any size.
- Order: newest delete first, then name descending, then newest doc first. The cursor key is (delete id, name, creation time, id); in area mode the same key holds `treePath` instead of the name (`treePathOrName`). The cursor scope binds `folderNodeId`, so a cursor works only for its folder.
- `top` is true when the item's delete differs from the folder's: a live folder, or a folder deleted by another delete.
- A caller whose only grant is on a folder that is itself in Trash lists what is inside it here, but not the folder itself (its row is in the parent folder or area). It restores the folder by the `nodeId` and `archiveOperationId` it saved before, like a file-only grant (decided: option A, no lookup route).
- Plugins may use this mode for an ordinary or restricted selected folder, including one in Trash. A file-only consent adds no parent access or Trash area (option A). Plugin Restore is still closed; it needs a separate job contract.
- The cursor is sealed with purpose `files_trash_list`. Its scope binds the key, subject, membership, area, and saved sources. A bad, empty, or stale cursor, or a Move that started or ended during the page, answers 400 "This Trash cursor changed. Start a new page." with `errorCode: "invalid_cursor"`.

## Trash areas

`files/trash/areas` takes `{ cursor?, limit? }` (limit 1–100, default 100) and answers `{ areas: [{ areaNodeId, path }], cursor, isDone }`. It gives the `areaNodeId` values for `files/trash/list`, like the app's area picker. For keys, the first page starts with the open part of the workspace (`areaNodeId: null`, `path: "/"`) when allowed, which counts toward `limit`. Then come the active restricted folders the key can open, by `treePath`.

- It reads the same streams as `files_tree.list_archive_areas`, merged on the server (`list_trash_areas_page` in `public_api_files_organize.ts`). The owner reads every restricted folder (`by_archive_restricted_kind_tree`). A member reads share rows by principal on `by_org_ws_principal_restricted_kind_archive_treePath`: their own shares, two roles, and everyone. The index has `kind`, so a read never touches a restricted file. Each stream seeks from the last `(treePath, nodeId)`, during a Move in both saved views, like `files_saved_list_page`.
- Each row checks its node again (an active restricted folder of the workspace) and the key's read access. A folder in several streams is listed once.
- Callers: personal keys and keys bound to a service account. A guest gets 403, also with `limit: 1`. The open area is listed only when the subject can open the workspace root (`files_nodes.get_path_access` for `/`), so an account with only folder grants gets its restricted folders, or an empty list. An account reads its own share rows (`service_account:<id>`) and its role's (`role:<role>`), never the workspace or plugin-grant principals, which do not reach an account. The owner shortcut (read every restricted folder) is for the owner as a person only: a key bound to an account the owner sponsors reads the account's shares. The account can open every folder its share rows name, so a page drops no row for access.
- Personal plugin runs and frames use a separate page of `plugins_file_consents.by_pair_areaEligible(pairId, true)`. Every indexed doc is returned in consent order, with no path sort or current-human filter. Applied Whole workspace View or Edit returns `{ areaNodeId: null, path: "/" }` in that same page; `/` need not come first. Saved targets use their current path read by node ID. The [consent worker](../access-control/SKILL.md#personal-plugin-file-grants) marks workspace consent and active restricted folders as eligible. A folder that later becomes ordinary or enters Trash may stay listed until that worker reaches it. Use `folderNodeId` for an ordinary folder or a folder selected while already in Trash; `areaNodeId` still means a restricted area. Eligibility changes with applied consent, so lists follow the same gradual access rule as reads and writes.
- The cursor is sealed with purpose `files_trash_areas`. Its scope binds the key, subject, membership, and saved sources. A bad, empty, or stale cursor, or a Move that started or ended during the page, answers 400 with `errorCode: "invalid_cursor"`. This also covers a stream read that finds the Move view changed.

## External plugin identity and access

`plugins_service_access_http_routes.ts` registers four server contracts. Identity exchange takes
`{exchangeId,requestedExpiresAt}`, the current `plu_` bearer, and the registered service-secret
header. It returns only a signed ES256 JWT. Its issuer is `<Bonobo Senate HTTP origin>/plugins-services`;
audience is `bonobo-plugin:<registered plugin name>`. The installation, version, account, session,
user, membership lifetime, required revision, and expiry all come from current Bonobo Senate authority.
Expiry is capped by the requested deadline, page expiry, and validation time plus 30 seconds.
The page's original personal pair must still match its membership lifetime. A
missing or stale pair is refused before any connection or lifetime write.

`/api/v1/plugins/members/list` takes `{installationId,cursor,startRevision}` and returns at most 50
member facts. `/api/v1/plugins/access/changes` takes `{installationId,afterRevision,limit}` (1–100)
and returns ordered access events with continuation revisions. The page holds only this
installation's events: its own installation, workspace, organization, plugin, and service account
scopes, each read from its own `by_scopeKey_revision` range. Revisions have gaps. `continueRevision`
promises that every event of the installation up to it is in the page. Both use the service-secret header
and an existing connection pinned by a valid page exchange. They require declared and accepted
`plugin.service.connect` and `workspace.members.read`. Registration may have `scopes: []`; identity
does not grant file or plugin-data access. A secret alone cannot attach to a workspace or refresh
retired registration/version/account pins.

These routes return `Cache-Control: no-store`. Bad credentials use the failed-auth rate bucket;
authenticated member/change reads also use the principal bucket. Feed docs are deleted after 30
days, and only after the notice dispatcher passed them. A cursor older than retention returns
`410 { code: "snapshot_required" }` when this installation had a deleted change. When none of its
scope heads moved after the cursor, it gets an empty page that skips to the head instead. A removed
installation returns terminal access information only. The owning backend must enforce lease expiry
on live queries as well as new calls.

`POST /api/v1/plugins/service-events/key` takes `{ pluginName }` and only the service-secret header.
It returns `{ key, createdAt }`, the `whsec_` key that signs `workspace.access.changed` notices, with
`Cache-Control: no-store`. A wrong secret answers 401. It uses the principal bucket, keyed by the
registration. Bonobo Senate calls no product-specific access webhooks: the one push is the general
signed notice in `../plugin-system/SKILL.md#access-change-notices-workspaceaccesschanged`.
See the [auth spec](../auth-system/SKILL.md#identity-for-external-plugin-backends).

Service-grant exchange, renew, seal-processing, verify-live, and saved-response recovery use
`/api/v1/plugins/service-grants/*`. Their existing credential, scope, and destination rules remain
separate from the short identity lease. The generated SDK exports all these public contracts.

## Plugin document store routes

The nine `/api/v1/plugin-data/*` routes are registered in `plugins_data_http_routes.ts` and implemented in `plugins_data_http.ts`. The store itself and its limits are documented in `../plugin-system/SKILL.md`.

| Route                                     | Scope               | Kinds                                                       |
| ----------------------------------------- | ------------------- | ----------------------------------------------------------- |
| `/api/v1/plugin-data/read`                | `plugin_data:read`  | `user_api_key`, `plugin_run`, `plugin_ui`, `plugin_service` |
| `/api/v1/plugin-data/list`                | `plugin_data:read`  | same as read                                                |
| `/api/v1/plugin-data/write`               | `plugin_data:write` | `user_api_key`, `plugin_run`, `plugin_service`              |
| `/api/v1/plugin-data/write-batch`         | `plugin_data:write` | same as write; up to 50 documents                           |
| `/api/v1/plugin-data/delete`              | `plugin_data:write` | same as write                                               |
| `/api/v1/plugin-data/write-versioned`     | `plugin_data:write` | `plugin_service` only                                       |
| `/api/v1/plugin-data/delete-versioned`    | `plugin_data:write` | `plugin_service` only                                       |
| `/api/v1/plugin-data/reserve`             | `plugin_data:write` | `plugin_service` only                                       |
| `/api/v1/plugin-data/release-reservation` | `plugin_data:write` | `plugin_service` only                                       |

**Private scopes apply to these routes too.** `read` and `list` never return a document inside a plugin scope the actor user has not proved a grant on: `read` answers the document as absent and `list` answers an empty page. That is on purpose — a refusal that said "you may not see this" would tell the caller a private channel exists. A `list` with no `keyPrefix` reads only the public half of the collection, and it does so as an index equality on the absent scope, not as a filter after the read, so `isDone` and the page size stay honest. The write routes refuse a write landing inside a scope the actor cannot write. See "Private scopes" in `../plugin-system/SKILL.md`.

`list` also takes an optional `keyPrefix` (printable ASCII `0x21`-`0x7E`, same validator the user-write door uses) that narrows the page to keys under that prefix as an index range; an invalid prefix answers 400. `read` and `list` responses carry `createdBy`, `updatedBy`, `ownership`, `createdAt`, and `revision` alongside the value. Member-initiated writes do not have an HTTP route at all: the plugin frame calls the `plugins_data.user_*` public mutations on its own Convex client, authenticated with its plugin-session JWT — see `../plugin-system/SKILL.md#plugin-document-store`. Both frame kinds reach those mutations. Only a file-view session sets `fileNodeId`, and `db_authorize_page_write` never reads that field, so a file view writes there exactly as a page does; the door is named for pages only because pages shipped first. For live reads, frames subscribe to `plugins_data.watch_documents` the same way instead of polling these routes; `list` remains the non-reactive deep-history path for a frame that needs documents beyond the SDK window manager's 600-doc ceiling.

## Reading deep history from `list`

`list` also takes two optional bounds, `keyStartExclusive` and `keyEndInclusive`. Both are keys and follow the key validator. They ride the index as a range, never a filter after the read, so every page inside a narrowed range is still full.

Inside a range you may continue with either the response `cursor` or a **fencepost**: the last key of the page you just read, sent as the next request's `keyStartExclusive`. Prefer the fencepost when the continuation has to outlive the process — it is only a key, so it survives a restart, and a cursor does not.

A `cursor` is bound to the read it came from. The route hands back a token carrying the store cursor **and** the scope that produced it: the route path, the resolved installation, the collection, `keyPrefix`, `keyStartExclusive`, and `keyEndInclusive`. Every one of those is compared against the next request's body. A mismatch is **400** naming the field that changed — `cursor was issued for a different keyPrefix. Start a new page instead of reusing it.` — so a page-1 cursor replayed against a different range is refused instead of being read as a position inside the new range. A token that does not decode answers 400 `cursor is not a cursor this route issued`. `cursor: null` is a legal first page, so the check is on the type, not on truthiness.

The token is base64-encoded JSON, not a signature. It exists so a reused cursor fails loudly, not as a security boundary: the installation inside it is compared against the one resolved from the caller's own token, so rewriting it buys a caller nothing it could not ask for directly.

A full page inside a range answers a non-null token with `isDone: false`. A finished page answers `cursor: null` with `isDone: true`.

`isDone` stays the exhaustion signal inside a range. Read it, and do not infer the end of the data from a short page: a final page that happens to be exactly `limit` long is indistinguishable from a full one, and crossed bounds answer `documents: []` with `isDone: true` rather than an unfinished empty page a caller would follow forever.

`truncated` has different meanings across the platform. `plugins_data.watch_documents` sets it when the range holds more than `limit` documents. `download-urls` sets it when the caller's input array was clipped from more than 20 ids. The remedy differs from pagination: `truncated` says *narrow your range or send fewer inputs*; `isDone: false` says *send the cursor*. File reads use `X-File-Next-Cursor` for continuation and never return truncated success.

**HTTP counting is unsupported.** `list` returns full document bodies, so counting a full installation is around 100 requests on Free (10,000 slots at 100 per page, about 50 seconds at 120/min) and around 1,000 on a paid plan (100,000 slots, about 8 minutes) — and on the order of 20 MB of bodies to learn one number. Only the slot ceiling scales with the plan; the 16 MiB byte ceiling does not. There is no count endpoint, and paging is not a substitute for one. A surface that needs a number has to keep one itself.

A plugin token derives its installation from the token itself. A `user_api_key` has no installation of its own, so its request body names one; the store normalizes that id and answers `Not found` for anything outside the key's tenant. The id arrives as a plain string on purpose — a `v.id` argument validator throws on a malformed value, which at an HTTP boundary is a 500 instead of a refusal.

The HTTP adapter passes the original `credentialRef` to the final store query or mutation. That transaction re-reads the key, run, UI session, or service grant and checks its current tenant, actor, lifetime, scope or capability, and installation link as applicable. Plugin credentials must still carry the installation's live account pin and a valid original pair. Personal keys must still be unbound. Revocation, expiry, rebinding, or a changed installation can therefore refuse a request after its initial HTTP check. The store also checks current membership and installation consent; file grants do not grant access to plugin-store docs. A fresh service connection keeps the installation's producer key, so it can finish the same reservation and replay the same versioned write without another charge.

All nine bodies therefore accept the same optional `installationId`, including the four service-only ones. A user key that omits it gets 400 `installationId is required for an API key`, and any plugin token that sends it gets 400 `installationId is not allowed for this token`. The four service-only bodies need the field for the refusal alone: leaving it out of those validators would make Zod strip it before `to_store_principal` ever sees it, so a service naming another installation would be answered as if it had named nothing.

Every request body is strict, so unknown fields return 400. The raw JSON body limit is 64 KiB for every route except `write-batch`, which allows 4 MiB for up to 50 documents. The limit includes property names, JSON escapes, and whitespace. Crossing it returns 400 `Request body is too large`. The larger batch limit is transport headroom only; every canonical document value still has the 16 KiB store limit.

`value` on the three routes that carry one is checked for every shape Convex cannot store: a field name that starts with `$`, holds a non-printable-ASCII character, or is longer than 1024 characters; an object with more than 1024 fields; an array with more than 8192 items; and a value nested deeper than 15 levels (the document holds the value one level inside itself, and Convex's own ceiling is 16). Convex applies the name rules while serializing the mutation arguments and the other three while validating the document, and every one of them **throws** rather than returning a refusal, so without the check at the HTTP boundary a caller's bad value is a 500 with no message instead of a 400. The check walks nested objects and arrays, because the rules apply at every depth, and the depth limit is what bounds the walk.

Every string in a request body is also checked for an unpaired Unicode surrogate, which `JSON.parse` accepts and Convex refuses. Write the check as "does this code unit complete the pair", never as "is it outside the low-surrogate range": past the last character `charCodeAt` answers `NaN`, every comparison against `NaN` is false, and the second form therefore calls a string ending in a high surrogate well formed.

A refused body answers 400 with `{ message }` only, and no `errorCode`. For a body that does not match the route's schema, such as an unknown field, the message names the first problem, like the Files routes do (see the strict body rule under "Routes" above).

Store refusals map to status by the name the store tagged, so rewording a refusal cannot change its status: 409 for the whole conflict family (another writer, a live reservation, a replayed idempotency key with different fields, a replay of an already-released reservation, a deleted key, a revision out of order, a revision replayed with a different value) and 403 for all six storage-ceiling messages `check_capacity` can return (installation bytes, document slots, collections, and the same three per member). Only three untagged refusals map by message — 401 `Unauthenticated`, 403 `Permission denied`, 404 `Not found` — and everything else is 400. The ceilings answer 403 rather than 507 to match `/api/v1/files/upload-urls`, which already answers a full quota with 403.

`files/list` without `recursive` reads the folder's direct children through the parent indexes, in name order, so its cost does not grow with deeper items. `order: "desc"` reads the same index range backwards, so a folder of 500k children costs the same per page in both orders. The order is part of the sealed cursor scope; `"asc"` and no order are the same scope, so old cursors keep working. A recursive list with `order: "desc"` answers 400 with only a message (a plugin call records it as `invalid_input`), because the walk reads in path order only. With `recursive`, it walks the subtree in path order, one restricted area at a time ("The walk" in the access-control skill). `kind` and `extension` are index fields in both cases.

Without `recursive`, every child of the folder is listed, also the ones the caller cannot open: those come back with `locked: true` and `status: null` (`files_nodes.list_subtree` with `withLocked`). With `recursive`, a locked folder or file comes back once with `locked: true`, and nothing under a locked folder is read or listed. A caller who cannot open the workspace root (a guest with one shared folder, or an account with no grant) gets 403 `Permission denied: /` for a list of `/`, with or without `recursive`, like Bash `ls /`. They list a shared folder by its exact path.

`path` must name a folder the caller can read. `files_saved_list_page` (`server/files-saved-list.ts`) looks the folder up with `internal.files_nodes.get_by_path` on every page, saved only like the list, in parallel with the Move view and membership reads and before any list range:

- A missing or trashed folder answers 404 `{ "message": "Folder not found: <path>" }`.
- A locked folder or file (one the caller cannot open), and any path below a locked folder whether it exists or not, answers 403 `{ "message": "Permission denied: <path>" }`. The body is only `message`; the status is the signal. Locked, not hidden: see the access-control skill. After `get_by_path` answers `null`, `files_saved_list_page` asks `internal.files_nodes.get_path_access` and answers `_nay` `folder_locked` or `folder_unavailable`.
- A readable file answers 400 `Path must point to a folder: <path>`. A 404 would tell an agent that the path is free.
- `<path>` is the normalized path the server read, so a Git Bash rewrite like `/C:/Program Files/Git` is visible.
- `/`, `""`, and a missing `path` list the root. The root has no node, so the route only asks whether the caller can open it. A plugin needs applied Whole workspace consent. A file or folder choice gives no access above that item, so listing the root returns 403.
- A plugin run settles the call as failed with `not_found` or `invalid_input`. A code grant rechecks its source first, so a lost source still answers 404 `File unavailable`.
- The folder id is part of the cursor scope. A folder moved to Trash between pages answers 404 on the next page, and a new folder at the same path answers 400 `This list cursor changed. Start a new page.` with `errorCode: "invalid_cursor"`
- A folder that exists only as the code grant user's pending draft answers 404, because the lookup is saved only.
- A member who can read `/Clients/Acme` but not `/Clients` gets 403 for `/Clients`. List `/Clients/Acme` instead: a recursive list of `/` stops at the locked `/Clients`.
- A scheduled plugin run rechecks every listed node after I/O. A node it can no longer read answers 403 `Permission denied: <path>`; a moved or trashed one answers 404 `File unavailable`.

The last page answers `cursor: null` with `isDone: true`, like every other public paged route. The saved list returns an empty `continueCursor` when it is done; the HTTP route maps it to `null`. `isDone` is the stop rule.

The `cursor` is sealed with AES-256-GCM by `crypto_seal_cursor` in `server/crypto-utils.ts`. The last key a page read can be a doc the caller may not read, so the cursor must never show it as plain text. The cursor is `c1.` plus base64url of a 4-byte key id, a 12-byte nonce, and the ciphertext. The plaintext is padded to 1 KiB blocks, so the length hides the length of a path the caller may not read, up to about 900 bytes. The route refuses a cursor longer than 16384 characters with 400 `invalid_input`. The scope (caller, membership, request fields, Move view, folder id) is bound as additional data and is not stored in the cursor. A cursor that does not open answers 400 `{ message: "This list cursor changed. Start a new page.", errorCode: "invalid_cursor" }`: an edited or cut cursor, an old plain JSON cursor, a cursor from another caller or request, or one sealed with a retired secret. The Move view is in the scope too, so any Move, Rename, reviewed Save or Cut/Paste in the workspace ends every open list cursor, and a first page can get the same answer while a Move starts. A re-invite (new membership) does the same. This is a normal answer: clients match `errorCode`, not the message, and restart with `cursor: null`, skipping ids they already showed. No other 400 carries `errorCode`.

The key comes from the Convex env var `LIST_CURSOR_SECRET` (32 random bytes as hex). It is read at module load, so a deploy without it, or with a value shorter than 32 characters, fails. The same length rule applies to `LIST_CURSOR_SECRET_PREVIOUS` when it is set. To rotate it, move the old value to the optional `LIST_CURSOR_SECRET_PREVIOUS` and set a new `LIST_CURSOR_SECRET`. Remove the previous value once old cursors no longer matter. An empty page with `isDone: false` can still hint that docs the caller may not read come next.

`contentTypePrefixes` (1 to 8 values) reads index fields too, so it is not a scan. Each value is a whole family like `image/` or an exact type like `image/png`, trimmed and lowercased. A family matches the stored type's `contentTypeFamily` (`image`), and an exact type matches its `contentTypeEssence`, the type without parameters, so `image/png` matches a stored `image/png;charset=x`. A value is never a partial prefix: `image/p` means the exact type `image/p`. Each value reads its own index range in path order, one restricted area at a time: `by_org_ws_scope_archive_family_treePath` or `by_org_ws_scope_archive_essence_treePath` on saved nodes, and `by_view_scope_archive_family_tree` or `by_view_scope_archive_essence_tree` on the places of the visible Move view. The list action merges these streams by path. Every row it reads matches, so a page costs about `values × limit` rows, never more for folders full of other types. The route drops repeated values. When a family and one of its exact types are both listed, both streams read the file and the merge lists it once.

- `image`, `ima`, or `image/png;charset=utf-8` answers 400 `contentTypePrefixes takes whole families like "image/" or exact types like "image/png".`
- A type filter without `recursive: true`, or with `extension`, answers 400 `contentTypePrefixes needs recursive: true and no extension.` The type indexes cover whole subtrees only.
- With `kind: "folder"` the answer is an empty, done page: folders have no type.
- A file whose stored type does not parse never matches.
- `scanLimit` is accepted and ignored, so older plugin builds that still send it keep working.

`limit` counts returned items. A recursive page reads no row under a locked folder, so locked rows do not thin it. It can still be short with `isDone: false` when it meets many small restricted folders: one request makes at most 64 stream calls, then returns what it has. Follow the cursor. Without `recursive`, one request reads at most 8 × `limit` rows per stream. Every writer of `contentType` on `files_nodes` and `files_saved_places` sets both type fields with `files_content_type_index_fields` (`shared/files.ts`). A rename keeps the stored type, so it keeps the fields too.

## Service upload routes

The five `/api/v1/files/service-uploads/*` routes are registered in `public_api_service_uploads_http_routes.ts`, implemented in `public_api_service_uploads_http.ts`, with the storage mutations in `public_api_service_uploads.ts`. All are POST, scope `files:write`, `allowedKinds: ["plugin_service"]`, and the route refuses any grant whose phase is not `processing`. The mutations re-check the grant doc, installation state, capabilities (`plugin.service.connect` + `workspace.files.write`), actor liveness/membership, and trusted account binding inside the transaction.

Service grants use their pair's applied Can edit on the target or creation parent. They do not need human workspace `content.write`. A new Read-only target also requires `workspace.files.manage-read-only` and current Can edit.

| Route                                               | Body                                                     | Answer                                                                                                                        |
| --------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `/api/v1/files/service-uploads/create-target`       | `{ idempotencyKey, targetKey, path, contentType, size, readOnly, nonCollaborative }` | pending `{ state, path, nodeId, uploadUrl, headers, uploadUrlExpiresAt }` or committed `{ state, path, nodeId, actualBytes }` |
| `/api/v1/files/service-uploads/remint`              | `{ idempotencyKey, targetKey }`                          | same union: fresh attempt and URL while pending, or committed                                            |
| `/api/v1/files/service-uploads/finalize`            | `{ idempotencyKey, targetKey }`                          | `{ state: "pending" \| "committed" \| "released", path, nodeId, actualBytes \| null }`                                        |
| `/api/v1/files/service-uploads/delete`              | `{ idempotencyKey, targetKey }`                          | `{ state: "deleted", paths }`                                                                                                |
| `/api/v1/files/service-uploads/archive-destination` | `{requestId, previousRequestId?, force?}` | `{requestId, archivedNodes, complete, refused:[{path,message}]}` |

Semantics that must not drift:

- `idempotencyKey` names one upload run (the meeting); `targetKey` names one file inside it. For create, remint, and finalize, the pair is the target's identity (`by_organization_workspace_installation_idempotencyKey_targetKey`), so a later run may reuse a target key for a different file. Replays with the same fingerprint answer the same target; the same key pair with different fields is 409. The target also stays bound to the exact destination seal that created it. Before an active replay, remint, or finalize returns anything, it loads the live node, checks that the node is active and still inside that seal, and rechecks the target's original file pair and its applied Can edit on the actual node. A missing or null target pair cannot match a new grant. When a service call observes that a member moved the file outside the seal, it sets the sticky `movedOutAt` fence: every old service door answers 404, and moving it back does not return control. A trashed node also answers 404 while trashed, but an ordinary member restore makes it active again. Missing file access answers 403. A later Read-only change is deliberately different: creating the target already accepted the upload, so the retry URL and R2 completion stay available. A released target answers 409 on create/remint. A pending replay or remint creates a fresh asset and atomically switches the target and node to it. Old-key cleanup cannot block this new key. Pending calls refuse if the node no longer uses the target's asset. Committed replays mint nothing, including after text conversion changes the node's content asset.
- New targets store the original service account ID beside the file pair. Background conversion has no live token resolver, so it checks that account's live trusted binding before adding file references. A revoked or replaced account leaves the accepted upload as a stored file. Background conversion refuses a missing pair or account. It never fills a pin from the current installation.
- Both mode booleans are required and both are in the fingerprint. `readOnly: true` sets the new file's local flag after the new capability and Can edit checks. Optional `force` is stored as false by default; only true adds a fingerprint field. Target identity stays on the target doc, separate from file policy. `nonCollaborative: true` is accepted only when the declared `contentType` is an editable text type, and it stays only on the target until conversion succeeds.
- New targets and fresh pending attempts require the payer's paid plan. Free or missing billing state returns `plan_required` → 403 with "File uploads need a paid plan". Check before nodes, assets, or quota writes. Committed replays, settlement, and cleanup do not repeat admission.
- Create and remint reserve and charge nothing. Their declared size must fit remaining `stored_file_bytes` capacity; otherwise `storage_full` → 403 with "This workspace has reached its storage limit". Keep the 16-target run cap and 16 reachable targets per sealed destination/key group. An existing target is resolved before these identity caps.
- `stored_file_bytes` starts at 10 GiB. Publication counts actual charged bytes once. Accepted uploads may finish after the cap fills. Deletion and moving to Trash give no refund. See the quotas skill for raising existing caps.
- Every target `path` applies conventional README/AGENTS/SKILL basename casing and `.agents` folder casing, then must be canonical (same rules as `upload-urls`) and strictly inside the grant's `destinationPathPrefix` — the prefix itself, a string-prefix sibling, or anything outside answers 403 `Path is outside this grant's destination`. A path collision with an existing file is 409; the service path never overwrites. A destination a Move holds is 409 `This item is being moved. Try again when the Move ends.` and writes nothing. The `upload-urls` folder limits apply too: more than 32 new folders answers 400 with `code: "too_many_folders"`, and a new path over 1,024 characters answers 400 `Paths can have at most 1,024 characters.`, before anything is written. A file can go into an existing folder at any depth.
- Create-target refuses a declared `size` that is not an integer from 1 through `files_MAX_UPLOADS_BYTES` (2 GiB) with 400 `File too large`. Member uploads use the same cap. The signed PUT does not bind length, so this check is on the service's declared size only. 2 GiB stays under the R2 single-PUT limit (5 GiB) on the one PUT the service upload path uses.
- Each attempt uploads directly to a fresh `assets/<assetId>` key with signed `If-None-Match: *`. A second PUT to that attempt returns 412; the caller polls confirmation instead of deleting the placeholder or assuming its bytes match. `plugin_service_storage_attempts` retains every asset-to-target receipt. Only the target's newest asset can publish; an older late PUT is deleted without billing. An editable stored content type runs the same upload conversion as a member upload (the asset's `processingWorkId` is left unset). A service target with `nonCollaborative: true` publishes chunks, one content/version asset and file snapshot, `textKind`, and `collaborationEnabled: false`, with no Yjs asset, snapshot, sequence, or update docs. Deterministic conversion fallback stays a blob, preserves the current write policy, and keeps `textKind` and `collaborationEnabled` null. Other service and member text uploads stay collaborative. Other stored content types use `processingWorkId: null`. Plugin upload events never fire for a service upload either way: `plugins_runtime_db_enqueue_upload_completed_runs` refuses any asset with a `plugin_service_storage_attempts.by_asset` receipt.
- R2 publication or finalize reconciliation settles a pending target once. Actual bytes must not exceed its declaration. On success, count real bytes and emit `file_upload` at one cent per started 20 MiB, minimum one cent. `actualBytes` and `chargedBytes` both name the winner's size. A valid moved-out accepted upload may still finish; its sticky fence keeps service doors closed.
- A new target stores the sealed destination path and stable folder node id. The dev deployment was checked before both fields became required. Move to Trash resolves the newest target by its original path and then follows the node id, so renaming the meeting folder does not make deletion report a false success. If a later run recreates a trashed destination at the same path, the newest target points the delete at that active folder instead of the older trashed generation. The subtree walk reads at most 256 folder/file docs, including already trashed descendants.
- A placeholder whose upload never finished is a real, empty file in the workspace. After eight days, `cleanup_expired_unfinalized_assets` keeps the placeholder, asset doc, and pending target. After recovery confirms the object is missing, a pending service placeholder retires its asset with `uploadRetiredAt` and an exact-key deletion job. An ordinary failed placeholder is removed. Delayed events cannot revive them. Remint and pending create replay create a fresh asset and URL, even while old cleanup runs. There is no resume; the service sends the whole file again. Dead-upload cleanup removes the placeholder even when locked. Retry doors still check current subject access and target state. A later lock never stops remint or the accepted first write. A member can delete the empty file like any other file, and the service can cancel it through `delete`. A placeholder that never received bytes has charged nothing.
- `delete` also cancels pending uploads. Its indexed `{installation, destinationPath, targetKey}` group covers upload runs, within the existing 16-target limit. It preflights the whole group atomically. Current target, seal, open epoch, credential file access, item flag and direct-parent list checks apply. Passing a flag needs explicit `force: true` and current `workspace.files.manage-read-only`. It never clears a flag. Committed files share one Trash operation and keep content and metadata. Pending targets keep exact-key cleanup through the URL expiry plus arrival margin. Released history supplies the bounded replay answer. Nothing is refunded.
- Late events for superseded, canceled, or discarded attempts only refresh exact-key cleanup. They cannot change target bytes, emit a billing event, or revive a file.
- `archive-destination` moves at most 256 visited nodes to Trash, in child-first order. The seal fixes the path. An initial lookup requires a saved service target or the existing same-plugin folder label. Current credential file access, exact target identity and epoch still apply. Without force, a refusal rejects the call before any writes. With force and current `workspace.files.manage-read-only`, allowed branches move to Trash while denied branches and their parents stay active. Flags and decision IDs stay unchanged. A partial result leaves the destination epoch and untouched targets open. Only full completion closes the epoch; callers must not delete grants or mark the whole destination deleted after `complete: false`.
- Move to Trash callers persist a `requestId` before sending. Same-ID replay returns its saved count and outcome after current identity checks; it never runs another move to Trash. A later attempt uses a new ID plus `previousRequestId`. It stays bound to the first destination node ID, exact sealed path and epoch. A moved, replaced or recreated destination conflicts. Each refusal is rendered under current read access, with a null path and generic message if unreadable. `plugins_file_archive_receipts` keeps these bounded receipts until installation/workspace cleanup; there is no TTL.
- Oversized settlement retires the asset, queues exact-key deletion through the signed PUT window, removes the placeholder, and releases the target with `releaseReason: "oversized"`. Finalize returns HTTP 409 "The stored file is larger than declared" (`oversized_upload`). Retrying the same key cannot publish it. A new key with a correct declaration can start a new target.
- Physical deletion gives no refund. Deleting the current original upload object releases a committed target. Deleting an old attempt cannot release the winner. Receipts remain until workspace purge.
- Workspace content purge calls `public_api_service_uploads_db_drain_batch` after file cleanup and before upload quota removal. It drains attempt receipts, destinations, and targets in bounded pages. An **uninstall writes to no `files_nodes` doc at all**: the uploaded files belong to the workspace, not to the plugin that put them there, and `workspace.plugins.manage` is not permission to delete a member's file or clear its write policy. Only a workspace-wide drain deletes receipt, destination, and target docs, because the workspace's files and quota docs go with them.

# Bounded file reads

`POST /api/v1/files/read` accepts only `{path,cursor?}` for text and binary files. Omit the cursor or send `null` for the first page. Pass the returned cursor with the same path to continue. Paths must be canonical root-based Files paths, without aliases, traversal, empty segments, backslashes, or wildcards. `maxBytes`, `pageBytes`, offsets and lengths are not accepted. The old `read-many` and `read-bytes` routes are removed.

Success is raw bytes with `Content-Type: application/octet-stream` and `Cache-Control: no-store`. `X-File-Content-Type`, `X-File-Revision`, and `X-File-Size` describe the served saved version. `X-File-Is-Latest` comes for every file; a stored (binary) file is always `true`. `X-File-Next-Cursor` is present only when more bytes remain. Browser CORS and the code runner preserve these headers. An empty file returns empty 200 with no cursor. A file larger than one page returns success with continuation, never a size-based 404. Text clients use one streaming UTF-8 decoder across pages and flush it at EOF.

Reads return the latest available saved bytes immediately. These may lag recent editor changes; reads do not wait for or trigger materialization. Pending creates are missing until Save. Pending replacements, moves, deletes and content edits do not change public saved paths or bytes. `get_saved_file_read_source` resolves the selected saved head and its exact version asset, without a pending overlay. Current text writers upload the exact saved text before publishing that asset, so text and binary use the same R2 range reader. No page loads earlier bytes, text chunks, or the Yjs update log.

The server chooses pages up to 1 MiB. Protected cursors bind the caller, membership lifetime, tenant, path, saved source, storage ETag and next byte position. A cursor grants no access. Recheck live authority and the selected saved source after I/O. The storage ETag also detects a same-key upload overwrite. A changed version returns 409 `file_changed`; discard the partial read before restarting. Retrying a cursor returns the same bytes while its version and access remain valid. Old versions are not retained for reads.

Errors are JSON with `message` and `errorCode`: 400 `invalid_input` or `invalid_cursor`, 401 `unauthenticated`, 403 `permission_denied`, 404 `not_found`, 409 `file_changed`, 429 `rate_limited` or `read_budget_exhausted`, and 502 `storage_unavailable`. Locked files and every path below a locked folder return the same 403 `Permission denied: <path>`. No storage keys, cursor internals or signed URLs leave the route.

Text accepts `files:read` or `files:download` for keys and short grants. Plugin UI and runs retain text-only `files:read`. Binary keeps `files:download` and the key/short-grant principal limit. Service-bound keys use the account's saved-file grants. Every plugin run call is settled, including refusals; scheduled reads keep their final access check and settlement in one mutation.

Ordinary short grants get an 8 MiB download budget only with `files:download`. Reads using download authority reserve the actual page byte count atomically before fetching. Ordinary text reads using `files:read` do not spend that download budget. Code grants charge all reads against their shared 8 MiB budget. Empty files cost no bytes. Failed or aborted reads are not refunded; retries spend bytes again. A page larger than the remaining budget returns 429. Long-lived keys retain their normal request rate limit without a per-run byte budget.

## Revision and freshness

`X-File-Revision` is an opaque string; callers must not parse it. `files_nodes_db_get_file_revision` (`files_nodes_content.ts`) makes it from database fields only, with no R2 ETag: a SHA-256 of the tenant, node, path, kind, content type, collaboration mode, and a tail. The tail is `[assetId, yjsContentHeadId, yjsLastSequenceId, lineageGeneration, lastSequence]` for a collaborative file, `[assetId]` for a non-collaborative one, and `[assetId, r2Key, size]` for a stored file. So any accepted editor update, any save of different bytes, a move or rename, a mode or type change, and a repair change it. Snapshot compaction and reads do not. The read cursor keeps its own digest (`sourceDigest`) for the mid-read change check.

`X-File-Is-Latest` is `true` when the selected head's `unmaterializedUpdateCount` is 0. `false` means people typed changes that the saved bytes do not have yet. Reads still serve the saved bytes at once. A public write publishes its own Yjs snapshot in the same step (see the `files-editable-text` skill), so the file is latest right after it.

Known limit (accepted): while someone types, the counter stays above 0 until the background save catches up, so a conditional write (`expectedRevision`) gets 409 `file_not_latest` during that time. An unconditional write is not blocked.

## Code execution grants

`public_api.create_code_grants({ source, principalKey, tokenHashes: { current, personal } })` returns a Result with `{ personalIsCurrent }`. The caller creates the two tokens; the mutation stores only hashes. It resolves both roots through `ai_chat_workspaces` from the captured original source. Both checks finish before writes. It then creates one `ai_chat_code_read_budgets` doc and the grants in the same transaction. The server uses `Date.now()` and a fixed ten-minute lifetime. Scopes are exactly list, read, and download for each whole root. No argument can select a third workspace or widen scopes.

`execute_code` reads saved files through these grants. Its `emitFile` outputs become readable through the public API only after the user saves them. Bash continues to read pending changes.

When current is personal/home, mint only the current grant. The caller uses the current token for both selectors. Otherwise each token names its own destination workspace, but both grants retain the same original `agentSource` and `codeReadBudgetId`. Their local `remainingReadBytes` is zero. The shared budget starts at 8 MiB and is looked up from the authenticated grant, never from a supplied budget ID.

Every code-grant authorization and byte reservation rechecks source creator, live membership, captured membership lifetime, source permissions, and the resolved destination. A deleted budget also closes its grants. List checks again after page and asset reads. File reads repeat grant and exact file checks after fetching, then check the code source once more after all file work, including error branches. A lost source returns 404 `File unavailable` without file details. Input-only validation errors need no file check. Short grants never receive signed download URLs, redirects, or service replay responses. Losing team access therefore stops an old team-chat token from reading even its owner's still-accessible home, even after re-invitation.

The existing grant expiry cron drains grants and budgets within one indexed batch cap. User finalization drains budgets by user beside its grant drain. Workspace cleanup drains budgets by source thread before deleting that thread, including budgets shared with home grants. Expiry also removes budgets whose grant was deleted earlier. No cleanup needs live membership.

`api_schemas_Main` and the generated HTTP SDK declare raw byte success and JSON errors. The plugin SDK uses `fetchRaw` for this route, retaining status, headers and the unread body. Its `fetchJson` method accepts only JSON routes.

# Plugin file doors

Registered external services use the same public Files contracts as other plugins, with optional writer conditions. `public_api_plugin_files.ts` and `public_api.ts` own the HTTP handlers; `plugins_external_files.ts` owns writer transactions. Writer requests need a live sealed service bearer, current service secret, and `workspace.files.own-write` alongside normal file consents. Ordinary requests without writer conditions keep their existing limits.

A writer and its folder give no access. Writers need applied Can edit through **My file permissions**, on the target or on the parent for a new file. Account sharing adds no plugin access.

`POST /api/v1/files/plugin-folders/ensure` accepts `{path,writer:{resourceKey,rootNodeId},access?:{readOnly?}}`. The resource key is an opaque string of 1–512 characters. Bonobo Senate never parses product IDs from it. A null root ID creates an unused sealed root; a supplied ID must identify the writer's exact labeled root. Repeating a key returns its saved writer and folder IDs without adopting another folder or restoring metadata, policy, or sharing. A new folder is a regular folder: it gets its parent's access, like a folder a person creates.

`POST /api/v1/files/plugin-writers/inspect` takes `{writerId,path,maxBytes}` and returns bounded editable text, content type, opaque content revision, exact parent/target IDs, and writer generation. The caller chooses the byte bound up to the platform text limit. The host reconstructs collaborative text and rejects changed or truncated reads. Markdown layout and rollover limits belong to the caller.

`POST /api/v1/files/write` accepts strict `writer:{writerId,operationId,writerGeneration,sequence,expectedNodeId,expectedContentRevision,contentHash}` plus the normal text options and required `expectedParentNodeId`. It reuses the ordinary staging/fill/create pipeline. Its final transaction checks current credentials, installation/account/actor, label, ACL, current file policies, pinned folders, writer generation and content revision. The proof and replay fingerprint also bind normalized content type, non-collaborative creation, and create-time read-only policy. Final publication compares the actual options with that proof. Publication and its receipt commit together. Identical retries return the receipt; changed inputs or old sequences refuse. Writer mode derives overwrite from the expected target and refuses conflicting overwrite or `skipIfUnchanged:true`.

`POST /api/v1/files/plugin-writers/advance` takes `{writerId,operationId,writerGeneration,nextGeneration}` and advances exactly one generation. `POST /api/v1/files/plugin-archive` takes `{path,writer:{writerId,operationId,writerGeneration,sequence,nodeId,expectedContentRevision?}}` and moves exactly one saved file to Trash. `POST /api/v1/files/plugin-access/set` takes `{path,access:{readOnly},writer:{writerId,operationId,writerGeneration}}`. Access and delete add `receipt` to the normal result; write does the same. Advance returns the receipt directly. None of these contracts knows about channels or transcripts.

Write and delete sequences are ordered within the current writer generation. After a confirmed fence, a rebuild may use the same or a lower source sequence. Old-generation calls still refuse, and equal or lower sequences in the current generation cannot overwrite a newer result or move it to Trash.

An exact committed write retry returns its saved receipt. Current credentials, applied file access, file policies, pinned folder, and writer generation still pass first. Receipt replay changes no content.

Moving a file to Trash accepts `expectedContentRevision`. A supplied revision must still match in the final Trash transaction. A caller may omit it when moving the current text to Trash is intended. Receipt replay returns the original result before checking the old content revision again.

Move to Trash resolves the exact requested node ID before checking access, including when it is already trashed. It checks that node's tenant, path, and pinned parent; it never picks a replacement at the same path. A new delete request for a file already in Trash saves only its receipt. The file's Trash operation ID, dates, author, and content stay unchanged. Current credentials, labels, permissions, policies, writer generation, and any supplied content revision still apply.

Uninstall closes writes through current installation checks and leaves the files and their sharing as they are. Tenant purge drains writer records in bounded batches.

Service exchange, seal and renew accept an optional `requestId`. External backends save that ID before HTTP. `/api/v1/plugins/service-grants/recover` takes the old bearer, service secret, original operation and request ID (plus the original destination for a seal). It returns only the exact saved credential while its resulting grant remains current. The saved response is encrypted at rest. Old bearers cannot authorize ordinary work or another renewal. Ciphertext lasts at most 24 hours; expired receipts remain as dedupe records and require reconnect. Calls without a request ID keep the existing Council behavior. A files-only registration may get an empty-scope interactive bootstrap grant; processing grants still require a real scope.

The shared folder, delete, and access routes live in `public_api_plugin_files_http_routes.ts` and `public_api_plugin_files.ts`. Invoke requests require `ui.invoke.requested`, including inside the mutation. Registered writer requests use the sealed service and proof rules above. Ordinary sealed service requests also support moving one file to Trash. The metadata contract is in `../plugin-system/SKILL.md`.

Folder paths preserve `.agents` with that casing before the normal strict path checks. This does not allow other leading-dot names or case-insensitive file reads.

- Only exact string `plugin-name` metadata selects a node. Existing targets check themselves; missing targets check the deepest existing folder. `source` is descriptive. No creator, ancestor label, policy, or service-target fallback exists. Initial plugin creation writes `source: plugin` and `plugin-name` on every new file and folder. Updates never restore labels.
- Invoke ensure creates only the missing folders below that checked folder. The credential needs applied Can edit there. A locked folder above it does not block creation. The request and response keep the full path. Live-run, label, capability, and Read-only checks still apply.
- Capabilities: write/delete need accepted `workspace.files.own-write`. Any supplied Read-only set/clear needs `workspace.files.manage-read-only`. The old `workspace.files.own-access` capability is removed: a new manifest that asks for it is refused.
- `access.readOnly` sets or clears the local boolean with Can edit and `workspace.files.manage-read-only`. It grants no access. Optional top-level `force: true` passes local flags only after the current capability check. Direct-parent list changes check the parent too. Ordinary writes never inherit force from a prior request.
- A sealed service grant can create and update editable text and move one matching file inside its destination to Trash. Same-plugin invoke output and member-tagged files can match too. Seal, live grant, capability, the subject's ACL, and current policy still apply. Removing a label stops generic writes; it does not cancel an accepted upload or change the separate sealed-target protocol.
- Upload runs keep sibling write/touch rules. Their new output gets labels, but labels never permit ensure, delete, or access through invoke-only doors.
- Invoke touch uses the same exact label rule, including its existing-node query. Creation applies initial metadata to each new node. Existing-file access options do not change its policy.
- Replacing a binary or noneditable file would change its sharing and needs manage permission. Personal plugin consent never grants that permission, so this replacement is refused. In-place text fills preserve identity, metadata, and sharing. Moving matching output to Trash through the separate delete doors still uses current Can edit and policy checks.
- Both `skipIfUnchanged` shortcuts are limited to user API keys. Plugin writes reach final transactional label, subject ACL, and policy checks even when bytes match.
- Invoke `files/write` accepts optional `expectedParentNodeId`. The HTTP boundary validates the ID; malformed values answer 400. Prepare and final create/fill check the same active parent ID, tenant, and path. A moved, trashed, replaced, or absent parent answers 409 without recreating it. This identity precondition does not require a matching parent label on an existing tagged invoke file. Registered service writers also require their pinned folder checks. The existing target-node anchor remains in force.

# Invoke door

Completed responses use outer 200 with `{ runId: string, pluginStatus: number, output: string }`.
The plugin status stays inside this object, so a plugin 401 does not trigger host-session refresh.
Output is the complete secret-masked text, including error bodies. It may be empty for 204.
The raw body and complete encoded JSON each have a 16 MiB cap. There is no public truncation flag.
The runner builds the JSON bytes once; Convex validates metadata, reads the whole bounded body,
and forwards the same bytes only after `finish_event_run` allows relay. The route overrides only
its derived public `200.body` type; errors remain handler-derived.

Host execution, stream, expiry, and unfinished-work failures answer 500. A response-size failure
also carries `code: "response_too_large"`; earlier side effects may already be saved. Clients must
stop automatic size-error retries and keep the same request ID for manual retry. A complete plugin
non-2xx may relay with a failed run outcome. Clean events may succeed with no file writes.
Deadlines cover execution and body reading: 35 seconds for invoke, 180 seconds for event.
Existing request limits and 400/413, session, permission, busy, and rate refusals stay in place.

Plugin-data writes carry the original trusted `credentialRef.runId` into the store transaction.
The live-run check reads status and `deadlineAt` from the run's Activity and `apiTokenExpiresAt`
from the run, plus the current installation, version, tenant, actor and service-account pin.
A live service account cannot extend an ended run. The cached principal query returns the earlier
token/deadline time; HTTP and host auth check the clock, and final mutations check it again.
The write, batch, and delete doors keep all existing collection, scope, ownership, and quota rules.

Every plugin run has one hidden Activity from admission. `/api/v1/activities/start` reveals that
same doc after live access checks and keeps its earlier output targets. `timeoutMs` sets an
expected finish time; Overdue does not end the run or extend its execution deadline. A second
feed opt-in returns 409. Real execution expiry is `timed_out` and prevents later API publication.

`POST /api/v1/plugin-backend/invoke` (registered in `plugins_invoke_http_routes.ts`, implemented in `plugins_invoke.ts`) lets a plugin frame run its own reviewed backend synchronously. Scope `backend:invoke`, `allowedKinds: ["plugin_ui"]`, capability `plugin.backend.invoke`, and the installed version must declare the endpoint in `backend.endpoints`.

- Body `{ endpoint, input?, serializationKey? }`, raw cap `INVOKE_REQUEST_MAX_BYTES` = 32 KiB — smaller than the plugin-data routes on purpose, because the host wraps the input with the configuration and origins and the runner refuses its own body above 64,000 bytes. The host also measures the exact runner JSON before `fetch` and answers 413 without calling the runner when the wrapper does not fit.
- The run is a normal `plugins_event_runs` record: the backend sees one synthetic `POST https://plugin.local<endpoint.path>` with event `ui.invoke.requested`, holds a normal `plr_` token, and lives under the same `MAX_API_CALLS = 20`, masking, and call ledger. Host events stay on the reserved `/__bonobo_senate/run` path. Manifest validation and the runner limit endpoint paths to `/` or slash-separated lowercase letters, digits, and dashes, at most 256 characters; no trailing/duplicate slashes, dots, escapes, or underscores.
- The run's `actorUserId` is the member behind the `plu_` session, host-verified — never page-supplied. The backend reads identity from the event envelope only.
- Serialization: at most one live invoke run per `(installationId, lockKey)`; the default lock key is the whole installation, and an endpoint declared `serialization: "caller-key"` requires the request's `serializationKey`. A second concurrent invoke answers 409 `busy` with `retryAfterMs`.
- Honest limit (say it in SDK docs too): the plugin store and the file system are two systems, one API call and one transaction each, so a backend writing both can crash in between. The run record ends `failed`, the store is the source of truth, and the plugin rebuilds the file on its next run. The host adds no fallback logic to hide this.

# Plugin Mounts API

`public_api_volumes.ts` owns the five POST routes below. `public_api_volumes_http_routes.ts`
registers each with one lazy import. All responses use `Cache-Control: no-store`.

| Route under `/api/v1/volumes` | Body | Result |
| --- | --- | --- |
| `/list` | optional `mountId` | configured mounts, volume states and installation usage/limits |
| `/stage` | `mountId`, `volumeKey`, `revision` | new `stagingId` and abandoned staging id, if any |
| `/write-many` | `stagingId`, `files: [{path, content}]` | written paths/bytes and per-item errors |
| `/publish` | `stagingId` | published key, revision, counts and time |
| `/delete` | `mountId`, `volumeKey` | `deleted: true`; files drain later |

The stored run supplies tenant, installation, actor, account and payer. Its claimed API call must
still be started for the exact route and run. Check live Activity/deadline, token, actor, membership,
source when present, account binding, installation/version, capability and management again at
each durable step. Scheduled runs also check their pinned Run as me grant.
Foreign or malformed staging ids return 404. List reports deleting volumes; other doors return
409 `volume_deleting` until the row is drained. A disabled installation cannot use these routes.

The whole request refuses bad shape, duplicate paths, folder/file overlaps, unknown mounts,
invalid keys/revisions, over 100 files or over 8,000,000 body bytes. A bad item path or content
is an item error. Paths stay exact and absolute within the volume: no empty, dot, parent,
backslash or control segments; at most 255 characters per segment, 1,024 total and depth 32.
Content is valid Unicode text at most 900,000 UTF-8 bytes. Empty files are allowed.

Limits are separate: `copy_cap_reached` (5,000 files / 30,000,000 bytes),
`installation_cap_reached` (20,000 / 200,000,000) and `daily_cap_reached` (10,000 new paths per
UTC day). Deleting docs still use the 32-volumes-per-mount and 128-volume-per-installation caps,
including old mount IDs dropped by upgrades. Installation counters include
published and staging copies. The daily key uses tenant and plugin name and survives reinstall.
Read tokens before upload; consume them in the final file transaction. Replacing a path in the
same staging copy uses no new token or billing event. Other item errors include `invalid_path`,
`invalid_content`, `path_conflict` and `storage_failure`.

R2 PUTs run in groups of 16. Prepared SYSTEM assets have their canonical volume key before PUT
and retain their unfinalized deadline until the file node commits. Final file transactions have at most
25 files / 2,000,000 new bytes and also budget old replacement content and chunk counts.
Each repeats authority, generation state, current credit, capacity and daily checks before writes.
Refused chunks create no node, charge or daily debit; unused uploaded assets are cleaned up.
Metadata is `source: plugin-volume` plus `volume-path`. Stored files are plain read-only text.

Staging expires 26 hours after its last stage/write. Publish refuses empty or expired copies,
then moves the pointer in one transaction. Replaced published copies and abandoned staging copies
retire for ten minutes. Retirement releases their usage once. Delete hides the volume at once
and starts its bounded drain. Every authorized exit settles the API call, including parsing,
limits, credit, storage and final authority failures. One batch still uses one of the run's 20 calls.
Mount writes bill 0.5 cents per new path; see the billing and quotas specs.

# Rate buckets and quota

Buckets live in `packages/app/convex/rate_limiter.ts`:

- `public_api_auth` (60/min, cap 10): charged per client+route for malformed or unknown tokens, so probing stays cheap to refuse.
- `public_api_principal` (4 parts of 5, burst 20 per key and route, 120/min total): charged once per authorized request, always with count 1. The key is `${kind}:${principalKey}:${route}` (`public_api_http_auth.ts`), so each route has its own budget per key. Each part is unsharded and refills at 30/min. One mutation walks all four parts from a random start and returns the first success, or the smallest wait if all refuse. A charge often reads only its first part. Capacity refuses only when every part has less than one token; exhausted write retries can still return an early 429. After a full drain, the next whole token in each part takes about two seconds. Fractions in separate parts are not pooled. Batch items charge their own bulk buckets.
- `public_api_files_write_bulk` (600/min, cap 100, 4 shards): `write-many`, `mkdir` (one token per path), and `delete` (one token per call). One up-front charge of `count: files.length` before any write; an over-budget batch is a whole-request 429 with zero files staged. One charge must stay <= capacity / shards = 25, because the first charge on an unused shard reads only that shard. A bigger batch on a fresh key is refused forever. The in-source test in `public_api.ts` checks every bulk route maximum.
- `public_api_files_upload_bulk` and `public_api_files_download_bulk` (120/min, cap 20 each, not sharded): `upload-urls` and `download-urls` charge `count: items.length` here once per request, after the principal charge. So a batch of N costs one principal call plus N bulk tokens, and minting upload URLs does not use the `write-many` budget.
- When a charge loses a write conflict on every Convex retry, `rate_limiter_limit_by_key` answers a 429 with `retryAfterMs: 1000` instead of a 500. It still fails closed: nothing is let through. Only an action can see this error; a mutation reruns as a whole. This mapping lives in the shared `rate_limiter_limit_by_key`, so it applies to every action that calls it, not only the public API.
- `public_api_plugin_data_write_bulk` (600/min, cap 100): `plugin-data/write-batch` only, charged the same way with `count: documents.length`.
- `plugins_backend_invoke` (30/min, cap 10, key `${userId}:${installationId}`): the invoke door, charged before the run is created — one busy frame cannot drain the member's invoke budget in every other plugin. Plan 5 may re-tune it; keep its constants named in `rate_limiter.ts`.

`upload-urls` uses shared stored-file admission. Before allocation, check the payer's paid plan, safe size, and the full batch against remaining capacity. Free returns HTTP 403 "File uploads need a paid plan". A full cap returns HTTP 403 "This workspace has reached its storage limit".

`stored_file_bytes` uses organization/workspace scope and starts at 10 GiB. Minting reserves and charges nothing. Valid publication counts real bytes and emits `file_upload` once. Accepted uploads can settle after the cap fills. A larger-than-declared object is deleted without publication or billing.

Service uploads use this same counter. Fresh pending attempts repeat admission; committed replay and cleanup do not. Neither deletion nor moving to Trash gives bytes back. See the quotas skill for raising existing caps.

# Editable text write pipeline

`/files/write` and `/files/write-many` accept every editable text type. The optional `contentType` (on the single route and on each `write-many` item) names the type: Markdown, plain text, JSON, YAML, and the other text types the app edits; anything else is refused with `contentType must be an editable text type.`. Without it a created file takes the hint from its name (`.md` is Markdown, a known text extension is that type), else plain text; a filled file keeps its own type, and naming a type that differs from an existing file's type is a conflict. The path must end in a valid file name: a `.md` name follows the Markdown name rule, and other names use `files_normalize_file_rename_name`. Both accept the special spelling described below. Every folder segment must already be a clean folder name. `write`, `write-many`, `touch`, and `upload-urls` all refuse a bad name with one shared 400 message from `invalid_name_message`: `File name "<name>" is not allowed.` (or `Folder name`), then the name rule, then `Try "<clean name>".` when cleanup can save the name. The API still never renames. Reads serve every editable text type; stored files enter through `/upload-urls`.

`public_api_write_one_text_file` (`public_api.ts`) is the shared engine for `write`, `write-many`, `edit`, and `append`. It takes a `change`: `{ kind: "write", content }`, `{ kind: "edit", oldText, newText }`, or `{ kind: "append", content }`. One attempt (`write_one_text_file_attempt`) decides create-vs-fill, builds the text, stages (`prepare_file_write`), PUTs the staged objects to R2, publishes (`publish_file_write` / `publish_file_fill`), and sweeps the stage on failure.

- The saved text is the caller's bytes, with one rule: one leading BOM is dropped and CRLF/lone CR become LF (`files_normalize_text_document_input`), like the app's Monaco editor. The rule runs above the byte count, so the document, the R2 content snapshot, the committed chunks, and the stored size all see the same string. A collaborative fill publishes these exact bytes and its own Yjs snapshot in one step, so no later background save rewrites them in editor style.
- Every success answer (not writer mode) carries `revision`, `size`, and `contentChanged`, computed in the publish transaction. `revision` equals the next read's `X-File-Revision`. For a write, `contentChanged` is true when the BOM/CRLF rule changed the text. For edit and append, see below.

- Writing over an existing editable text file fills in place: the nodeId stays stable for open editors and links, and open Yjs sessions converge on the new content. Non-editable targets (stored uploads) move to Trash and recreate.
- `nonCollaborative: true` (optional, both routes) creates the file with no Yjs document: its text lives only in the committed chunks, and an editor saves it by replacing the whole text. The flag is read ONLY when this write creates the file. A write over a file that already exists keeps the mode that file has, so the flag can never flip an existing file — the Properties dialog owns that decision, because turning collaboration off deletes the edit history. The fill branch for a non-collaborative target has no document to project into, so it replaces the committed content instead, and `skipIfUnchanged` compares the plain text there. See the `files-editable-text` skill for the mode itself.
- `write`, `write-many`, `touch`, and `upload-urls` select an existing literal target before applying conventional README/AGENTS/SKILL basename casing and `.agents` folder casing to a new path. An inaccessible literal target is still occupied: access checks must refuse it, not redirect the write to another canonical file. Every new file door turns bare `readme` into `README.md`. Other names keep their extension policy. All other name cleanup is refused. File reads remain exact and case-sensitive. Empty content is refused too — importers create empty placeholder files through `/api/v1/files/touch`. A new path that would add more than 32 new folders answers 400 `invalid_input` on `write` and `touch` before any upload, and on plugin folder ensure.
- `overwrite: "fail"` returns 409 `A file already exists at this path`; a folder at the path is always 409.
- Writes onto a locked name follow the OS. A create-only write (`overwrite: "fail"`) onto a name the caller sees as a locked row answers the same 409 `A file already exists at this path` (EEXIST); the name is already visible, so this tells nothing. An overwrite of a locked file answers 403 `Permission denied` (EACCES). Below a locked folder no name shows, so every write there is 403.
- `skipIfUnchanged: true`: when the saved bytes equal the normalized text, the route returns 200 with `unchanged: true` before staging — no stage, no asset docs, no uploads, no new version snapshot. It compares bytes, not Yjs documents, so a change in spacing alone is saved. It skips only when the file is latest and, with `expectedRevision`, the revision matches. It reads the revision (`get_file_write_revision`) before the text and answers with it. So if a save lands between the two reads, the caller holds the older revision, and a later conditional write is refused instead of erasing that save. The skip first asks the same node-level write check the publish would ask; a caller the publish would refuse falls through to the normal write path and gets the same refusal, so the unchanged marker cannot confirm content to someone who cannot write the node. Only the fill path can be unchanged.
- Failure vocabulary (per-item `errorCode` in `write-many`, plugin settle codes in `write`): `unauthenticated` (401), `permission_denied` (403), `conflict` (409), `file_changed`, `file_not_latest`, `file_needs_repair`, `file_busy` (all 409), `storage_failure` (500). Every error body of `write`, `edit`, `append`, and `write-many` is `{ message, errorCode }`, also for refusals before the body is read (`unauthenticated`, `permission_denied`, `rate_limited`). The one exception is a plugin writer request to `write` (with the service secret header): its writer protocol refusals, such as a malformed writer or node ID (400) or a stale writer receipt (409), stay `{ message }` only. A `write-many` request-level 400 about one item also names its `path`. `insufficient_funds` (402) never appears as a `write-many` per-item `errorCode`, because `write-many` refuses the whole request before any item is tried. `file_reference_denied` (403) and `file_reference_limit` (400) are plugin settle codes in `write` only: a plugin may add a `bonobo-file://` ref only to a file it can read, at most 50 new refs per write (`server/files-media-refs.ts`). The action finds the added refs; `publish_file_write` and `publish_file_fill` check them.
- A per-item `storage_failure` with message `Failed to write file` means an R2 PUT failed. `r2_put_object` (`convex/r2_client.ts`) already tries each PUT up to 3 times, with a 30 s deadline per try. A thrown fetch (timeout, network) is sent again at once; a 429/5xx answer is sent again after 1 s, then 2 s. Other 4xx answers and a caller abort are not retried. Callers with their own retry (bash `cp` transfer items, GitHub mount Workpool) now multiply it: 3 item attempts × 3 PUT tries. Before this retry (2026-10-21), 2 of 731 new files in one `write-many` run failed because one Yjs snapshot PUT got no answer for 30 s. A `storage_failure` whose message is `Write was not published` comes from the publish mutation, not from R2. A client should still resend failed items.
- Nothing is free: both write routes run one `internal.billing.check_credits` gate at route entry, with `userId: public_api_visibility_user_id(principal)` (the actor; the organization's billing mode then picks the payer). A refusal is HTTP 402 `{ message: "Insufficient funds", errorCode: "insufficient_funds" }` — on `write` the plugin call also settles with that `errorCode`; on `write-many` the whole request refuses with zero files staged. `publish_file_write` and `publish_file_fill` each emit one `file_save` event through `billing_db_emit_file_save` in the same transaction (version part: the staged content snapshot asset id). A `skipIfUnchanged` no-op is gated but emits nothing. `/api/v1/files/touch` has no gate and no emit — the app's sidebar create of an empty file is free too. A sealed service upload emits `file_upload` once per target at settlement (`db_settle_canonicalized_target`; charge key: the target id), priced by its real byte count. Settlement has no credit gate because the accepted bytes are already stored and create-target refused Free plans. See `../billing-system/SKILL.md`.
- A policy that blocks the caller returns 409 `conflict`. A read-only policy reports `This item is read-only.`
  The caller may have ACL permission and still be blocked by policy. `prepare_file_write` checks policy
  after auth and ACL. Publication resolves the path and checks the original credential, current ACL,
  and current Read-only flag before its first write. A policy removed before publish does not block it.
- The existing-file fill publish checks the current node, tenant, ACL, and Read-only flag before it
  checks editable shape, collaboration mode, or Yjs lineage. An unauthorized caller cannot use
  shape or lineage errors to inspect a restricted file. An allowed collaborative fill must carry
  the exact `yjsLastSequenceId` returned by prepare; a stale lineage refuses even if its numeric
  sequence matches the new document.
- A stage for an existing target keeps that target's node id. This prevents stale work from
  overwriting a different node. Refused staged keys go to `files_r2_object_deletion_jobs`. Plugin runs
  must match the selected account within their current request scope and allowed policy reach.
  A refused policy check settles the call with `conflict` and writes no output.
- Stage cleanup also uses `files_r2_object_deletion_jobs`. Plugin completion or tenant deletion may
  remove a stage while its action still has R2 PUTs in progress. Keep each stage job until
  `stage.expiresAt` plus five minutes. If the action later finds the stage missing, it advances the
  same jobs after its PUTs finish. It must not shorten the cleanup window.
- Frontmatter caps: 128 distinct fields (`files_metadata_MAX_FRONTMATTER_FIELDS`) and 512 index documents (`files_metadata_MAX_FRONTMATTER_INDEX_DOCUMENTS`), both in `packages/app/shared/files-metadata.ts`. On the CREATE path the metadata insert helper's `Too many frontmatter fields` throw rolls the publish back, and the pipeline does not map that throw, so the API caller sees a generic error instead of a clean 400; the orphaned stage is swept by the hourly stage cleanup cron. On the FILL path the committed chunks refresh through materialization, which settles over-cap frontmatter with the `contentFrontmatterTooLarge*` marker pair instead of failing the request — the write returns 200 and the committed content stays at the last sequence that fit (see `../files-editable-text/SKILL.md`).

`write-many` batch semantics:

1. Auth first, then the 8 MB bounded body read (`read_request_text_bounded`).
2. Validate every item with the single-route rules before writing anything — one bad item is a whole-request 400 with the offending `path`. Duplicate normalized paths in one batch are a 400 too. Paths resolve in parallel, but the checks run in request order, so the first bad item decides the 400.
3. One up-front bulk-bucket charge, then up to 4 new files at once (`FILES_WRITE_MANY_CONCURRENCY`, with `async_all_settled_with_limit` from `shared/async-utils.ts`), in two waves. Wave 1 writes the first file of each parent folder, so two files never race to create the same parent. Wave 2 writes the rest. Overwrites of files that already exist (one `get_by_path` per item) run last, also up to 4 at once. A collaborative fill stages its Yjs update (`stage_trusted_yjs_update`, kind `public_fill`, 5-minute expiry) with no hold on the private storage counters, so parallel fills do not conflict on those docs. A refused or thrown `publish_file_fill` deletes the fill stage (`retire_trusted_yjs_update_stage`). A new stage deletes the same user's older stage for that file, so of two overlapping fills by one user, the older one finds its stage gone ("Not found") and tries again like a change during the write. Files with different parents can still create the same missing grandparent at once, and when a wave-1 file fails before it creates its parent, its wave-2 siblings may race to create that parent; Convex retries those conflicts.
4. Per-item outcomes, in request order: `{ written: [{ path, nodeId, contentType, revision, size, contentChanged, unchanged? }], errors: [{ path, message, errorCode }] }`. An item with `expectedRevision` is checked on its own; a stale item fails alone. A mid-batch `unauthenticated` aborts the whole request with 401 (and `invalid_input` with 400): files not started yet are skipped, but files already in flight may still finish. Other failures are reported per item and the batch continues.

## Conditional writes and retries

`expectedRevision` (string, 1–256 characters) is optional on `write`, each `write-many` item, `edit`, and `append`. With it the file must exist and still have that revision. It is checked early in `prepare_file_write` and again in `publish_file_fill` before any content write; the final check is the real one. `db_check_file_write_revision` runs after the access and Read-only checks, so a caller who cannot write the file learns nothing. In `publish_file_fill` it also runs after the file's place check (path, archive, editable shape, mode, and Yjs document id). So a file renamed away during the upload answers `changed_during_write`, never the moved file's repair state. The order inside `db_check_file_write_revision` is: repair marker → 409 `file_needs_repair`, revision differs → 409 `file_changed` ("The file changed since you read it. Read it again."), not latest → 409 `file_not_latest`. The repair check runs for every fill; before, such a fill threw an uncaught 500.

- A missing, moved, or replaced file is `file_changed`, never a new create. A file that appears after the lookup is refused too.
- 400 with `overwrite: "fail"` or with `writer` (writer mode keeps its own protocol). `null` is 400 by type.
- A stored (not text) target with `expectedRevision` is 409 `conflict`, not 400: it is workspace state, and a 400 would stop a whole `write-many` batch.

Without `expectedRevision`, the server retries by itself when someone types during the write. `publish_file_fill` answers `changed_during_write` when the file moved away and for its three pin refusals (asset, sequence, lineage generation). A prepare whose target moved under it answers the same. `public_api_write_one_text_file` runs up to `FILE_WRITE_MAX_ATTEMPTS` (3) attempts; each repeats lookup, text build, prepare, PUT, and publish. After the last one it answers 409 `file_busy` ("Someone is editing this file. Try again."). With `expectedRevision` it never retries: `changed_during_write` becomes 409 `file_changed` at once. The create path is not retried. A fill that the Yjs reserve gate refuses because the file holds too many unsaved editor updates (`files_yjs_COMPACTION_RETRY_MESSAGE`) is retried the same way; the throw rolls the fill back, and the action deletes its stage and uploads first. When that file also has a settle marker (text or frontmatter too large), the gate answers the repair message instead, because the background save can never free the budget. That fill is not retried: it answers 409 `file_needs_repair`. When the full update count is already known, `db_check_file_write_revision` gives that answer earlier, before any answer about the text; only a full byte budget waits for the gate, because it needs the size of the write's own update. After any handled failure (a publish refusal on fill or create, a failed upload or stage) the engine cleanup gets `keepPluginCall: true`, and the route settles the plugin call with the answer the caller gets (for example 409 `file_busy`), not `unpublished_write`. Only the published attempt emits `file_save`.

## Edit and append

`public_api_http_change_file` serves both routes. Bodies are strict: `edit` takes `{ path, oldText, newText, expectedRevision?, force? }` with non-empty `oldText`; `append` takes `{ path, content, expectedRevision?, force? }`. Only `user_api_key` callers. Auth asks `files:write`; the route then checks `files:read` itself (403), because a `requiredScope` array means "either" (`public_api_http_auth.ts`). Text with a lone surrogate is 400 `Text must be valid Unicode.`. The path follows the read route's canonical path rule. The credit gate is the same as `write`.

- The target must be an existing editable text file. A missing path is 404 `not_found` ("File unavailable"), a locked one 403 `Permission denied: <path>`, like a read. A folder or stored file is 400 `Edit and append work only on a text file.`.
- `apply_text_change`: an edit needs exactly one literal match; overlapping matches count (the search goes on from `start + 1`). No match is 409 `text_not_found`; more than one is 409 `text_not_unique`. Errors carry no snippets or counts. Before a match error, a 400 for a changed file over the size limit, or a 500 for a document that cannot be rebuilt, the attempt runs the checks a save makes first (`find_save_refusal`, one `get_file_save_refusal` query on the current file): a revoked credential 401, a file that moved or was deleted (`changed_during_write`: the write looks the path up again, or answers `file_changed` when the caller sent `expectedRevision`), write access 403, Read-only 409 `conflict`, repair marker 409 `file_needs_repair`, then `expectedRevision` (409 `file_changed` / `file_not_latest`). So a text answer never hides one of these, and a caller who lost access during the slow reads learns nothing. An append adds `content` at the end, with no newline.
- The base text is the exact saved bytes when they can be read and the file is latest. Otherwise someone is typing, and the base is the live editor text (bridge tax: the result has editor formatting). The result follows the BOM/CRLF rule and the size limit of `write`. `contentChanged` is true when that rule changed the text or the base was the editor text.
- A no-op (`oldText === newText`, empty `content`, or an edit that keeps the saved bytes) saves nothing and answers `unchanged: true`. It is a no-op only while the saved text is still the text the change started from: if another request saved the same result in between, the change still applies on top (two equal appends both land). An edit may leave the file empty. An unconditional no-op while someone types saves the editor text; accepted, because it is rare.
- A non-collaborative edit or append always pins the saved asset, so a save that lands during the upload is never erased: the attempt is retried on the new text.
- Without `expectedRevision`, a client retry after a lost answer can apply an append twice. Docs and CLI help tell callers to send `expectedRevision` when they may retry.

# Binary upload pipeline

For each file, `upload-urls` creates an active `files_nodes` doc, a `files_r2_assets` doc, and a signed
PUT URL. The URL writes directly to
`organizations/<org>/workspaces/<ws>/assets/<assetId>` with signed `If-None-Match: *`.
The R2 finalizer confirms the object and publishes its metadata. Reusing the URL cannot overwrite it.

The whole batch validates before any write. Existing literal paths select their own target, even when locked.
Replacement moves that target to Trash and creates the upload at the same path; it never changes a different canonical sibling.
A create-only batch (`overwrite: "fail"`) onto a locked name answers 409 `A file already exists at this path`, like the write routes; a replace of it answers 403.
New paths get conventional README/AGENTS/SKILL basename casing and `.agents` folder casing. The batch checks names, sizes, collisions, per-path
the key's ACL on the deepest existing folder (with the scope stored on it), current write policies on replacement files and destination folders,
and quota. It also refuses a path a Move holds (409 `This item is being moved. Try again when the Move ends.`),
and a new path with a name over 255 characters or over 1,024 characters in total (400 `Names can have at
most 255 characters.` or `Paths can have at most 1,024 characters.`). A replace keeps its path.
Each path finds its deepest existing folder with `files_db_create_path_lookups`. Without a Move it
looks up the parent first, then walks up through missing folders. This keeps active descendants
readable during partial Move to Trash repair. During Move, the request pins one Before or After view.
Exact path indexes choose normal nodes or selected places; reserved physical nodes cannot fill a
selected empty path. Missing parents use binary path probes. Reads depend on the request paths,
not on saved parent depth. A move op that rewrites physical paths still walks names from the root.
The whole call caches its path reads. Each item's
access checks (on its file and on that folder) come right after its lookups, before any other answer for it
and before later items, so a locked folder answers 403 whether a name below it exists or not. These 403s
name the path as sent. Only then does a path that would add more than 32 new folders (`files_NEW_FOLDER_DEPTH_MAX`) answer 400 with
`code: "too_many_folders"`, its `path`, and `This path creates too many new folders (limit 32).`.
A batch whose new folders plus the existing parents it found number more than 64
(`files_REQUEST_FOLDER_PREFIXES_MAX`) answers 400
`{ message: "This request uses too many folders (limit 64). Send fewer files per request.", code: "too_many_folders", path }`,
with the path that went over. Folders above a found parent do not count, so a file can go into an existing
folder at any depth. The native upload regression checks all 20 files at the 1,024-character path limit
during an unrelated Move, including the mutation's final flush, under 4,096 index reads. A `path` over 4,096 characters
(`files_STORED_PATH_MAX_LENGTH`, the older path cap) answers `Paths can have at most 1,024 characters.` in
the HTTP action, before the batch takes more rate limit slots and before any lookup
(`files_check_request_path_length`). So paths up to 4,096 stay replaceable while the work per path stays
bounded. Paths had no cap before that one, so an older stored path can be longer, and no request can name it.
This route has no raw body byte limit (the 64 KiB limit above is for the plugin data routes): the item
count and this path check bound it. `write` and `touch` share these cached lookups and start
the create at the found folder. Like upload-urls, they check that folder with the scope stored on it, and a
file on the way answers 409 `An intermediate segment is owned by a file`.
One bad item returns 400, 403, or 409 with its `path`, and creates nothing. Each asset stores
`uploadUrlExpiresAt`, like `create_upload_node`. Creating these docs accepts
the upload. A later policy change does not cancel publication or processing. The finished node keeps its current policy.

- `upload-urls` is the deliberate public CREATE path for stored files and editable documents alike: an upload whose stored type is an editable text type converts into an editable document on finalization. The caller's `contentType` wins when it is valid, `application/octet-stream` included; the name is only a hint when no type is sent, and a file with neither is stored bytes (`files_resolve_upload_content_type`). Media uploads keep their type for plugin routing.
- `skipProcessing: true` inserts assets with `processingWorkId: null`: the R2 event finalizer records the object (r2Key, real size, etag) but starts no text conversion and no plugin dispatch. Import tools want this; app-like uploads omit it.
- Until the R2 event arrives, the asset has no `r2Key` and `files/list` reports the file as `pending`. Events can arrive minutes late through Cloudflare queue retries.
- Every asset is born with `unfinalizedExpiresAt` (now + 24 h). Publication clears it. Recovery inspects the direct object hourly for 30 hours after its URL was issued, then weekly. After eight days, a missing ordinary upload loses its placeholder and asset after an exact-key deletion handoff, even when locked. A pending service upload keeps its placeholder and target but retires that asset; a retry uses a new asset. The deletion ledger remains through the signed URL's write window. Non-upload assets retain their existing reference checks and retry policy.
- A presigned PUT URL can still work after key revocation until it expires. Settlement checks the real size against the declared size. A larger object is deleted without publication or billing. An accepted upload can settle after the workspace cap fills.

# Public file links

A member can give one file an "Anyone with the link can view" link. The link doc, its live checks, and every event that ends it are specified in `../access-control/SKILL.md` ("Public file links"). API and plugin writes follow this approved product rule:

- An in-place write keeps the link and its token. This covers `write` and `write-many` fills of an existing editable file (`publish_file_fill`), plugin run and invoke fills, and sealed service fills. `publish_file_fill` does not end or replace the link. A write staged before the link was turned on and published after it keeps that token. Failed writes, `skipIfUnchanged` no-ops, and receipt-only retries keep it too.
- A move to Trash and create write ends the old file's link: `write` over a stored (non-editable) file, `upload-urls` replacing an existing path, plugin move to Trash and recreate, `plugin-archive`, and the service-upload delete and Trash doors. The new file has no link.
- API and plugin writes publish nothing. An embedded image or video shows on a public page only when it is public (its public flag). A key with `files:write` but no `files:download` can add a reference, and visitors see that image only if it is public. The plugin's existing read checks on added refs still apply. See "The public flag" in the access-control skill.
- Private API scope checks do not change. The same key still gets 403 from `/api/v1/files/download-urls`, and a file id alone never opens a file. The link token is a separate authority.
- No `/api/v1` route and no API or plugin credential can turn a link on or off or read its token.
- `POST /api/v1/files/public/set` turns the public flag of one file on or off. Body `{ nodeId, public: boolean }`. Success is `{ nodeId, public: boolean }`. It needs `files:publish` and a person's own key (`allowedKinds: ["user_api_key"]`). A key bound to a service account cannot hold `files:publish` (it is not in `public_api_SERVICE_ACCOUNT_SCOPES`), and plugin tokens get 403. The mutation `public_api.set_file_public` checks edit on the file (and read for On), then runs the app's `files_sharing_db_set_node_public` with the same checks. Errors: 400 bad body or a folder (`not_a_file`), 401 unauthenticated, 404 for a missing, trashed, or uneditable node (or one the key cannot read, for On), 409 `move_busy` or `not_ready` (an access change of this item or a folder above is still running; On only), 429 with `retryAfterMs` when the HTTP action finds the per-user `files_sharing_write` bucket spent, 403 for other refusals.
- Coverage: `convex/files_share_links.public.test.ts` (public check, `set_node_public`, writers, Move, plugin bind, the API route) and `convex/files_share_links.view.test.ts`.

# API-keys page quick-start

The workspace `API keys` page (`packages/app/src/routes/w/$organizationName/$workspaceName/api-keys/index.tsx`) explains the scopes and generates runnable samples:

- Scope descriptions: `files:read` is "Read the committed content of editable text files by path"; `files:write` is "Create and update editable text files by path, and upload other files". The notes explain that reads cover Markdown plus recognized plain text, and that an upload whose stored content type is an editable text type converts into an editable document.
- The create dialog takes a JSON setup in a Monaco editor, so people and agents can paste one text: `{ "name": "Local file reader", "scopes": ["files:list", "files:read"] }`. The Identity picker (Personal or a service account) stays outside the text. The parser is `api_key_setup_parse` in `packages/app/shared/api-key-setup.ts`. It refuses broken JSON, unknown or repeated fields, unknown scopes, an empty scope list, and a name that is empty or longer than 80 characters after trimming. A scope listed twice is kept once, like the server, and gets a warning (`duplicate_scope`) that does not stop the key. Each error and warning marks its exact text in the editor and is listed under it, errors in `Problems in the setup` and warnings in `Warnings in the setup`. Each listed item is a button that puts the caret on its text. Create stays enabled: a click on a setup with problems creates nothing, shows every problem (also the ones hidden on the untouched default text), and puts the caret on the first one. The editor suggests the field names and the scope ids that are not in the setup yet, only the scopes the chosen Identity can use, and shows the docs of a field or scope on hover. Suggestions come from `api_key_setup_suggest` and `api_key_setup_hover_target` in the same module, through app-owned Monaco providers, because the app turns off the Monaco JSON language service. The scope list opens by itself after `[` and `,` and after a picked `scopes` field. Ctrl+. (or the light bulb) offers quick fixes from `api_key_setup_quick_fixes`: change a scope typo to the closest scope, remove an unknown or not-allowed scope, remove a repeated scope, remove an unknown or repeated field, and add a missing `name` or `scopes`. Each parser error and warning has a stable `code` for this. Each known scope id shows its short label as grey text after it (a Monaco inlay hint, so copied text stays clean). A paste is laid out like the default setup, two spaces and one item per line, with `api_key_setup_format_edits`. The server checks the same rules again.
- The JSON text is the only state of the setup. The preset buttons above the editor (Read only, Upload CLI, Full files) and the checkboxes in "All scopes" rewrite only the `scopes` list in that text (`api_key_setup_with_scopes`), so a typed name and comments outside the list stay. Each change is one undo step in the editor. The checkboxes mirror the scopes listed in the text and turn off while the JSON is broken. A service account key cannot check a personal-only scope, but can uncheck one. A preset leaves out the scopes the chosen Identity cannot use.
- The setup starts with `files:list` and `files:read`. Every other scope is opt-in. The page also mints the two plugin-data scopes: `plugin_data:read` ("Read the documents an installed plugin stores in this workspace.") and `plugin_data:write` ("Create, change, and delete those plugin documents."). Both are opt-in, because most keys never touch plugin data, and a plugin's documents can hold whatever that plugin collected. The "All scopes" dropdown (a chevron `<details>`) in the dialog shows every scope id with its description, as a checkbox.
- `files:write`, `files:permissions`, `files:publish`, and `plugin_data:write` are write scopes. Any of them in a valid setup shows one shared write warning.
- For a service-account identity, the parser marks each scope outside `public_api_SERVICE_ACCOUNT_SCOPES` (for example `files:publish`), instead of removing it without a word.
- A minted key has a `Test key` button that POSTs it to `/api/v1/auth/verify` and reports whether the key is live and which scopes it carries. It is the only place the page calls the API itself. It sends the key in the `Authorization` header with `credentials: "omit"`, never in a URL.
- The curl and Node samples list Markdown files with `extension: "md"` (one extension per call), not `contentTypePrefixes`, and the empty-workspace error is `No Markdown files found`. `api-keys/index.test.tsx` pins these sample semantics.

# Guardrails

- Keep `public_api_Scope` as the explicit scope union. Do not export one constant per scope. Check
  standalone scope literals and collections with `satisfies`, and keep the exhaustive
  scope-to-permission map checked with `satisfies Record<public_api_Scope, ...>`.
- Keep batch item caps <= their bucket capacities, and keep the caps named as constants next to the other `FILES_*` limits.
- Keep per-item error messages exact — importers match on them. A locked item answers "Permission denied" and a missing one answers "not found"; do not blur the two (access-control skill, "Locked, not hidden").
- New routes need: schema entry in `api_schemas_Main`, a route definition in `public_api_http_routes.ts` (or the matching feature route module), `public_api_authorize_request` with an explicit `requiredScope`, a rate-bucket decision, a root route-inventory entry, and tests for scope refusal plus at least one batch/limit edge. Add every new scope to the exhaustive scope-to-app-permission map in `public_api_http_auth.ts`; use `null` only when no app permission applies, or when the route checks each item for the caller (the file scopes). Keep a cheap implementation static only when its imports stay small. Otherwise, load the heavy implementation through one literal dynamic import inside the registered route.
- A route that a plugin call reaches must settle its `plugins_event_run_calls` row on every exit, including refusals. The plugin-data routes that a `plugin_run` may reach do this through one `settle(...)` helper so a new early return cannot leave a call hanging. The four service-only plugin-data routes (versioned write, versioned delete, reserve, and release-reservation) never settle, because `allowedKinds` excludes `plugin_run` so their `pluginCallId` is always null. Adding `plugin_run` to one of those lists means adding its settle calls in the same change.
