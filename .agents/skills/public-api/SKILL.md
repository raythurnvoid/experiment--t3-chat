# Mental model

The public API is the workspace file surface for external callers: import CLIs, scripts, and plugins. Every route is a Convex HTTP action with a typed entry in `api_schemas_Main` (`packages/app/shared/api-schemas.ts`). A route without a schema entry does not exist.

The HTTP wrappers are split by startup cost. `/api/v1/files/list` lives in `packages/app/convex/public_api_files_list_http.ts` and stays in the small static root graph because it is the hot plugin read path. The other `/api/v1` routes are spread over five more small modules, each registered in `http.ts`: `public_api_http_routes.ts` (the generic file routes), `public_api_plugin_files_http_routes.ts`, `public_api_service_uploads_http_routes.ts`, `plugins_data_http_routes.ts`, and `plugins_invoke_http_routes.ts`. Each route loads its heavy implementation (`public_api.ts` or `plugins_data_http.ts`) with a literal dynamic import only when that route runs. Shared Bearer-token authorization lives in `packages/app/convex/public_api_http_auth.ts`. Public scopes and the plugin token formats that principal resolution and HTTP authorization must agree on live in `packages/app/shared/public-api.ts`; one-consumer credential and grant details stay private to their owning Convex module.

Plugin UI documents and `/api/v1/*` share the Convex HTTP origin. Their iframe keeps that origin through `sandbox="allow-scripts allow-same-origin allow-forms"`, so the browser sends the existing JSON plus `Authorization` request directly without a CORS preflight. Do not add a `text/plain` token envelope or route calls through the host app. External browser callers on another origin still use normal CORS behavior.

A caller is never more powerful than the user behind it. `public_api_http_auth.ts` maps file and plugin-data scopes to their app permission. Routes pass only their scope. File requests also check the actual target; a service account may hold only a file grant, so HTTP entry must not require a workspace-wide account grant. Invoke file writes require both the actor's and the account's current permission. Upload-triggered runs keep their source/sibling ceiling and never pass a selected-writer policy. The plugin-data store keeps its separate actor and private-scope rules. Final file mutations recheck the original credential, membership, consent, target ACL, account grant, and current policy in one transaction.

# Principals and scopes

`public_api_authorize_request(ctx, request, { requiredScope, allowedKinds, route })` resolves the Bearer token into one principal kind:

Public API scopes and app permissions are separate concepts and use separate values. API scopes use colon names such as `files:read`; app permissions use dot names such as `content.read`. Several file scopes can map to the same app permission, so do not make their values identical or pass the permission from each route.

- `user_api_key` (`pk_<keyId>.<secret>`): key minted on the API keys page by a signed-in Clerk user. `serviceAccountId: null` is a personal key. A bound key uses the account's file grants and writer identity, intersected with its sponsor's current rights. Bound keys accept only `files:list`, `files:read`, `files:write`, `files:download`, and `files:permissions`. Personal keys also accept `plugin_data:read` and `plugin_data:write`. Binding requires current account-management permission and an active account in the same workspace. Rotation preserves that binding and revokes the original credential ID; a new token cannot revive a staged write from the old key.
- `public_api_grant` (64-hex, short-lived): list/read only — the grant validator accepts only `files:list` and `files:read`. Organization removal deletes the member's grants so a later invite cannot revive an old token.
- `plugin_run` (`plr_...`) and `plugin_ui` (`plu_...`): plugin runtime tokens with their own constraints (a backend plugin run writes editable text only — next to its triggering file for an upload run, on nodes selected by matching editable `plugin-name` metadata for an invoke run, see "Plugin file doors" below — and can only download its own source upload). Both require their workspace doc to still exist with no `pluginDataPurgeStartedAt` fence, so phase-one tenant deletion and data reset revoke them before delayed plugin rows drain. Organization removal also deletes that member's plugin UI sessions. A `plu_` token is minted together with a plugin-session JWT that runs live Convex queries against the plugin-facing doors — the first step toward exposing Convex reactivity as a public API; both expire with the session. `POST /plugins-ui/session-jwt` (outside `/api/v1/*`, no `api_schemas_Main` entry) stays as a fallback that exchanges a live `plu_` token for that same JWT. The public API itself never verifies a JWT: `resolve_principal` reads the `plu_` bearer only. Contract: `../plugin-system/SKILL.md`; identity model: `../auth-system/SKILL.md`. Read "page" as "page or file view" everywhere this skill talks about a `plugin_ui` token: a plugin page and a plugin file view get their `plu_` token from the same table, `resolve_principal` looks a token up by its hash alone, and the principal it returns carries no frame kind at all. So every `plugin_ui` rule here is a rule for both frame kinds.
- `plugin_service` (`psg_...`, stored hashed in `plugin_service_grants`): a grant for an external service that acts for one installation. An outside server gets one by presenting a member's plugin frame token to `/api/internal/plugins/service-grants/exchange` together with the plugin's registered exchange secret (a publisher-managed row in `plugins_service_registrations`, compared by hash in constant time), and keeps it alive through the sibling `renew` route; both live in `packages/app/convex/plugins_service.ts` (see `../plugin-system/SKILL.md#service-grant-exchange`). It is bound to the installation rather than to a user session, so a worker can finish work the member started. Its `principalKey` is stable across token rotation, which is what makes it a durable producer identity for versioned documents and reservations. Grants come in two phases. An `interactive` grant is what the exchange mints: one working day, renewable, carrying the registration's scopes minus `files:write` (a file scope only means anything sealed). A `processing` grant comes only from `/api/internal/plugins/service-grants/seal-processing`, which trades a live interactive grant for a new grant sealed to one exact destination path prefix, carrying exactly the registered scopes, expiring six days after the seal; renewal rotates its token but never moves that deadline, and a processing grant cannot seal again. Both phases still need the actor's live membership and permissions on every call today. Every call also rechecks that the installation is enabled, its workspace exists without the purge fence, and the installation still accepts the matching capabilities, so uninstalling, tenant deletion, or removing a capability revokes it. `resolve_principal` narrows scopes by the installation's live capabilities and drops `files:write` whenever `destinationPathPrefix` is null.

Scope names: `files:list`, `files:read`, `files:write`, `files:download`, `files:permissions`, `secrets:read`, `outbound:fetch`, `activities:write`, `plugin_data:read`, `plugin_data:write`, `backend:invoke`. The five file scopes and two plugin-data scopes are available for personal keys. The remaining scopes belong to plugin tokens only; `backend:invoke` exists only on a `plugin_ui` token whose installation accepted `plugin.backend.invoke`.

Plugin runs, service grants, and UI sessions pin their account when minted. Each use requires that active account to still match the installation and its trusted publisher/source binding. Rebinding refuses old credentials instead of moving them to the new account. File reads, lists, and downloads intersect account grants with actor visibility. Downloads repeat both checks after signing, before returning URLs. File grants never grant private plugin-data access. Plugin-session JWT store calls validate the same live pin and keep the existing member/store rules; they are not file-write credentials.

Routes restrict kinds with `allowedKinds`; a valid token of a disallowed kind gets 403. `write-many` and `upload-urls` are `user_api_key` only. `write` and `touch` also allow `plugin_run`, and `write` also allows a `plugin_service` grant: the route refuses any grant that is not sealed (`processing` phase) or whose path is not strictly inside its `destinationPathPrefix`, with 403 `Path is outside this grant's destination`. `read` and `list` allow `plugin_run` too — the scopes come from the installation's accepted `workspace.files.read`, and a run always reads with its actor's eyes (`public_api_visibility_user_id`), so it can never see inside a restricted folder that member cannot open. `download-urls` allows the plugin kinds too. Apart from `/api/v1/files/write` and `/api/v1/files/plugin-archive`, the generic file routes stay closed to `plugin_service`: its file surface is the sealed `/api/v1/files/service-uploads/*` pipeline plus those two doors. A `plugin_ui` token may read and list plugin documents but never write them — a page that needs to write goes through its own backend or a service grant. Three separate checks enforce that, and they are not redundant: `resolve_principal`'s `returns` validator makes `plugin_data:write` unrepresentable for a page token, every write route leaves `plugin_ui` out of `allowedKinds`, and `refuse_page_principal` refuses the kind inside the mutation itself. The in-transaction one is what a caller reaching the mutation directly, or one wrong edit to an `allowedKinds` list, still runs into. A page session can belong to an anonymous identity and is the first thing a scripting bug in a plugin reaches, so a write door there would turn one such bug into stored data that plugin backends later act on with their own secrets.

# Routes

All routes are POST and return JSON. Batch caps are tied to rate-bucket capacities — do not raise one without the other.

| Route                         | Scope              | Notes                                                                                                                                                                                      |
| ----------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/api/v1/files/list`          | `files:list`       | File items carry `status` (`pending` until the R2 object is confirmed, then `ready`; `null` for folders) and `size`                                                                        |
| `/api/v1/files/read`          | `files:read`       | Serves every editable text class (Markdown and plain text); user API keys read committed content only, `public_api_grant` reads (and `read-many`) include the grant user's pending overlay |
| `/api/v1/files/read-many`     | `files:read`       | Up to 50 paths, per-item errors                                                                                                                                                            |
| `/api/v1/files/write`         | `files:write`      | One editable text file; `overwrite: "replace" \| "fail"`, `skipIfUnchanged`; credit gate 402 + one `file_save` emit at publish                                                                   |
| `/api/v1/files/write-many`    | `files:write`      | Up to 20 files, 8 MB request cap, batch semantics below; one whole-request credit gate 402 + one `file_save` emit per written item                                                          |
| `/api/v1/files/touch`         | `files:write`      | Up to 8 paths; free — no gate, no emit (the app's sidebar empty-file create is free too)                                                                                                    |
| `/api/v1/files/download-urls` | `files:download`   | Up to 20 node ids, presigned GET urls, TTL <= 15 min                                                                                                                                       |
| `/api/v1/files/upload-urls`   | `files:write`      | Up to 20 files, presigned PUT urls, upload pipeline below                                                                                                                                  |
| `/api/v1/files/write-policy/get` | `files:read` | Personal or service-bound API keys only; returns authorized policy controls and hides unreadable ancestor details |
| `/api/v1/files/write-policy/set` | `files:permissions` | Personal or service-bound API keys only; requires current target management permission and changes the local policy |
| `/api/v1/files/plugin-folders/ensure` | `files:write` | Invoke only; create labelled folders, applying requested access only on initial creation. Existing folders keep their policy |
| `/api/v1/files/plugin-archive` | `files:write` | Invoke archives a matching node and its subtree, up to 256 nodes; sealed service archives one matching file. Preflight every label, actor/account ACL, and policy before clearing policy and archiving |
| `/api/v1/files/plugin-access/set` | `files:write` | Invoke only; change a matching node's policy/readers with live manage permission; 400 when both access fields are absent |
| `/api/v1/plugin-backend/invoke` | `backend:invoke` | `plugin_ui` only; runs the plugin's declared backend endpoint synchronously and relays its response                                                            |
| `/api/v1/activities/start`    | `activities:write` | Plugin-facing activity feed entry; its durable mutation rechecks the live installation/version, active actor membership, and unarchived source file                                        |
| `/api/v1/auth/verify`         | none               | `user_api_key` only, empty body; answers the key's tenant and the scopes it can still use today                                                                                            |

`/api/v1/auth/verify` is the one route with no required scope, so it uses `public_api_authorize_key_inspection` instead of `public_api_authorize_request`. Keep them separate: making `requiredScope` nullable would let an ordinary route forget its app-permission check. It reports the sponsor and nullable account ID. The helper filters stored scopes through current actor permissions. An empty list is valid. Account access is checked on each requested file, not inferred from this workspace-level answer.

## Plugin document store routes

The nine `/api/v1/plugin-data/*` routes are registered in `plugins_data_http_routes.ts` and implemented in `plugins_data_http.ts`. The store itself and its limits are documented in `../plugin-system/SKILL.md`.

| Route                                     | Scope               | Kinds                                                       |
| ----------------------------------------- | ------------------- | ----------------------------------------------------------- |
| `/api/v1/plugin-data/read`                | `plugin_data:read`  | `user_api_key`, `plugin_run`, `plugin_ui`, `plugin_service` |
| `/api/v1/plugin-data/list`                | `plugin_data:read`  | same as read                                                |
| `/api/v1/plugin-data/write`               | `plugin_data:write` | `user_api_key`, `plugin_run`, `plugin_service`              |
| `/api/v1/plugin-data/write-batch`         | `plugin_data:write` | same as write; up to 50 documents                           |
| `/api/v1/plugin-data/delete`              | `plugin_data:write` | same as write                                               |
| `/api/v1/plugin-data/write-versioned`     | `plugin_data:write` | `plugin_service` only                                       |
| `/api/v1/plugin-data/delete-versioned`    | `plugin_data:write` | `plugin_service` only                                       |
| `/api/v1/plugin-data/reserve`             | `plugin_data:write` | `plugin_service` only                                       |
| `/api/v1/plugin-data/release-reservation` | `plugin_data:write` | `plugin_service` only                                       |

**Private scopes apply to these routes too.** `read` and `list` never return a document inside a plugin scope the actor user has not proved a grant on: `read` answers the document as absent and `list` answers an empty page. That is on purpose — a refusal that said "you may not see this" would tell the caller a private channel exists. A `list` with no `keyPrefix` reads only the public half of the collection, and it does so as an index equality on the absent scope, not as a filter after the read, so `isDone` and the page size stay honest. The write routes refuse a write landing inside a scope the actor cannot write. See "Private scopes" in `../plugin-system/SKILL.md`.

`list` also takes an optional `keyPrefix` (printable ASCII `0x21`-`0x7E`, same validator the user-write door uses) that narrows the page to keys under that prefix as an index range; an invalid prefix answers 400. `read` and `list` responses carry `createdBy`, `updatedBy`, `ownership`, `createdAt`, and `revision` alongside the value. Member-initiated writes do not have an HTTP route at all: the plugin frame calls the `plugins_data.user_*` public mutations on its own Convex client, authenticated with its plugin-session JWT — see `../plugin-system/SKILL.md#plugin-document-store`. Both frame kinds reach those mutations. Only a file-view session sets `fileNodeId`, and `db_authorize_page_write` never reads that field, so a file view writes there exactly as a page does; the door is named for pages only because pages shipped first. For live reads, frames subscribe to `plugins_data.watch_documents` the same way instead of polling these routes; `list` remains the non-reactive deep-history path for a frame that needs documents beyond the SDK window manager's 600-doc ceiling.

## Reading deep history from `list`

`list` also takes two optional bounds, `keyStartExclusive` and `keyEndInclusive`. Both are keys and follow the key validator. They ride the index as a range, never a filter after the read, so every page inside a narrowed range is still full.

Inside a range you may continue with either the response `cursor` or a **fencepost**: the last key of the page you just read, sent as the next request's `keyStartExclusive`. Prefer the fencepost when the continuation has to outlive the process — it is only a key, so it survives a restart, and a cursor does not.

A `cursor` is bound to the read it came from. The route hands back a token carrying the store cursor **and** the scope that produced it: the route path, the resolved installation, the collection, `keyPrefix`, `keyStartExclusive`, and `keyEndInclusive`. Every one of those is compared against the next request's body. A mismatch is **400** naming the field that changed — `cursor was issued for a different keyPrefix. Start a new page instead of reusing it.` — so a page-1 cursor replayed against a different range is refused instead of being read as a position inside the new range. A token that does not decode answers 400 `cursor is not a cursor this route issued`. `cursor: null` is a legal first page, so the check is on the type, not on truthiness.

The token is base64-encoded JSON, not a signature. It exists so a reused cursor fails loudly, not as a security boundary: the installation inside it is compared against the one resolved from the caller's own token, so rewriting it buys a caller nothing it could not ask for directly.

A full page inside a range answers a non-null token with `isDone: false`. A finished page answers `cursor: null` with `isDone: true`.

`isDone` stays the exhaustion signal inside a range. Read it, and do not infer the end of the data from a short page: a final page that happens to be exactly `limit` long is indistinguishable from a full one, and crossed bounds answer `documents: []` with `isDone: true` rather than an unfinished empty page a caller would follow forever.

`truncated` is a different signal, and the name already carries **three** meanings across the platform. Do not read it as one rule. `plugins_data.watch_documents` sets it when the range holds more than `limit` documents. `download-urls` sets it when the caller's own input array was clipped from more than 20 ids. `read-many` sets it when the paths were clipped past 50 **or** the content bytes were clipped. What separates `truncated` from `isDone` is the remedy, not the question: `truncated` says *narrow your range or send fewer inputs*, `isDone: false` says *send the cursor*. A new field that means one of the three has to say which one.

**HTTP counting is unsupported.** `list` returns full document bodies, so counting a full installation is around 100 requests on Free (10,000 slots at 100 per page, about 50 seconds at 120/min) and around 1,000 on a paid plan (100,000 slots, about 8 minutes) — and on the order of 20 MB of bodies to learn one number. Only the slot ceiling scales with the plan; the 16 MiB byte ceiling does not. There is no count endpoint, and paging is not a substitute for one. A surface that needs a number has to keep one itself.

A plugin token derives its installation from the token itself. A `user_api_key` has no installation of its own, so its request body names one; the store normalizes that id and answers `Not found` for anything outside the key's tenant. The id arrives as a plain string on purpose — a `v.id` argument validator throws on a malformed value, which at an HTTP boundary is a 500 instead of a refusal.

The HTTP adapter passes the original `credentialRef` to the final store query or mutation. That transaction re-reads the key, run, UI session, or service grant and checks its current tenant, actor, lifetime, scope or capability, and installation link as applicable. Plugin credentials must still carry the installation's live account pin. Personal keys must still be unbound. Revocation, expiry, rebinding, or a changed installation can therefore refuse a request after its initial HTTP check. The store also checks current membership and installation consent; file grants do not grant access to plugin-store docs.

All nine bodies therefore accept the same optional `installationId`, including the four service-only ones. A user key that omits it gets 400 `installationId is required for an API key`, and any plugin token that sends it gets 400 `installationId is not allowed for this token`. The four service-only bodies need the field for the refusal alone: leaving it out of those validators would make Zod strip it before `to_store_principal` ever sees it, so a service naming another installation would be answered as if it had named nothing.

Every request body is strict, so unknown fields return 400. The raw JSON body limit is 64 KiB for every route except `write-batch`, which allows 4 MiB for up to 50 documents. The limit includes property names, JSON escapes, and whitespace. Crossing it returns 400 `Request body is too large`. The larger batch limit is transport headroom only; every canonical document value still has the 16 KiB store limit.

`value` on the three routes that carry one is checked for every shape Convex cannot store: a field name that starts with `$`, holds a non-printable-ASCII character, or is longer than 1024 characters; an object with more than 1024 fields; an array with more than 8192 items; and a value nested deeper than 15 levels (the document holds the value one level inside itself, and Convex's own ceiling is 16). Convex applies the name rules while serializing the mutation arguments and the other three while validating the document, and every one of them **throws** rather than returning a refusal, so without the check at the HTTP boundary a caller's bad value is a 500 with no message instead of a 400. The check walks nested objects and arrays, because the rules apply at every depth, and the depth limit is what bounds the walk.

Every string in a request body is also checked for an unpaired Unicode surrogate, which `JSON.parse` accepts and Convex refuses. Write the check as "does this code unit complete the pair", never as "is it outside the low-surrogate range": past the last character `charCodeAt` answers `NaN`, every comparison against `NaN` is false, and the second form therefore calls a string ending in a high surrogate well formed.

A refused body answers 400 `Request body validation failed` and does **not** say which field was wrong. That is one message for a bad collection name, an unknown extra field, a malformed string, and an unstorable value alike, so a caller debugging a 400 has to bisect its own body. Callers relying on the message to locate the problem should not.

Store refusals map to status by the name the store tagged, so rewording a refusal cannot change its status: 409 for the whole conflict family (another writer, a live reservation, a replayed idempotency key with different fields, a replay of an already-released reservation, a deleted key, a revision out of order, a revision replayed with a different value) and 403 for all six storage-ceiling messages `check_capacity` can return (installation bytes, document slots, collections, and the same three per member). Only three untagged refusals map by message — 401 `Unauthenticated`, 403 `Permission denied`, 404 `Not found` — and everything else is 400. The ceilings answer 403 rather than 507 to match `/api/v1/files/upload-urls`, which already answers a full quota with 403.

`files/list` applies `contentTypePrefixes` inside one Convex query before pagination. `limit` counts matching docs. `scanLimit` controls how many source docs the filtered query may inspect; the public route defaults it to 10,000, and the internal query caps it at 10,000 source docs. The query does not set `maximumBytesRead`. A sparse filtered page can still be short or empty while `isDone` is false, so callers must continue with the returned cursor. Direct internal callers such as AI file tools omit `scanLimit` and keep the 1,000-doc default. The prefix predicate uses lexicographic string ranges because Convex filters do not provide `startsWith`.

## Service upload routes

The five `/api/v1/files/service-uploads/*` routes are registered in `public_api_service_uploads_http_routes.ts`, implemented in `public_api_service_uploads_http.ts`, with the storage mutations in `public_api_service_uploads.ts`. All are POST, scope `files:write`, `allowedKinds: ["plugin_service"]`, and the route refuses any grant whose phase is not `processing`. The mutations re-check the grant doc, installation state, capabilities (`plugin.service.connect` + `workspace.files.write`), actor liveness/membership, and workspace `content.write` inside the transaction. A new read-only target also requires `workspace.files.create-read-only` and live `content.permissions.manage` at its effective destination ACL.

| Route                                               | Body                                                     | Answer                                                                                                                        |
| --------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `/api/v1/files/service-uploads/create-target`       | `{ idempotencyKey, targetKey, path, contentType, size, readOnly, nonCollaborative }` | pending `{ state, path, nodeId, uploadUrl, headers, uploadUrlExpiresAt }` or committed `{ state, path, nodeId, actualBytes }` |
| `/api/v1/files/service-uploads/remint`              | `{ idempotencyKey, targetKey }`                          | same union: fresh attempt and URL while pending, or committed                                            |
| `/api/v1/files/service-uploads/finalize`            | `{ idempotencyKey, targetKey }`                          | `{ state: "pending" \| "committed" \| "released", path, nodeId, actualBytes \| null }`                                        |
| `/api/v1/files/service-uploads/delete`              | `{ idempotencyKey, targetKey }`                          | `{ state: "deleted", paths }`                                                                                                |
| `/api/v1/files/service-uploads/archive-destination` | `{}`                                                     | `{ archivedNodes }`                                                                                                           |

Semantics that must not drift:

- `idempotencyKey` names one upload run (the meeting); `targetKey` names one file inside it. For create, remint, and finalize, the pair is the target's identity (`by_organization_workspace_installation_idempotencyKey_targetKey`), so a later run may reuse a target key for a different file. Replays with the same fingerprint answer the same target; the same key pair with different fields is 409. The target also stays bound to the exact destination seal that created it. Before an active replay, remint, or finalize returns anything, it loads the live node, checks that the node is active and still inside that seal, and rechecks both the presenting actor's and account's `content.write` access on the actual node, including its restricted scope. When a service call observes that a member moved the file outside the seal, it sets the sticky `movedOutAt` fence: every old service door answers 404, and moving it back does not return control. An archived node also answers 404 while archived, but an ordinary member restore makes it active again. Missing actor or account access answers 403. A later write-policy change is deliberately different: creating the target already accepted the upload, so the retry URL and R2 completion stay available. A released target answers 409 on create/remint. A pending replay or remint creates a fresh asset and atomically switches the target and node to it. Old-key cleanup cannot block this new key. Pending calls refuse if the node no longer uses the target's asset. Committed replays mint nothing, including after text conversion changes the node's content asset.
- Both mode booleans are required and both are in the fingerprint. `readOnly: true` selects the installation's account as the local writer, after actor/account management checks. Target identity stays on the target doc, separate from file policy. `nonCollaborative: true` is accepted only when the declared `contentType` is an editable text type, and it stays only on the target until conversion succeeds.
- Create-target is closed to `Free`. Storing files for a service costs real money, so only a workspace whose payer is on `Pay As You Go` or `Pro` may start one. `Free`, an anonymous payer's synthetic snapshot, and a payer with no billing state all answer `plan_required` → 403. The payer is the billed user (`billing_pick_billed_user_id`), so an owner-billed organization answers to the owner's plan and not to the acting member's. This gate runs before the quota doc is seeded, because a Convex mutation that returns `_nay` still commits whatever it wrote first. It is also the only door that can really refuse an upload: the quota below can only bill bytes R2 already stored. Only a new target is gated. Replay, remint, finalize, delete, and archive do not repeat this plan gate. Delete and archive still check the current write policy.
- There is no booking step and create-target charges nothing. The `size` in the request is only the service's guess, and the signed PUT does not bind it, so the workspace is charged for the largest size R2 confirms across that target's attempts. Create-target refuses with `storage_full` → 403 only when the quota is already full, which stops the next file rather than the current one. The counter only grows, exactly like `public_api_upload_bytes`. At most 16 targets may be created in one upload run. One sealed destination may also hold at most 16 reachable pending or committed targets for the same target key across runs, which bounds all-or-nothing cleanup. Moved-out and released history does not count. An exact replay of an existing target still works at either cap because create-target resolves replays first.
- The quota is a budget, not a guard. A signed PUT does not bind the object's length, so a service can always store more than it declared; the R2 event settlement charges the stored bytes, it does not prevent them. Blocking an upload is the plan gate's job, not the counter's.
- Every target `path` must be canonical (same rules as `upload-urls`) and strictly inside the grant's `destinationPathPrefix` — the prefix itself, a string-prefix sibling, or anything outside answers 403 `Path is outside this grant's destination`. A path collision with an existing file is 409; the service path never overwrites.
- Create-target refuses a declared `size` that is not an integer from 1 through `files_MAX_UPLOADS_BYTES` (2 GiB) with 400 `File too large`. Member uploads use the same cap. The signed PUT does not bind length, so this check is on the service's declared size only. 2 GiB stays under the R2 single-PUT limit (5 GiB) on the one PUT the service upload path uses.
- Each attempt uploads directly to a fresh `assets/<assetId>` key with signed `If-None-Match: *`. A second PUT to that attempt returns 412; the caller polls confirmation instead of deleting the placeholder or assuming its bytes match. `plugin_service_storage_attempts` retains every asset-to-target receipt. Only the target's newest asset can publish; an older late PUT is charged and deleted. An editable stored content type runs the same upload conversion as a member upload (the asset's `processingWorkId` is left unset). A service target with `nonCollaborative: true` publishes chunks, one content/version asset and file snapshot, `textKind`, and `collaborationEnabled: false`, with no Yjs asset, snapshot, sequence, or update docs. Deterministic conversion fallback stays a blob, preserves the current write policy, and keeps `textKind` and `collaborationEnabled` null. Other service and member text uploads stay collaborative. Other stored content types use `processingWorkId: null`. Plugin upload events never fire for a service upload either way: `plugins_runtime_db_enqueue_upload_completed_runs` refuses any asset with a `plugin_service_storage_attempts.by_asset` receipt.
- The R2 event settles the target in the same transaction that records the canonical object. The target records the winner's exact `actualBytes` separately from `chargedBytes`, the largest confirmed object across all accepted attempts. If a member already moved an accepted placeholder outside its seal, the event still finishes the file and charges its confirmed size, while `movedOutAt` keeps every old service door closed. The declared size never reaches the books, so an object smaller or larger than declared is simply charged for what it is, over the ceiling if needed. Finalize normally reports the active settled state; it can also reconcile a canonical asset that was recorded before the target was settled.
- A new target stores the sealed destination path and stable folder node id. The dev deployment was checked before both fields became required. Archive resolves the newest target by its original path and then follows the node id, so renaming the meeting folder does not make deletion report a false success. If a later run recreates an archived destination at the same path, the newest target points archive at that active folder instead of the older archived generation. The subtree walk reads at most 256 folder/file docs, including already archived descendants.
- A placeholder whose upload never finished is a real, empty file in the workspace. After eight days, `cleanup_expired_unfinalized_assets` keeps the placeholder, asset doc, and pending target. After recovery confirms the object is missing, an unprotected file's asset gets `uploadRetiredAt` and an exact-key deletion job. Delayed events cannot revive it. Remint and pending create replay create a fresh asset and URL, even while old cleanup runs. There is no resume; the service sends the whole file again. Any local or inherited write policy defers this cleanup, including a selected-writer policy: background cleanup cannot act as that writer. Retry doors still check current actor/account access and target state, but a later policy change does not cancel an accepted upload. A member can delete the empty file like any other file, and the service can cancel it through `delete`. A placeholder that never received bytes has charged nothing.
- `delete` also cancels pending uploads. Its validated `idempotencyKey` does not narrow cleanup: the indexed `{ installation, destinationPath, targetKey }` group covers upload runs. Moved-out and released history stays outside the live scan. One released target provides a bounded replay answer. Before writing, every live match must pass exact target, destination, open-epoch, actor/account write, and current policy checks. A service can pass only a direct policy selecting its account, with current `workspace.files.create-read-only` consent and actor management permission. Historical origin, the old request's `readOnly`, and a matching account alone never bypass target checks. Any ancestor policy blocks this direct-only operation. Committed matches share one archive operation and keep their assets, content, and metadata. Clearing each local policy before archive also requires account management permission. Targets become `released` with `deleteRequestedAt`; canonical sizes stay unchanged. Pending matches enqueue exact-key cleanup, then delete only the empty placeholder and asset. Pending cancellation keeps cleanup through the issued URL's expiry plus the arrival margin. Both cases return `"deleted"`. Create/remint treat released targets as gone; finalize reports `released`. Nothing is refunded.
- A direct object event may arrive after its attempt was superseded, cancelled, or discarded. The retained receipt maps that asset to its logical target. `record_untracked_asset_event` charges only the increase over `chargedBytes` and advances the exact-key deletion job in the same mutation. This remains true after a newer attempt commits. `actualBytes` remains the winning object's size, or null if nothing committed. For A=12 MB and newer B=5 MB, the budget is 12 MB and finalize reports 5 MB in either event order. No late event emits another file-save event or refunds bytes.
- `archive-destination` is the Council delete-meeting door. It archives the destination and active descendants in one operation, up to 256 nodes, without deleting R2 objects or refunding bytes. It follows the saved destination node so a member rename does not strand cleanup. Before writing, it checks actor/account ACL and current policy across the collected nodes. An already archived node whose target is released with `deleteRequestedAt` is completed deletion history; after those checks, its node, policy, and target stay unchanged. Other present targets must pass tenant, installation, destination, and open-epoch checks. Active released targets still refuse. Invalid targets never fall through to the separate labelled-file rules. Passing and clearing a direct account policy uses the same consent and management checks as `delete`; ancestor policies still block. It clears permitted local policies before archiving so a member can restore the set. The archive closes that destination epoch. Restoring it later does not reopen service authority; replay returns zero. A later create opens a new epoch. A member-only folder that reused the path is untouched. Missing or already archived destinations return `{ archivedNodes: 0 }`.
- Physical deletion gives nothing back. `settle_object_deletion_job` releases a committed target only when its current original upload object is deleted. Deleting an older attempt cannot close the winning target. Targets and receipts remain until workspace purge.
- Workspace content purge calls `public_api_service_uploads_db_drain_batch` after file cleanup and before upload quota removal. It drains attempt receipts, destinations, and targets in bounded pages. An **uninstall writes to no `files_nodes` doc at all**: the uploaded files belong to the workspace, not to the plugin that put them there, and `workspace.plugins.manage` is not permission to delete a member's file or clear its write policy. Only a workspace-wide drain deletes receipt, destination, and target docs, because the workspace's files and quota docs go with them.

# Plugin file doors

The three `/api/v1/files/plugin-*` routes live in `public_api_plugin_files_http_routes.ts` and `public_api_plugin_files.ts`. Only archive accepts both invoke and sealed service principals. Ensure and access require `ui.invoke.requested`, including inside the mutation. Chitchat uses invoke calls; Council uses its sealed service grant. The metadata contract is in `../plugin-system/SKILL.md`.

- Only exact string `plugin-name` metadata selects a node. Existing targets check themselves; missing targets check the deepest existing folder. `source` is descriptive. No creator, ancestor label, policy, or service-target fallback exists. Initial plugin creation writes `source: plugin` and `plugin-name` on every new file and folder. Updates never restore labels.
- Capabilities: the write/archive doors require accepted `workspace.files.own-write`; the `access` options (on ensure, on write-create, and on `plugin-access/set`) require `workspace.files.own-access` — a request that sends access options without it is 403 `Permission denied` before anything is created.
- `access.readOnly: true` selects the installation's account as the writer. Creation needs both actor and account management permission; writer selection grants no access. `false` clears the local rule. Invoke may satisfy matching ancestor writer rules; sealed service requests may satisfy a direct rule only. Read-only and nonmatching ancestor rules still block. Current policy decides authority, regardless of who first created it. See `../files-read-only/SKILL.md`.
- `access.readScopeId` binds readers to a live scope in the same installation, with at most four bindings per scope. A dead scope answers 404. A foreign binding refuses until drained or detached. `readScopeId: null` detaches the binding and preserves its restriction and grants. Reader refresh preserves independent account grants. Human sharing edits detach the binding; service-account grant edits, denied/no-op sharing, and metadata edits preserve it. Repeated ensure never restores removed grants or detached sharing. Prepare all policy and reader changes before writes. A repeated local policy or absent-binding detach needs target management only; a real change also checks the nested restricted scopes it affects.
- A sealed service grant can create and update editable text and archive one matching file inside its destination. Same-plugin invoke output and member-tagged files can match too. Seal, live grant, capability, actor/account ACL, and current policy still apply. Removing a label stops generic writes; it does not cancel an accepted upload or change the separate sealed-target protocol.
- Upload runs keep sibling write/touch rules. Their new output gets labels, but labels never permit ensure, archive, or access through invoke-only doors.
- Invoke touch uses the same exact label rule, including its existing-node query. Creation applies initial metadata to each new node. Existing-file access options do not change its policy or reader binding.
- Plugin archive-and-recreate replacement requires live manage permission on the old target. Finish all access-consent, parent actor/account ACL and policy, and target checks before archive. The old node retains its grants and binding; the new node inherits parent sharing. In-place fills preserve identity, metadata, and sharing.
- Both `skipIfUnchanged` shortcuts are limited to user API keys. Plugin writes reach final transactional label, actor/account ACL, and policy checks even when bytes match.
- Invoke `files/write` accepts optional `expectedParentNodeId`. The HTTP boundary validates the ID; malformed values answer 400. Prepare and final create/fill check the same active parent ID, tenant, and path. A moved, archived, replaced, or absent parent answers 409 without recreating it. This identity precondition does not require a matching parent label on an existing tagged file. Chitchat passes the fresh private-folder ID on every private transcript write. The existing target-node anchor remains in force.

# Invoke door

`POST /api/v1/plugin-backend/invoke` (registered in `plugins_invoke_http_routes.ts`, implemented in `plugins_invoke.ts`) lets a plugin frame run its own reviewed backend synchronously. Scope `backend:invoke`, `allowedKinds: ["plugin_ui"]`, capability `plugin.backend.invoke`, and the installed version must declare the endpoint in `backend.endpoints`.

- Body `{ endpoint, input?, serializationKey? }`, raw cap `INVOKE_REQUEST_MAX_BYTES` = 32 KiB — smaller than the plugin-data routes on purpose, because the host wraps the input with the configuration and origins and the runner refuses its own body above 64,000 bytes. The host also measures the exact runner JSON before `fetch` and answers 413 without calling the runner when the wrapper does not fit.
- The run is a normal `plugins_event_runs` record: the backend sees one synthetic `POST https://plugin.local<endpoint.path>` with event `ui.invoke.requested`, holds a normal `plr_` token, and lives under the same `MAX_API_CALLS = 20`, masking, and call ledger. Host events stay on the reserved `/__bonobo_senate/run` path. Manifest validation and the runner limit endpoint paths to `/` or slash-separated lowercase letters, digits, and dashes, at most 256 characters; no trailing/duplicate slashes, dots, escapes, or underscores.
- The run's `actorUserId` is the member behind the `plu_` session, host-verified — never page-supplied. The backend reads identity from the event envelope only.
- Serialization: at most one live invoke run per `(installationId, lockKey)`; the default lock key is the whole installation, and an endpoint declared `serialization: "caller-key"` requires the request's `serializationKey`. A second concurrent invoke answers 409 `busy` with `retryAfterMs`.
- Honest limit (say it in SDK docs too): the plugin store and the file system are two systems, one API call and one transaction each, so a backend writing both can crash in between. The run record ends `failed`, the store is the source of truth, and the plugin rebuilds the file on its next run. The host adds no fallback logic to hide this.

# Rate buckets and quota

Buckets live in `packages/app/convex/rate_limiter.ts`:

- `public_api_auth` (60/min, cap 10): charged per client+route for malformed or unknown tokens, so probing stays cheap to refuse.
- `public_api_principal` (120/min, cap 20): charged once per authorized request. `download-urls` and `upload-urls` charge `count - 1` extra units so a batch of N costs the same as N single calls.
- `public_api_files_write_bulk` (600/min, cap 100): `write-many` only. One up-front charge of `count: files.length` before any write; an over-budget batch is a whole-request 429 with zero files staged.
- `public_api_plugin_data_write_bulk` (600/min, cap 100): `plugin-data/write-batch` only, charged the same way with `count: documents.length`.
- `plugins_backend_invoke` (30/min, cap 10, key `${userId}:${installationId}`): the invoke door, charged before the run is created — one busy frame cannot drain the member's invoke budget in every other plugin. Plan 5 may re-tune it; keep its constants named in `rate_limiter.ts`.

`upload-urls` plan gate: before anything else in the mutation, `billing_db_check_paid_plan` on the billed user (the workspace payer, so an owner-billed organization answers with the owner's plan). A `Free` payer, an anonymous payer, and a payer with no billing state all get 403 `This workspace's plan does not include file uploads`. Keeping a file in the bucket costs money every month, and the byte quota below can only bill what R2 already stored, so the plan is the only door that can refuse an upload. Same gate, same message, in the Files sidebar mutations — see the files-explorer-tree skill.

`public_api_upload_bytes` quota (org+workspace scope, 50 GB of declared bytes): consumed by `upload-urls` mints in the same mutation that creates the nodes and assets. Monotonic — deleting files does not refund. Seeded lazily at the first mint, after the plan gate above; see the quotas skill for the exception this creates.

`plugin_service_storage_bytes` quota (org+workspace scope, 10 GiB): the service-upload budget. Create-target charges nothing and only refuses a workspace that is already full; the separate plan gate above is what refuses a non-paying workspace outright. Confirmed events charge only the increase over the target's previous largest object. The winning file's size stays separate. Monotonic, exactly like `public_api_upload_bytes` — deleting a service-uploaded file gives nothing back. Also seeded lazily, at the first target.

# Editable text write pipeline

`/files/write` and `/files/write-many` accept every editable text type. The optional `contentType` (on the single route and on each `write-many` item) names the type: Markdown, plain text, JSON, YAML, and the other text types the app edits; anything else is refused with `contentType must be an editable text type.`. Without it a created file takes the hint from its name (`.md` is Markdown, a known text extension is that type), else plain text; a filled file keeps its own type, and naming a type that differs from an existing file's type is a conflict. The path must end in a valid file name (`Path must end in a valid file name.`): a `.md` name follows the Markdown name rule (README casing), any other name must already be a normalized file name (`files_normalize_file_rename_name`). Reads serve every editable text type; stored files enter through `/upload-urls`.

`write_one_text_file` (module-private helper in `public_api.ts`) is the shared engine for `write` and `write-many`: decide create-vs-fill, stage (`prepare_file_write`), PUT the staged objects to R2, publish (`publish_file_write` / `publish_file_fill`), and sweep the stage on failure.

- Both routes normalize the incoming content at the request boundary, ABOVE the byte count: one leading BOM is dropped and CRLF/lone CR become LF (`files_normalize_text_document_input`). The document, the R2 content snapshot, the committed chunks, and the stored size all see the same normalized string.

- Writing over an existing editable text file fills in place: the nodeId stays stable for open editors and links, and open Yjs sessions converge on the new content. Non-editable targets (stored uploads) archive-and-recreate.
- `nonCollaborative: true` (optional, both routes) creates the file with no Yjs document: its text lives only in the committed chunks, and an editor saves it by replacing the whole text. The flag is read ONLY when this write creates the file. A write over a file that already exists keeps the mode that file has, so the flag can never flip an existing file — the Properties dialog owns that decision, because turning collaboration off deletes the edit history. The fill branch for a non-collaborative target has no document to project into, so it replaces the committed content instead, and `skipIfUnchanged` compares the plain text there. See the `files-editable-text` skill for the mode itself.
- Paths must already be canonical: every name is checked with `files_normalize_name` and refused when the canonical form differs, unlike the app UI, which silently normalizes. One non-obvious corner: special names like `readme.md` canonicalize to uppercase `README.md`, so the lowercase spelling is refused (with the generic invalid-name message). Empty content is refused too — importers create empty placeholder files through `/api/v1/files/touch`.
- `overwrite: "fail"` returns 409 `A file already exists at this path`; a folder at the path is always 409.
- `skipIfUnchanged: true`: when projecting the incoming Markdown into the current doc is a semantic no-op (`fillUpdate === null`), the route returns 200 with `unchanged: true` before staging — no stage, no asset docs, no uploads, no new version snapshot. The skip first asks the same node-level write check the publish would ask; a caller the publish would refuse falls through to the normal write path and gets the same refusal, so the unchanged marker cannot confirm content to someone who cannot write the node. Only the fill path can be unchanged; comparison is Yjs-level, not byte-level, because materialized Markdown is not byte-stable. `null` never lies, but the reverse is not guaranteed: some semantically identical rewrites still publish.
- Failure vocabulary (per-item `errorCode` in `write-many`, plugin settle codes in `write`): `unauthenticated` (401), `permission_denied` (403), `conflict` (409), `storage_failure` (500). `insufficient_funds` (402) is a plugin settle code in `write` only; it never appears as a `write-many` per-item `errorCode`, because `write-many` refuses the whole request before any item is tried.
- Nothing is free: both write routes run one `internal.billing.check_credits` gate at route entry, with `userId: public_api_visibility_user_id(principal)` (the actor; the organization's billing mode then picks the payer). A refusal is HTTP 402 `{ message: "Insufficient funds" }` — on `write` the plugin call also settles with `errorCode: "insufficient_funds"`; on `write-many` the whole request refuses with zero files staged. `publish_file_write` and `publish_file_fill` each emit one `file_save` event through `billing_db_emit_file_save` in the same transaction (version part: the staged content snapshot asset id). A `skipIfUnchanged` no-op is gated but emits nothing. `/api/v1/files/touch` has no gate and no emit — the app's sidebar create of an empty file is free too. A sealed service upload emits the same event once per target at settlement (`db_settle_canonicalized_target`; version part: the target id) with no gate there, because the bytes are already stored and `create-target` already refused Free plans. See `../billing-system/SKILL.md`.
- A policy that blocks the caller returns 409 `conflict`. A read-only policy reports `This item is read-only.`
  The caller may have ACL permission and still be blocked by policy. `prepare_file_write` checks policy
  after auth and ACL. Publication resolves the path and checks the original credential, current ACL,
  and current writer policy before its first write. A policy removed before publish does not block it.
- The existing-file fill publish checks the current node, tenant, ACL, and writer policy before it
  checks editable shape, collaboration mode, or Yjs lineage. An unauthorized caller cannot use
  shape or lineage errors to inspect a restricted file. An allowed collaborative fill must carry
  the exact `yjsLastSequenceId` returned by prepare; a stale lineage refuses even if its numeric
  sequence matches the new document.
- A stage for an existing target keeps that target's node id. This prevents stale work from
  overwriting a different node. Refused staged keys go to `files_r2_object_deletion_jobs`. Plugin runs
  must match the selected account within their current request scope and allowed policy reach.
  A refused policy check settles the call with `conflict` and writes no output.
- Stage cleanup also uses `files_r2_object_deletion_jobs`. Plugin completion or tenant deletion may
  remove a stage while its action still has R2 PUTs in progress. Keep each stage job until
  `stage.expiresAt` plus five minutes. If the action later finds the stage missing, it advances the
  same jobs after its PUTs finish. It must not shorten the cleanup window.
- Frontmatter caps: 128 distinct fields (`files_metadata_MAX_FRONTMATTER_FIELDS`) and 512 index documents (`files_metadata_MAX_FRONTMATTER_INDEX_DOCUMENTS`), both in `packages/app/shared/files-metadata.ts`. On the CREATE path the metadata insert helper's `Too many frontmatter fields` throw rolls the publish back, and the pipeline does not map that throw, so the API caller sees a generic error instead of a clean 400; the orphaned stage is swept by the hourly stage cleanup cron. On the FILL path the committed chunks refresh through materialization, which settles over-cap frontmatter with the `contentFrontmatterTooLarge*` marker pair instead of failing the request — the write returns 200 and the committed content stays at the last sequence that fit (see `../files-editable-text/SKILL.md`).

`write-many` batch semantics:

1. Auth first, then the 8 MB bounded body read (`read_request_text_bounded`).
2. Validate every item with the single-route rules before writing anything — one bad item is a whole-request 400 with the offending `path`. Duplicate normalized paths in one batch are a 400 too.
3. One up-front bulk-bucket charge, then sequential writes (concurrent publishes would conflict on shared ancestor folders).
4. Per-item outcomes: `{ written: [{ path, nodeId, contentType, unchanged? }], errors: [{ path, message, errorCode }] }`. A mid-batch `unauthenticated` aborts the whole request with 401; other failures are reported per item and the batch continues.

# Binary upload pipeline

For each file, `upload-urls` creates an active `files_nodes` doc, a `files_r2_assets` doc, and a signed
PUT URL. The URL writes directly to
`organizations/<org>/workspaces/<ws>/assets/<assetId>` with signed `If-None-Match: *`.
The R2 finalizer confirms the object and publishes its metadata. Reusing the URL cannot overwrite it.

The whole batch validates before any write. It checks canonical paths, sizes, collisions, per-path
actor/account ACL including restricted ancestors, current write policies on replacement files and destination ancestors,
and quota. One bad item returns 400, 403, or 409 with its `path`, and creates nothing. Each asset stores
`uploadUrlExpiresAt`, like `create_upload_node`. Creating these docs accepts
the upload. A later policy change does not cancel publication or processing. The finished node keeps its current policy.

- `upload-urls` is the deliberate public CREATE path for stored files and editable documents alike: an upload whose stored type is an editable text type converts into an editable document on finalization. The caller's `contentType` wins when it is valid, `application/octet-stream` included; the name is only a hint when no type is sent, and a file with neither is stored bytes (`files_resolve_upload_content_type`). Media uploads keep their type for plugin routing.
- `skipProcessing: true` inserts assets with `processingWorkId: null`: the R2 event finalizer records the object (r2Key, real size, etag) but starts no text conversion and no plugin dispatch. Import tools want this; app-like uploads omit it.
- Until the R2 event arrives, the asset has no `r2Key` and `files/list` reports the file as `pending`. Events can arrive minutes late through Cloudflare queue retries.
- Every asset is born with `unfinalizedExpiresAt` (now + 24 h). Publication clears it. Recovery inspects the direct object hourly for 30 hours after its URL was issued, then weekly. After eight days, a missing ordinary upload loses its placeholder and asset after an exact-key deletion handoff. An unprotected pending service upload keeps its placeholder and target but retires that asset; a retry uses a new asset. Any local or inherited write policy defers retirement, including a selected-writer policy, because background cleanup cannot act as the selected writer. The deletion ledger remains through the signed URL's write window. Non-upload assets retain their existing reference checks and retry policy.
- Known residual: a presigned PUT url outlives key revocation for its TTL, and the finalizer records the real object size without a cap check (declared size is a mint-time check only).

# Guardrails

- Keep `public_api_Scope` as the explicit scope union. Do not export one constant per scope. Check
  standalone scope literals and collections with `satisfies`, and keep the exhaustive
  scope-to-permission map checked with `satisfies Record<public_api_Scope, ...>`.
- Keep batch item caps <= their bucket capacities, and keep the caps named as constants next to the other `FILES_*` limits.
- Keep per-item error messages exact — importers match on them. Do not blur per-item errors to hide restricted-path existence; that leak is accepted and documented in the access-control skill.
- New routes need: schema entry in `api_schemas_Main`, a route definition in `public_api_http_routes.ts` (or the matching feature route module), `public_api_authorize_request` with an explicit `requiredScope`, a rate-bucket decision, a root route-inventory entry, and tests for scope refusal plus at least one batch/limit edge. Add every new scope to the exhaustive scope-to-app-permission map in `public_api_http_auth.ts`; use `null` only when no app permission applies. Keep a cheap implementation static only when its imports stay small. Otherwise, load the heavy implementation through one literal dynamic import inside the registered route.
- A route that a plugin call reaches must settle its `plugins_event_run_calls` row on every exit, including refusals. The plugin-data routes that a `plugin_run` may reach do this through one `settle(...)` helper so a new early return cannot leave a call hanging. The four service-only plugin-data routes (versioned write, versioned delete, reserve, and release-reservation) never settle, because `allowedKinds` excludes `plugin_run` so their `pluginCallId` is always null. Adding `plugin_run` to one of those lists means adding its settle calls in the same change.
